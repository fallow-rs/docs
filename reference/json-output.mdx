This page lists the JSON output of each fallow command for scripts, CI jobs and agents. [Findings](/concepts/findings) explains findings, rules and gates.

## Get JSON output {#get-json-output}

Add `--format json` to a command. Add `--quiet` to remove the progress lines from stderr:

```bash
fallow dead-code --format json --quiet
```

| Option or variable | Effect |
|:--|:--|
| `--pretty` | Indents the JSON. Without it, the output is one line. |
| `--explain` | Adds the definitions of the metrics, the rules and the fields to `_meta`. |
| `--lean` | Leaves out empty arrays and zero counts. Only `fallow dead-code`, `fallow health` and the bare `fallow` run accept it. Other commands exit with code 2 ([Lean JSON](/cli/global-flags#lean)). |
| `--output-file <PATH>` | Writes the report to a file. |
| `FALLOW_FORMAT=json` | Sets JSON as the default format. |
| `FALLOW_SUGGESTIONS=off` | Leaves out `next_steps`. |

The samples on this page come from a small demo project. They are shortened: whole lines are removed.

## Stability rules {#stability}

- **Paths.** Each path is relative to the project root and uses `/`.
- **`kind`.** Each envelope has a `kind` field that names its shape. Branch on `kind`, not on the fields that you find.
- **`schema_version`.** Each envelope has its own `schema_version`, which is independent of the fallow `version` and of the other envelopes. It changes when a field gets a new name or type, or when fallow removes a field. It also changes when a required enum field gets a new value, or a finding gets a new required field.
- **New fields.** A new optional field does not change `schema_version`. Ignore the fields that you do not know.
- **Open sets.** The names in `gate_outcomes` and the `kind` of a `workspace_diagnostics` entry are open sets. A new name can appear without a new `schema_version`.
- **Same input, same output.** Two runs on one commit give the same bytes, except `elapsed_ms`, `head_sha` and `_meta.telemetry.analysis_run_id`.

## The envelope {#envelope}

Most envelopes share these top-level fields:

| Field | Content |
|:--|:--|
| `kind` | The name of the envelope, for example `"dead-code"`. |
| `schema_version` | The version of this envelope. A number or a string, as in the samples. |
| `version` | The fallow version that wrote the output. |
| `elapsed_ms` | The time of the analysis in milliseconds. |
| `gate_outcomes` | One entry for each [gate](/concepts/findings#gates) that the run checked. See [Gate outcomes](#gate-outcomes). |
| `request_outcomes` | One entry for each request that narrows the run, for example `--changed-since`, with `status`: `applied` or not. |
| `workspace_diagnostics` | Problems with the project that are not findings. See [Workspace diagnostics](#workspace-diagnostics). |
| `next_steps` | Read-only commands to run next: `id`, `command`, `reason`. At most 3 entries, the most important first. Absent when it is empty. |
| `_meta` | `telemetry.analysis_run_id` in each run. With `--explain`, also `docs`, `field_definitions`, `metrics` and `rules`. |

### Findings and actions {#actions}

Each finding is an object in an array of its issue type, for example `unused_exports`. Most findings have these fields:

| Field | Content |
|:--|:--|
| `path`, `line`, `col` | The place of the finding. |
| `finding_id` | A stable id of the finding, for example `dc1:unused-export:b650995c7b5b87c1`. |
| `effective_severity` | The severity of the rule for this file: `error` or `warn`. |
| `actions` | The fixes and suppressions for this finding. |

Each entry of `actions` has a `type`, an `auto_fixable` boolean and a `description`. `auto_fixable` applies to this finding only: one `type` can be fixable on one finding and not on another. A suppression action has the comment to add in `comment`. [`fallow fix`](/cli/fix) applies the actions with `auto_fixable: true`.

An `add-to-config` action resolves a finding with a new entry in the config file, for example in `ignoreDependencies` or `ignoreExports`. It has `config_key`, `value`, and can have `value_schema`: a URL to the part of the published `schema.json` that describes `value`. A program can read that schema and check `value` before it writes the value into the config file:

```json
{
  "type": "add-to-config",
  "config_key": "ignoreDependencies",
  "value": "autoprefixer",
  "value_schema": "https://raw.githubusercontent.com/fallow-rs/fallow/main/schema.json#/properties/ignoreDependencies/items"
}
```

### Next steps {#next-steps}

`next_steps` is separate from the `actions` of each finding. Each entry is `{ id, command, reason }`, and `command` never changes a file. The `id` values are `setup`, `impact-report`, `trace-unused-export`, `trace-clone`, `complexity-breakdown`, `scope-workspaces`, `audit-changed` and `recheck-baseline`. Through MCP, use the `id` to call the matching tool, not the `command` in a shell.

- `setup` (`fallow agent install --dry-run`) comes only in a run outside CI, on a project with findings and no config file. It goes away when a config file exists, or after `fallow init --decline`.
- `impact-report` (`fallow impact`) comes at most once a week, when local [Impact tracking](/cli/impact) is on and its counts are not zero. It can come on a clean run.
- `recheck-baseline` comes when a narrowed run loads a baseline that it cannot judge. Its command reads the baseline again over the whole project. See [Baseline staleness](/cli/baselines#baseline-staleness).

### Gate outcomes {#gate-outcomes}

`gate_outcomes` holds one entry for each gate, keyed by the gate name, for example `error-severity-findings`:

| Field | Content |
|:--|:--|
| `status` | `pass`, `warn`, `fail` or `skipped`. |
| `enforced` | `true` when a `fail` sets exit code 1. |
| `observed` | The measured value, when the gate has one. |
| `threshold`, `threshold_label` | The limit of the gate. |

A gate fails the run when `status` is `fail` and `enforced` is `true`. The bare `fallow` run in a JSON format reports a failed gate with `enforced: false`, unless you pass `--fail-on-issues`.

### Workspace diagnostics {#workspace-diagnostics}

Each `workspace_diagnostics` entry has `path`, `kind` and `message`. `message` ends with a step to take. `degrades_analysis: true` marks a problem that can make the result incomplete, for example a file that fallow cannot parse. A diagnostic never changes the exit code. [Warnings about the config](/configuration/overview#config-warnings) explains the kinds about config entries.

```json
{
  "path": ".",
  "kind": "rule-packs-not-configured",
  "message": "No rule packs are configured, so the policy detector did not run and its violation counts are zero because nothing was measured. Add `rulePacks` to the config, or set `policy-violation` to off to state that the check is not wanted."
}
```

Some kinds have more fields:

| Kind | Fields |
|:--|:--|
| `production-excluded-file-imported` | In [production mode](/concepts/production-mode), a built-in production pattern excluded a source file that a production file imports. `pattern` is the built-in pattern, verbatim. `file_count` is the exact number of such files for that pattern. `files` lists the first five files in path order, relative to the project root. `path` is the first file. Fallow writes one entry for each pattern, with `degrades_analysis: true`. |
| `inert-flag` | A flag has no effect on this run. `flag` names the flag, `analysis` names the analysis, and `reason` gives the cause. When a config key turns the analysis off, `key` names that key, for example `duplicates.enabled` for `--dupes-baseline`. |
| `env-value-ignored` | An environment variable, such as a `FALLOW_PRODUCTION*` variable, has a value that fallow cannot read, so the run ignores it. `name` names the variable. The entry never holds the value. |
| `config-file-shadowed` | Two config files exist in one directory. `used` names the file that fallow loaded, and `ignored` names the other file. |
| `config-load-fell-back` | The editor could not load the config, so the language server analyzed with the default config. `error` gives the cause. |
| `unknown-security-category` | `security.categories` names a category that fallow does not know. `id` names it. |

The human output prints a flag without effect and an ignored variable as one `Note:` line, and `--quiet` hides that line. `fallow audit --format json` has a root `workspace_diagnostics` array when a notice exists. The MCP tools show these notices in `warnings`, and the language server writes them to its log. To see each setting of a run and its cause, run [`fallow config --resolved`](/cli/config#show-the-settings-of-a-run).

## Errors {#errors}

When a command fails with `--format json`, stdout holds an error document, and the exit code is `2`. The document has no `kind`. This sample comes from `fallow mutation` with uncommitted changes:

```json
{
  "error": true,
  "message": "the git worktree has 1 uncommitted path: package-lock.json",
  "exit_code": 2,
  "code": "FALLOW_MUTATION_DIRTY_WORKTREE",
  "help": "commit or stash the changes, or pass --allow-dirty"
}
```

`error`, `message` and `exit_code` are always present. `code`, a stable name of the error, and `help`, the step to take, are optional. [Exit codes](/reference/exit-codes) lists each code.

## Dead code {#dead-code}

`fallow dead-code --format json`:

| Field | Content |
|:--|:--|
| `total_issues` | The number of findings in all arrays. |
| `entry_points` | The number of entry points from each source. |
| `summary` | The number of findings of each issue type. |
| `unused_files`, `unused_exports`, `unused_dependencies` and the other arrays | One array for each issue type, with one object for each finding. |
| `stale_suppressions` | Suppressions that hide no finding. `origin` describes the comment or the tag. `origin.kind_known: false` marks a token that is not an issue type. |
| `cascade_hidden` | The number of findings in unused files that the report leaves out. Absent when it is 0. With `--group-by`, the field is at the root, and no group has it. SARIF has the same count in `runs[0].properties.cascadeHidden`. See [`showCascade`](/reference/config-rules#showcascade). |
| `baseline`, `baseline_deltas`, `baseline_staleness` | Only in a run with `--baseline`. `baseline_staleness` tells how much of the baseline still matches. Dead code, duplication and health share its fields, for example `scope_reasons`, `gate_trips`, `unrecognised_format`, `saved_by` and `format`. See [Baseline staleness](/cli/baselines#baseline-staleness). |

```json
{
  "kind": "dead-code",
  "schema_version": 11,
  "version": "3.47.0",
  "elapsed_ms": 186,
  "total_issues": 6,
  "unused_exports": [
    {
      "path": "src/lib/format.ts",
      "export_name": "formatPercent",
      "is_type_only": false,
      "line": 3,
      "col": 13,
      "span_start": 103,
      "is_re_export": false,
      "finding_id": "dc1:unused-export:b650995c7b5b87c1",
      "actions": [
        {
          "type": "remove-export",
          "auto_fixable": true,
          "description": "Remove the unused export from the public API"
        },
        {
          "type": "suppress-line",
          "auto_fixable": false,
          "description": "Suppress with an inline comment above the line",
          "comment": "// fallow-ignore-next-line unused-export"
        }
      ],
      "effective_severity": "error"
    },
  "gate_outcomes": {
    "error-severity-findings": {
      "status": "fail",
      "enforced": true,
      "observed": 6.0,
      "threshold_label": "error"
    }
  },
  "next_steps": [
    {
      "id": "trace-unused-export",
      "command": "fallow dead-code --trace src/lib/format.ts:formatPercent",
      "reason": "verify an export is truly unused before deleting"
    },
  ],
  "_meta": {
    "telemetry": {
      "analysis_run_id": "run_d7b2f098153aa420"
    }
  }
}
```

SARIF has the same number in `runs[].properties.cascadeHidden`. The human and Markdown formats print it in a note.

With `--group-by`, the `kind` is `dead-code-grouped`, and `groups` holds the findings of each group.

## Duplication {#dupes}

`fallow dupes --format json`:

| Field | Content |
|:--|:--|
| `clone_groups` | One object for each [clone group](/analysis/duplication): `instances`, `token_count`, `line_count`, `fingerprint`, `spread`, `actions`. |
| `clone_families` | One object for each set of files that share clone groups: `files`, `groups`, `suggestions`, `actions`. |
| `stats` | The totals of all compared code, also when `--top` limits the list. |
| `clone_groups_shown`, `clone_groups_omitted` | The number of groups in `clone_groups`, and the number that `--top` left out. |
| `clone_families_shown`, `clone_families_omitted` | The same numbers for `clone_families`. |
| `range_marker_problems` | [Range markers](/configuration/suppression#suppressing-one-clone-with-a-range) with a problem. |

`fingerprint` holds the [handle](/analysis/duplication) of the group, for example `dup:f42424e8`. Each instance has a `fragment` field with the source text. `--no-fragments` leaves it out.

## Health {#health}

`fallow health --format json`:

| Field | Content |
|:--|:--|
| `findings` | One object for each function above a complexity limit: `cyclomatic`, `cognitive`, `crap`, `severity` (the band), `effective_severity` (the rule), `actions`. |
| `summary` | The numbers of files and functions, the limits, and the number of findings in each band. |
| `health_score` | The [health score](/analysis/health), its grade and its penalties. |
| `vital_signs` | The metrics of the whole project. |
| `file_scores` | The [maintainability index](/analysis/health) and other scores of each file. |
| `hotspot_summary`, `hotspots` | Files that change often and are complex. |
| `targets` | Ranked refactoring targets. |
| `sections` | The sections that the run produced, in a fixed order. |

```json
{
  "kind": "health",
  "schema_version": 13,
  "version": "3.47.0",
  "elapsed_ms": 56,
  "findings": [
    {
      "path": "src/services/customers.ts",

    "files_analyzed": 16,
    "functions_analyzed": 24,
    "functions_above_threshold": 1,
```

## Audit {#audit}

`fallow audit --format json` reports the [changed-code check](/concepts/changed-code):

| Field | Content |
|:--|:--|
| `command` | Always `"audit"`. |
| `verdict` | `pass`, `warn` or `fail`. |
| `changed_files_count` | The number of changed files in scope. |
| `base_ref`, `base_description`, `head_sha` | The base of the comparison and the commit of the head. |
| `summary` | The number of findings in each analysis. |
| `attribution` | The findings that the change introduced and the findings that it inherited, for each analysis. |
| `dead_code`, `duplication`, `complexity` | The findings of each analysis in the changed files. |
| `diff_risk` | Findings about the change itself, for example weakened tests. Absent when there are none. |

```json
{
```

## Architecture {#architecture}

`fallow architecture --format json` has the fields of [Dead code](#dead-code). The architecture arrays hold the findings: `circular_dependencies`, `re_export_cycles`, `package_cycles`, `boundary_violations`, `boundary_coverage_violations`, `boundary_call_violations` and `policy_violations`. With `--shared-state`, `shared_state` holds the shared-state report.

A `boundary_violations` entry has `from_path`, `to_path`, `from_zone`, `to_zone` and `import_specifier`. An import through a barrel file has `via_path`. An import of a file that is not public has `reason: "internal_file"` and `public_files`. See [Boundary configuration](/configuration/boundaries).

```json
{
  "kind": "architecture",
  "schema_version": 2,
  "version": "3.47.0",
  "elapsed_ms": 59,
  "total_issues": 2,
  "boundary_violations": [
    {
      "from_path": "src/reports/invoice.ts",
      "to_path": "src/services/orders.ts",
      "from_zone": "reports",
      "to_zone": "services",
      "import_specifier": "src/services/orders.ts",
      "line": 1,
      "col": 14,
      "finding_id": "dc1:boundary-violation:48f7879d0efd6aba",
      "actions": [
        {
          "type": "refactor-boundary",
          "auto_fixable": false,
          "description": "Move the import through an allowed zone or restructure the dependency",
          "note": "This import crosses an architecture boundary that is not permitted by the configured rules"
        },
        {
          "type": "suppress-line",
          "auto_fixable": false,
          "description": "Suppress with an inline comment above the line",
          "comment": "// fallow-ignore-next-line boundary-violation"
        }
      ],
      "effective_severity": "error"
    },
```

## Security {#security}

`fallow security --format json`:

| Field | Content |
|:--|:--|
| `config` | The configured and the effective severity of each security rule, and the selected categories. |
| `security_findings` | One object for each candidate: `kind`, `category`, `cwe`, `path`, `line`, `evidence`, `severity`, `trace`, `reachability`, `actions`. |
| `unresolved_edge_files`, `unresolved_callee_sites` | The number of places that fallow could not follow. |

With `--summary`, the output has `summary` and no arrays of findings. Each finding is a candidate that a person must check. See [Security](/analysis/security).

Each hop of `trace` has `path`, `line`, `col` and `role`. A hop with the role `secret-source` also has `secret_reads`: one entry (`name`, `line`, `col`) for each non-public env read of that module. [Client-server leak location and trace](/cli/security#client-server-leak-trace) has the detail.

```json
{
  "kind": "security",
  "schema_version": "8",
  "version": "3.47.0",
  "elapsed_ms": 73,
  "security_findings": [
    {
      "finding_id": "016ae89b0e96180f",
      "stable_finding_id": "sec1:f6797a2384c0b3fc",
      "kind": "tainted-sink",
      "category": "dangerous-html",
      "cwe": 79,
      "path": "src/services/render.ts",
      "line": 2,
      "col": 2,
      "evidence": "Non-literal value assigned to el.innerHTML. Candidate for verification: confirm the value is not attacker-controlled, or is sanitized, before it reaches the DOM.",
      "severity": "medium",
  "unresolved_edge_files": 0,
  "unresolved_callee_sites": 9,
```

```json
      "line": 1,
      "col": 45,
```

## Mutation testing {#mutation}

`fallow mutation --format json`:

| Field | Content |
|:--|:--|
| `completion` | `status` and `reasons`. A `partial` run stopped before it tested each mutant, for example at `--max-mutants`. |
| `scope` | The code that the run changed. |
| `runner`, `cache` | The test runner and the result cache. |
| `summary` | The number of mutants with each status, the `score` and the `coverage`. |
| `mutants` | One object for each mutant: the place, the `operator`, the `change`, the `status` and the tests. |
| `functions` | The results of each function. |
| `files` | The changed files with their SHA-256 digest. |
| `gate_outcomes` | The `mutation-min-score` gate, when `--min-score` or `mutation.minScore` sets it. |

## List {#list}

`fallow list --boundaries --format json` has the `kind` `list-boundaries`. `boundaries` holds the zones after preset expansion, with `file_count` for each zone, and the rules:

```json
{
  "kind": "list-boundaries",
  "boundaries": {
    "configured": true,
    "zone_count": 3,
    "zones": [
      {
        "name": "services",
        "patterns": [
          "src/services/**"
        ],
        "file_count": 3
      },
    "rule_count": 3,
    "rules": [
      {
        "from": "services",
        "allow": [
          "shared"
        ]
      },
```

The other `fallow list` options give an object without `kind` and `schema_version`. It has the fields of the requested lists: `plugins`, `files`, `file_count`, `entry_points`, `entry_point_count`, `workspaces`, `workspace_count` and `workspace_diagnostics`. Each entry point has `path` and `source`.

## Explain {#explain}

`fallow explain <issue-type> --format json` describes one issue type. The output has no `schema_version`:

```json
{
  "kind": "explain",
  "id": "fallow/unused-export",
  "name": "Unused Exports",
  "summary": "Export is never imported",
  "rationale": "Named exports that are never imported by any other module in the project. Includes both direct exports and re-exports through barrel files. The export may still be used locally within the same file.",
  "example": "export const formatPrice = ... exists in src/money.ts, but no module imports formatPrice.",
  "how_to_fix": "Remove the export or make it file-local. If it is public API, import it from an entry point or add an intentional suppression with context. To treat exported Effect schemas as type contracts, set effect.schemaExportsAsTypes: fallow then reports them as unused types.",
  "docs": "https://fallow.tools/docs/explanations/dead-code/#unused-exports",
```

## JSON Schema {#schema}

The JSON Schema of each envelope is [`docs/output-schema.json`](https://github.com/fallow-rs/fallow/blob/main/docs/output-schema.json) in the fallow repository. Validate against the schema of the fallow version that you run: an older copy can reject a new `workspace_diagnostics` kind.
