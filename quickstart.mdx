Run one command in your project. In a few seconds, you get a report in three parts: dead code, duplication and complexity. This page shows you how to read each part.

## Before you start

- You need a JavaScript or TypeScript project with a `package.json`.
- You need Node.js 22 or later for `npx`. [Installation](/installation) lists the other ways to get fallow.
- Install the dependencies of your project (`npm install`). Fallow reads the packages in `node_modules`. Without them, it can report an import or a dependency wrongly.

## Run fallow

Go to the root of your project and run:

```bash
npx fallow
```

Fallow needs no config file for this run. It reads your `package.json`, turns on a [plugin](/concepts/plugins) for each framework and tool that you use, and analyzes each source file.

The examples on this page come from a small demo project with 16 files.

## Read the header

```text
■ Metrics: dead files 6.3% (1 of 16) · dead exports 14.3% (3 of 21) · MI 92.8 (good)
  16 files analyzed
  3 entry points detected (2 package.json, 1 plugin)
```

| Part | Meaning |
|:--|:--|
| `dead files` | The share of files that no entry point reaches. |
| `dead exports` | The share of exports that no file imports. |
| `MI` | The [maintainability index](/analysis/health), from 0 to 100. Higher is better. |
| `entry points` | The number of files where your code starts, and how fallow found them. |

An [entry point](/concepts/entry-points) is a file that something outside your source code runs, for example the start of your app or a test. Fallow follows the imports from each entry point. The dead code part of the report is only as good as this line.

If fallow prints `No entry points detected`, stop here. Read [Entry points and reachability](/concepts/entry-points), and tell fallow where your code starts.

## Read the dead code part

```text
● Unused files (1)
  src/utils/legacy-currency.ts
  Files not reachable from any entry point

● Unused exports (3)
  src/lib/format.ts
    :3 formatPercent
  src/lib/index.ts
    :1 formatPercent (re-export)
  src/services/orders.ts
    :18 cancelOrder
  Exported symbols with no known consumers

● Unused dependencies (1)
  left-pad
  Listed in dependencies but never imported

● Unlisted dependencies (1)
  uuid
  Packages imported in code but missing from package.json

✗ 1 file · 3 exports · 1 unused dependency · 1 unlisted dependency (0.09s)
```

Each group holds the [findings](/concepts/findings) of one issue type. A finding in a file gives the path, the line and the name. A dependency finding gives the package name.

| Finding | Meaning | Usual fix |
|:--|:--|:--|
| [Unused file](/rules/unused-file) | No entry point reaches the file. | Delete the file. |
| [Unused export](/rules/unused-export) | The file is in use, but no file imports this name. | Remove the `export` keyword, or delete the code. |
| [Unused dependency](/rules/unused-dependency) | `package.json` lists the package, but no file imports it. | Remove it from `package.json`. |
| [Unlisted dependency](/rules/unlisted-dependency) | A file imports the package, but `package.json` does not list it. | Add it to `package.json`. |

`formatPercent` appears twice. Line 3 of `format.ts` defines the function. Line 1 of `index.ts` exports it again for other files. Both lines are one problem: remove the name from `index.ts`, then remove the `export` keyword in `format.ts`.

## Read the duplication part

```text
● Duplicates (1 clone groups)

     17 lines  2 instances  spread 2  dup:f42424e8
    src/reports/export.ts:3-19
    src/utils/summary.ts:7-23

⚠ 34 lines (20.0%) duplicated across 2 files (0.01s)
```

A [clone group](/analysis/duplication) is one block of code that exists in two or more places. This group has 17 lines, and two files hold it. `dup:f42424e8` is the name of the group.

The last line counts each copy: 2 times 17 lines is 34 lines. The percentage is the share of the code that fallow compared. By default, fallow does not compare test files such as `*.test.ts`.

## Read the complexity part

```text
● High complexity functions (1)
  No coverage file found, so CRAP scores are a static estimate. Pass `--coverage <coverage-final.json>` for measured scores, or raise `health.maxCrap`.
  src/services/customers.ts
    :9 classifyCustomer CRITICAL
          23 ! cyclomatic   32 ! cognitive   39 lines
         552.0 ! CRAP
```

Fallow lists the functions that are hard to change safely. The `!` marks each number that is above its limit.

| Number | Meaning |
|:--|:--|
| `cyclomatic` | The number of paths through the function. |
| `cognitive` | An estimate of how hard the function is to read. Nested code counts more. |
| `CRAP` | Complexity combined with test coverage. A complex function without tests gets a high number. |

Without a coverage file, fallow estimates the coverage from the imports of your tests. [Health and complexity](/analysis/health) explains each number, its limit, and how to use real coverage. The complexity part also lists a score for each file and the refactoring targets.

## Read the result

```text
Failed: dead-code (6 issues), dupes (1 clone group), health (1 above threshold): start with src/services/customers.ts
Setup: `fallow init` writes a config; `fallow agent install --dry-run` previews the agent guide, skills, MCP server, and commit gate (hide this hint: `fallow init --decline`).
```

The `Failed:` line names each part that has findings, and the file to start with. The `Setup:` line shows while your project has no config file.

This run exits with code 1, because a dead code finding and a complexity finding fail by default. Clone groups alone do not fail the run: you set a limit for duplication yourself. [Exit codes](/reference/exit-codes) lists each code.

## What you learned

- `npx fallow` runs three analyses in one pass: dead code, duplication and complexity.
- The dead code part starts from the entry points.
- A finding names a file, a line and a name, or a package.
- The exit code is 1 when a finding fails the run.
