In under a minute, you get a list of unused code, duplication, and complexity hotspots in your project. Everyone starts with the same command. At the end, pick the integration that fits your work.

## 1. Run fallow

From your project root, run:

```bash
npx fallow
```

This command runs three analyses in one pass:

- **Dead code**: unused files, exports, dependencies, cycles, boundaries, and more
- **Duplication**: repeated logic across files
- **Health**: complexity hotspots and refactor targets

<Tip>
  Built-in plugins cover Next.js, Vite, Ember, Wuchale, Jest, Tailwind, PandaCSS, Contentlayer, tap, tsd, and more. The first run needs no configuration.
</Tip>

## 2. Run the focused commands you'll use most

```bash
npx fallow dead-code          # Cleanup candidates
npx fallow dupes              # Repeated logic
npx fallow health             # Complexity and refactor targets
npx fallow review             # Advisory review brief over changed files (always exits 0)
npx fallow fix --dry-run      # Preview automatic cleanup
```

- `dead-code` reports unused files, exports, types, dependencies, circular dependencies, and boundary violations. See the [dead code guide](/analysis/dead-code).
- `dupes` finds AST-based duplicates in the default `mild` mode. To also find clones with renamed variables, add `--mode semantic`. See the [duplication guide](/analysis/duplication).
- `health` reports complexity findings, maintainability per file, hotspots, and ranked refactor targets. See the [health explanation](/explanations/health).
- `fix --dry-run` shows the automatic cleanup without changing files. To apply it, remove `--dry-run`. See the [auto-fix guide](/analysis/auto-fix).

<Tip>
  To clean up or refactor TypeScript, add `--type-aware` when aliases,
  re-exports, class contracts, packages, or exact consumers affect the
  decision. This optional semantic pass is slower. See
  [Type-aware TypeScript analysis](/analysis/type-aware).
</Tip>

## Optional: create a config

Fallow works without a config file. To customize it, run:

```bash
fallow init
```

`fallow init` detects your project structure and writes a config for it. It also adds `.fallow/` to your `.gitignore`.

<CodeGroup>
```jsonc .fallowrc.json
{
  "$schema": "https://raw.githubusercontent.com/fallow-rs/fallow/main/schema.json",
  "entry": ["src/workers/*.ts", "scripts/*.ts"],
  "ignorePatterns": ["**/*.generated.ts"],
  "rules": {
    "unused-files": "error",
    "unused-exports": "warn",
    "unused-types": "off"
  }
}
```
```toml fallow.toml
entry = ["src/workers/*.ts", "scripts/*.ts"]
ignorePatterns = ["**/*.generated.ts"]

[rules]
unused-files = "error"
unused-exports = "warn"
unused-types = "off"
```
</CodeGroup>

<Info>
  To migrate from knip or jscpd, run `fallow migrate`, or read the [knip](/migration/from-knip) or [jscpd](/migration/from-jscpd) guide.
</Info>

## Optional: runtime intelligence

The static layer of fallow is free and open source. To learn which code actually executed in production, add the runtime layer:

```bash
npx fallow license activate --trial --email you@company.com
npx fallow coverage setup
npx fallow health --runtime-coverage ./coverage
```

Before you start, read [Static vs runtime intelligence](/explanations/static-vs-runtime) to learn how the two layers differ. Then follow the [runtime coverage guide](/analysis/runtime-coverage) for the setup.
