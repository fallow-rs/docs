A value from the command line goes into a shell command, and nothing checks it. Somebody who controls that value can then run any command on your server, and no test of the normal case shows it. `fallow security` finds the places in your code where unsafe input can reach a dangerous call, or where a server secret can reach a browser bundle. Each result is a **candidate**: a place to check, not a confirmed vulnerability.

```bash
npx fallow security
```

The analysis is opt-in: it runs only with this command, and `fallow audit` and bare `fallow` do not report its candidates. It runs no code. Its cost is the review: each candidate needs a person or a coding agent to check it.

## What fallow finds

This example adds two files to the demo project. `src/reports/archive.ts` passes its argument to `exec()`, and `src/index.ts` calls it with `process.argv[2]`. `src/lib/banner.ts` writes HTML, and no file imports it.

```ts
// src/reports/archive.ts
import { exec } from "node:child_process";

export const archiveReports = (target: string): void => {
  exec(`tar -czf ${target} reports/`);
};
```

## How fallow decides

The two candidates above are both sinks, and the first one also has untrusted input on its path. Fallow looks for two kinds of candidates.

A **sink** is a call or an assignment that is dangerous with an unsafe value: `exec()`, `innerHTML`, `eval()`, a SQL `query()`, a `fetch()` to a computed URL, and others. Fallow has a catalogue of sinks, grouped in categories with a CWE number. A sink becomes a candidate when its argument is not a literal. Some categories check literal values, for example `rejectUnauthorized: false` or a `postMessage` to the origin `"*"`.

A **client-server leak** ([`client-server-leak`](/rules/client-server-leak)) is a file with a top-level `"use client"` directive that reaches a non-public `process.env` value through its imports. Fallow follows the imports from each client file. Public names such as `NEXT_PUBLIC_*` and `VITE_*` are not secrets. A client file that reaches a server-only module, for example one that imports `node:fs`, is a `server-only-import` candidate. The demo has no client file, and the second blind spot says so.

For each candidate, fallow adds three facts that set the priority:

- **Untrusted input.** A **source** is a value that comes from outside: a request parameter, `process.argv`, a `message` event. Fallow reports `arg-level` when the argument of the sink comes from a source in the same file, and `module-level` when only an import connects them.
- **Reachability.** Fallow checks whether an entry point reaches the file of the sink.
- **Boundaries.** Fallow checks whether the path crosses from server code to client code, or crosses an [architecture](/analysis/architecture) boundary.

A candidate gets `high` when an entry point reaches a sink with an argument from a source. A crossed boundary also gives `high`, and so does [runtime coverage](/analysis/runtime-coverage) that shows that the code runs often. Another candidate with untrusted input gets `medium`. Each other candidate gets `low`. The `exec()` call gets `medium`, because the source is in `src/index.ts` and only an import connects it to the sink. Fallow does not prove that a value reaches the sink without a check, so each candidate needs verification.

## Act on a finding

Read the trace, and open the code at each step. In the demo, `process.argv[2]` goes into `archiveReports` with no check, so the first row of this table applies:

| Situation | Action |
|:--|:--|
| An attacker can control the value, and nothing checks it. | Fix the code: validate the input, use a fixed list of values, or use an API without a shell or without HTML. |
| A check or a sanitizer exists that fallow does not see. | Put `// fallow-ignore-next-line security-sink` above the line, and add the reason. |
| The file is also unused. | Delete the file, as for `src/lib/banner.ts`. |

A coding agent can verify the candidates for you. Run `fallow security --format json --surface` to get each candidate with its trace. The agent checks each candidate and writes a verdict file. Then `fallow security survivors` shows only the candidates that the agent kept. Fallow makes no model calls itself. [Verify security candidates with an agent](/cli/security-agent-verification) has the input and the verdict format.

## Fail a run

By default, `fallow security` reports and exits with code 0, also when old code has many candidates. The option `--gate new` fails a run only on the candidates that a change adds. In the demo, a branch adds the two files above:

```bash
npx fallow security --gate new --changed-since main
```

```text
Gate: REVIEW REQUIRED, 2 new security items in changed lines. fallow has not confirmed a vulnerability.
```

The run exits with code 8 when the change adds a candidate on a changed line. Candidates in old code do not fail the gate. Exit code 8 is only for this gate, so a CI job can allow it without a hidden error. Use `--gate newly-reachable --changed-since main` to fail when the change makes an old candidate reachable from an entry point. [Changed code and baselines](/concepts/changed-code) explains how fallow finds the changed lines.

To fail on each candidate in some paths, set the rule to `error` in your config file. For example, the rule `security-sink` can be `error` for `src/api/**` with an `overrides` entry. See [Rules](/configuration/rules).

## What fallow cannot see

- A candidate is not a vulnerability. The `high` priority means "check this first".
- Fallow cannot follow a call through dynamic dispatch or a computed member. The JSON output counts these places as `unresolved_callee_sites`. Run `fallow security blind-spots` to list them.
- The client-server leak check needs `"use client"` files, or the React Router plugin. Without them, it checks nothing and says so.
- The catalogue does not find a weakness in logic, for example a missing permission check.
