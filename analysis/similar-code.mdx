Two teams often solve one problem twice, with different code. For example, one function trims and lower-cases the email address of an order form. Another function cleans the email address of an imported order with a regular expression. When a new email rule arrives, the fix reaches one function, and the other keeps the bug. [`fallow dupes`](/analysis/duplication) does not find this pair, because it compares the code itself. `fallow similar-code` compares the meaning of whole functions with a model that runs on your machine. Use it after `fallow dupes`, to find logic that you can merge after a review.

```bash
npx fallow similar-code
```

<Warning>
  Each result is an unverified candidate. The score is not a probability. It does not prove that the two functions behave the same, and it does not mean that a merge is safe. Read both functions and their tests before you decide.
</Warning>

The analysis is opt-in. It is not part of bare `fallow`, `fallow audit`, `fallow dupes`, CI gates, SARIF output or the editor diagnostics. It adds no issue type, and a candidate does not change the exit code.

## What fallow finds

### Before the first run

The analysis needs two parts that the `fallow` package does not install:

1. The `fallow-similar-code` package, at the same version as `fallow`:

   ```bash
   npm install --save-dev fallow-similar-code@<fallow version>
   ```

2. The pinned model, a download of about 324 MB. The first download needs your confirmation:

   ```bash
   npx fallow similar-code setup --local
   ```

   Before it asks, setup shows the model, the license and the download size. Project config and agents cannot approve the download for you. Without a terminal, setup stops unless you pass `--yes`.

To check that both parts are ready, run `fallow similar-code status`. Its `Ready` line says `yes` or `no`, and when a part is missing, a `Next` line names the step. A `fallow` binary from Homebrew or `cargo install` finds the `fallow-similar-code` program only in its own directory. [`fallow similar-code`](/cli/similar-code) explains that setup.

After setup, the analysis runs offline. The source of your functions stays on your machine. Fallow stores the computed vectors in a cache in your user directory, with one namespace for each project. `fallow similar-code cache clear --yes` removes them and keeps the model.

### The report

For this example, add the two email functions of the opening to the demo project: `normalizeOrder` in `src/orders/normalize.ts` and `cleanImportedOrder` in `src/imports/clean.ts`. The human report has this form. Each candidate is a pair of functions, with the command that inspects it:

```text
Similar-code candidates (unverified)
Model score is cosine similarity, not a probability or refactor verdict.

similar-code:candidate:v1:<hex>  score 0.9123  High
  src/orders/normalize.ts:12  normalizeOrder
  src/imports/clean.ts:8  cleanImportedOrder
  Inspect: fallow similar-code inspect similar-code:candidate:v1:<hex> --candidates similar-code.json

Completion: Complete
Cache: Miss (0 hits, 42 misses, 42 writes)
```

| Part | Meaning |
|:--|:--|
| `similar-code:candidate:v1:<hex>` | The id of the candidate. The inspect and review steps use it. |
| `score 0.9123` | The cosine similarity of the two function vectors. 1 is the highest value. It has meaning only for the pinned model and the current settings. Use it to rank your review work. |
| `High` | The band of the score: `VeryHigh` from 0.95, `High` from 0.88, and `Moderate` below 0.88. |
| `Completion: Complete` | Each phase of the run finished. |
| `Cache` | The vectors that fallow read from the cache, and the vectors that it computed. |

An empty list proves that no candidate exists only when the completion is `Complete`. A `Partial` run tells you in its JSON output which limit or problem stopped the work.

## How fallow decides

Fallow takes each function of at least `similarCode.minLines` lines (default 3). The model turns each function into a vector, and fallow compares the vectors of each pair. A pair with a score at or above `similarCode.threshold` (default 0.8) is a candidate.

A large project gives many pairs, so narrow the search with the scope options of the other analyses:

```bash
npx fallow similar-code --file src/orders/normalize.ts
npx fallow similar-code --changed-since main
npx fallow similar-code --threshold 0.88 --min-lines 6 --top 20
```

`--file` keeps the pairs that include the file. `--changed-since` keeps the pairs that touch a changed file.

## Act on a candidate

A candidate is not a finding, so you record your decision in a file of your own. The review has three steps:

1. Save the candidates as JSON:

   ```bash
   npx fallow similar-code --format json --quiet > similar-code.json
   ```

2. Inspect one candidate. Run the command from the same project root:

   ```bash
   npx fallow similar-code inspect similar-code:candidate:v1:<hex> \
     --candidates similar-code.json --format json --quiet
   ```

   Inspect first checks that both functions did not change since the search. Then it adds the evidence that it can find, for example:

   - the source of both functions and the imports between them,
   - the callers, the callees and the related tests,
   - the owners and the recent changes,
   - overlap with `fallow dupes`, and hints such as `async` or `throw`.

   Inspect marks each kind of evidence that it cannot find as missing.

3. Write your decision in a separate verdict file. Fallow does not change the candidate file:

   ```json
   {
     "schema_version": "1",
     "verdicts": [
       {
         "candidate_id": "similar-code:candidate:v1:<hex>",
         "review_key": "similar-code:review:v1:<hex>",
         "candidate_worthy": true,
         "behaviorally_equivalent": false,
         "refactor_safe": false,
         "outcome": "related-but-distinct",
         "rationale": "Both normalize orders, but only the import path keeps external IDs."
       }
     ]
   }
   ```

Each judgment is `true`, `false` or `null` (unknown). `refactor_safe: true` needs `behaviorally_equivalent: true`, and that needs `candidate_worthy: true`. The outcome is one of `same-responsibility`, `related-but-distinct`, `intentional-duplication`, `unrelated` and `needs-human-review`.

When you merge two functions, run your tests and `fallow dupes` again.

### With an agent

The MCP server has two read-only tools: `find_similar_code` and `inspect_similar_code`. Neither tool downloads the model, changes code or writes a verdict. When setup is missing, the agent must ask you to run the setup. When the behavior is not clear, the agent must give the outcome `needs-human-review`. See [MCP server](/integrations/mcp).

## Fail a run

A candidate never changes the exit code, so the search itself cannot fail a run. The review can: to join the candidates and the verdicts, and to fail when a candidate has no verdict, run:

```bash
npx fallow similar-code review --candidates similar-code.json \
  --verdicts verdicts.json --require-verdict-for-each-candidate
```

A candidate without a verdict then makes the command exit with code 2. [`fallow similar-code`](/cli/similar-code) has the other exit codes.

## What fallow cannot see

- How two functions behave. A high score means that they read alike to the model, and the model runs no code.
- A shared block inside two large functions. The model compares whole functions, and `fallow dupes` finds those blocks.
- A meaning of a score outside one project. A score depends on the model and the settings. Do not compare scores between projects, and do not use a score as a quality limit.

Config can set the threshold, the minimum size and the `ignore` globs. It cannot choose another model, another provider or a remote service.
