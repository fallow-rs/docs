Code that nothing uses still costs you. People read it, tests run it, and a search shows it. `fallow dead-code` finds the files and the exports that your project does not use, so that you can delete them.

```bash
npx fallow dead-code
```

## What fallow finds

```text
  3 entry points detected (2 package.json, 1 plugin)

── Unused Code ─────────────────────────────────────

● Unused files (2)
  src/utils/legacy-currency.ts
  src/utils/legacy-report.ts
  Files not reachable from any entry point
  https://fallow.tools/docs/explanations/dead-code/#unused-files

● Unused exports (3)
  src/lib/format.ts
    :3 formatPercent
  src/lib/index.ts
    :1 formatPercent (re-export)
  src/services/orders.ts
    :18 cancelOrder
  Exported symbols with no known consumers
  https://fallow.tools/docs/explanations/dead-code/#unused-exports
  To auto-fix: fallow fix --dry-run
  To suppress: // fallow-ignore-next-line unused-export

● Unused type exports (1)
  src/services/order-book.ts
    :3 OrderStatus

● Unused enum members (1)
  src/services/order-book.ts
    :8 Channel.Phone

● Unused class members (1)
  src/services/order-book.ts
    :18 OrderBook.clear

✗ 2 files · 3 exports · 1 type · 1 enum member · 1 class member · 1 unused dependency · 1 unlisted dependency (0.03s)
  2 findings in unused files are hidden · --show-cascade shows them
```

| Part | Meaning |
|:--|:--|
| `3 entry points detected` | The [entry points](/concepts/entry-points) where fallow starts. When fallow finds none, this line starts with `⚠ No entry points detected`, and the findings are not reliable. |
| `● Unused files (2)` | The issue type and the number of [findings](/concepts/findings) of that type. |
| `:3 formatPercent` | The line and the name of one finding. |
| `(re-export)` | The line of a [barrel file](/concepts/entry-points) that exports the name again. One fix removes both lines. |
| The URL | The page that explains the issue type. |
| `To auto-fix`, `To suppress` | The command that fixes the findings, and the comment that hides one finding. |
| `✗` | At least one finding has the [severity](/concepts/findings) `error`, so the command exits with code 1. |
| `2 findings in unused files are hidden` | Findings inside the unused files. See [Findings in unused files](#findings-in-unused-files). |

The same run also reports dependency findings, such as `left-pad` and `uuid` here. [Dependencies](/analysis/dependencies) explains them. `fallow dead-code` has more issue types, for example unresolved imports, duplicate exports and framework findings. [Issue types](/reference/issue-types) lists each one.

## How fallow decides

Fallow starts at each entry point and follows each import. [Entry points and reachability](/concepts/entry-points) explains this walk. Then fallow checks each kind of code:

- An [unused file](/rules/unused-file) is a file that no entry point reaches. A file that only unused files import is also unused. Fallow never reports an entry point as an unused file.
- An [unused export](/rules/unused-export) is an export of a reachable file that no file imports. Fallow follows each name through barrel files to the file that declares it.
- An [unused type](/rules/unused-type) is an exported type alias or interface that no file uses. An `import type` counts as a use.
- An [unused enum member](/rules/unused-enum-member) is a member of a used enum that no code reads. `Object.values(Channel)` and other uses of the whole enum count for each member.
- An [unused class member](/rules/unused-class-member) is a method or a property that no code outside the class reads. A call inside the class itself does not count.

Fallow reads the code and does not run it. It does not use the TypeScript type checker. The opt-in [type-aware analysis](/analysis/type-aware) adds the type checker for the cases that syntax cannot decide.

### Class members

Fallow checks public methods, public properties and static methods. It does not report these members:

- `private` members and `#private` members.
- `protected` members. The opt-in rule [`unused-protected-class-member`](/rules/unused-protected-class-member) checks them.
- Members with a decorator, such as `@Get()` or `@Input()`. A decorator tells fallow that a framework calls the member. To check the members of a decorator that is only a label, list it in [`ignoreDecorators`](/reference/config-dead-code#ignoredecorators).
- Lifecycle methods of React and Angular, such as `componentDidMount` and `ngOnInit`. Add other names that a framework calls to [`usedClassMembers`](/reference/config-dead-code#usedclassmembers).

A call through a parent class counts for each override in a child class. When code uses the whole object, for example `Object.keys(book)` or `{ ...book }`, fallow counts each member as used.

### Exports of an entry point

Fallow does not report the exports of an entry point, because code outside your project can use them. When a [plugin](/concepts/plugins) knows the names that a framework reads, fallow checks the other exports of that file. [Entry points and reachability](/concepts/entry-points) explains both cases.

### Imports of a whole module

For `import * as m from "./m"`, fallow counts only the names that the code reads, such as `m.a`. Code that reads each key, such as `Object.keys(m)`, uses each export. [Entry points and reachability](/concepts/entry-points) has the table of import forms.

### Findings in unused files

An unused file can also hold unused exports, types and members. Fallow does not list these findings, because the delete of the file removes them. The last line of the report gives their number. To list them, add `--show-cascade`:

```bash
npx fallow dead-code --show-cascade --unused-files --unused-exports
```

```text
● Unused exports (5)
  src/utils/legacy-currency.ts (2)
    :1 toGuilders
    :3 fromGuilders
  src/lib/format.ts
    :3 formatPercent
```

The [`showCascade`](/reference/config-rules#showcascade) key in the config file does the same for each run. The health metrics count these findings with and without the option.

## Act on a finding

First check the finding. `--trace` shows why fallow reports an export:

```bash
npx fallow dead-code --trace src/services/orders.ts:cancelOrder
```

```text
  UNUSED cancelOrder in src/services/orders.ts

  File: reachable
  Namespace: value
  Reason: No references found, export is unused
```

For a file, use `--trace-file`. It shows the exports of the file and the files that import it:

```bash
npx fallow dead-code --trace-file src/utils/legacy-report.ts
```

```text
  UNREACHABLE src/utils/legacy-report.ts

  Exports (1):
    export legacyTotal [unused]

  Imports from (1):
    <- src/utils/legacy-currency.ts
```

[Find why fallow reports a finding](/guides/trace-a-finding) shows each trace command. Then act on the finding:

| Situation | Action |
|:--|:--|
| Nothing uses the code. | Delete the file, the export or the member. |
| Only the file itself uses an export. | Remove the `export` keyword and keep the code. |
| A tool or a framework loads the code, and fallow does not know it. | Correct the entry points or the plugin. See [Fix a wrong finding](/guides/false-positives). |
| You keep the code on purpose. | Add a suppression comment. See [Suppress a finding](/guides/suppress). |

`fallow fix` removes unused exports and unused enum members for you. Run `fallow fix --dry-run` first. [Fix findings automatically](/guides/auto-fix) explains what it changes.

### Work in this order

1. Delete the unused files.
2. Run `fallow dead-code` again.
3. Remove the unused exports, types and members.

An import in an unused file still counts as a use of an export. When you delete the file, the exports that only that file imported become unused. The second run shows them.

## Set a limit

By default, each issue type on this page has the severity `error`. A finding then makes the command exit with code 1. A finding at the severity `warn` shows in the report and does not change the exit code. To fail on these findings too, add `--fail-on-issues`:

```bash
npx fallow dead-code --fail-on-issues
```

To change the severity of an issue type, set its [rule](/concepts/findings) in the config file:

```jsonc
// .fallowrc.jsonc
{
  "rules": {
    "unused-class-members": "warn"
  }
}
```

An existing project often has many findings on the first run. Save a [baseline](/guides/baselines), so that fallow fails only on new findings. On a pull request, run [`fallow audit`](/analysis/changed-code). It judges only the findings that the change introduces.

## Limits

- Fallow cannot follow a path that exists only when the code runs, for example `import(name)` with a variable. Name these files in `dynamicallyLoaded`.
- Fallow cannot see code that uses a name through reflection, for example a dependency injection container that reads class names.
- Fallow cannot see a use outside the project, for example a file that only a deploy script outside the repository runs.
- A file that only tests import is reachable in a normal run. Use [production mode](/concepts/production-mode) to check the code that ships.

[Limits of fallow](/guides/limits) lists each known limit and its workaround.
