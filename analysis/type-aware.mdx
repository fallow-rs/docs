Fallow reads your code as syntax. It does not run the TypeScript compiler. Some TypeScript facts are not in the syntax of your files, for example a method that an interface of a package requires. The **type-aware analysis** is an opt-in analysis that uses the TypeScript type checker to confirm what syntax alone cannot decide. Turn it on with `--type-aware`.

## What fallow finds

A job class implements the `Job` interface of a package. The package calls `run()`. Your code never calls it:

```ts
// src/cleanup-job.ts
import type { Job } from "job-queue";

export class CleanupJob implements Job {
  async run(): Promise<void> {
    console.log("remove old sessions");
  }
}
```

```ts
// src/index.ts
import { schedule } from "job-queue";
import { CleanupJob } from "./cleanup-job";

schedule(new CleanupJob());
```

Without the type checker, fallow does not read the `Job` interface in the package. It reports `run` as unused:

```bash
npx fallow dead-code --unused-class-members
```

```text
● Unused class members (1)
  src/cleanup-job.ts
    :4 CleanupJob.run
  Class methods or properties never referenced outside their class

✗ 1 class member (0.04s)
```

With `--type-aware`, the type checker resolves `Job` to its declaration in the package. The interface requires `run`, so fallow removes the finding:

```bash
npx fallow dead-code --unused-class-members --type-aware
```

The type-aware analysis adds these results:

| Result | Where |
|:--|:--|
| A check of each [`unused-export`](/rules/unused-export), [`unused-type`](/rules/unused-type) and [`unused-class-member`](/rules/unused-class-member) finding | `fallow dead-code`, `fallow audit` and bare `fallow` |
| The exact consumers of one export, the affected files and the tests to run | `fallow dead-code --symbol-impact src/api.ts:Client` |
| Public signatures that use a type that the package does not export ([`private-type-leak`](/rules/private-type-leak)) | `fallow dead-code --private-type-leaks` |
| Public types that tie modules or packages together | `fallow health --type-coupling` |
| A check that a mutant still compiles | `fallow mutation --typecheck` |

## How fallow decides

Fallow first runs its normal analysis. Then it sends only the candidates to the type checker: the exports, types and class members that the normal analysis reports as unused. The type checker answers for the exact declaration. A name that only looks the same is not enough.

Each candidate gets one outcome:

| Outcome | Finding |
|:--|:--|
| `confirmed-used` | Removed. The type checker found a reference. |
| `contract-preserved` | Removed. An interface, an abstract member, an override or a framework contract requires the declaration. |
| `confirmed-no-static-references` | Kept. Each project that owns the file has no reference. |
| `retained-unresolved` | Kept. The type checker could not resolve the declaration or its project. |
| `retained-abstained` | Kept. Dynamic code, a decorator, an overload or another known gap stops a sure answer. |

Thus, the type-aware analysis removes findings of these three kinds. It never adds one. The rule `private-type-leaks` is an exception: it is `off` by default, and a type-aware run sets it to `warn` when your config does not set it. Each result also has a status: `complete`, `partial` or `unavailable`. [Evidence and its limits](/concepts/evidence) explains what static evidence can prove.

`fallow fix --type-aware` removes a class member only when each owning project gives a complete negative answer, and the declaration did not change. Run it with `--dry-run` first.

## Turn it on

The type checker runs in a separate package, `fallow-type-aware`. It brings TypeScript 7, so the `fallow` package does not install it. Install it in your project next to `fallow`, at the same version. Fallow accepts only an exact version match:

```bash
npm install --save-dev fallow fallow-type-aware@<your fallow version>
```

A global `fallow` needs a global `fallow-type-aware`. A one-off `npx fallow` that is not in your project does not find the project package: start both packages with `npx -p fallow@<version> -p fallow-type-aware@<version> fallow`.

Check that fallow finds it:

```bash
npx fallow type-aware status
```

Then turn the analysis on for one run with `--type-aware`, or for each run in your config file:

```jsonc
// .fallowrc.jsonc
{
  "typeAware": {
    "enabled": true,
    "require": "best-effort"
  }
}
```

Pass `--no-type-aware` to keep one run syntactic. When fallow misses a TypeScript project that uses your code, add it with `--type-aware-project packages/web/tsconfig.json`. The option is repeatable.

### Homebrew, Cargo and binary installs {#homebrew-cargo-and-binary-installs}

A `fallow` binary from Homebrew, `cargo install` or a release archive does not find an npm package. On macOS and Linux, run `fallow type-aware setup` once. The command downloads the signed package of its own fallow version into your user directory. The package needs Node.js 20 or later on `PATH`. On Windows, install `fallow` and `fallow-type-aware` from npm. The GitHub Action and the GitLab template install the package themselves. [`fallow type-aware`](/cli/type-aware) has the details of `status`, `setup` and `cleanup`.

## Cost

The type checker builds a TypeScript program for each selected project and scans its symbols. This adds time to the run, and more time on a large project. A CLI or CI run pays this cost each time. The editor keeps the program in memory between saves. One request to the type checker can take 2 minutes at most. Change the limit with `FALLOW_TYPE_AWARE_TIMEOUT_SECS`.

Fallow starts the type checker only when the run has a candidate for it. A run with no candidate costs nothing extra.

## Set a limit

`typeAware.require` decides what happens when the type checker cannot give a complete answer:

| Cause | `best-effort` (default) | `complete` |
|:--|:--|:--|
| Fallow finds no `fallow-type-aware` package | The syntactic findings. The kinds that the analysis can remove (the three above and `private-type-leak`) get `warn`, so they do not fail the run. | Exit code 2 |
| The type checker fails, times out, or gives a partial answer | The syntactic findings at their configured severity | Exit code 2 |

Start with `best-effort`. Use `--type-aware-require complete` in CI only when an incomplete answer must fail the job.

`fallow audit` compares the base and the head of a change with the same type-aware setting. To keep the audit syntactic, set `audit.typeAware` to `false`.

## Svelte virtual-module exports {#svelte-virtual-module-exports}

The Svelte tools make a virtual TypeScript module for each `.svelte` file. The type checker that fallow uses cannot make these modules. Fallow supports a default import of a component, and a named export that the type checker can see.

A project can import or export again a named binding from a `.svelte` file that the type checker cannot resolve. Fallow then marks the project `unavailable` with the reason `svelte-virtual-module-exports`. With `best-effort`, fallow keeps the syntactic findings. With `complete`, the run fails.

Do not move valid component exports to a `.ts` file only for fallow. Use `svelte-check` for Svelte and TypeScript errors.

## Limits

- The type-aware analysis does not replace `tsc --noEmit` or a linter. Fallow does not report compiler errors or typed lint findings.
- The type checker sees only your projects. A consumer outside them, for example a user of your published package, stays unknown. Package exports and `publicPackages` still decide which exports are public.
- `confirmed-no-static-references` does not prove that code is unused. Reflection, framework registration and runtime behavior can use it.
- Dynamic member access, decorators, overloads and a non-literal `import()` make fallow keep the finding.
