Type-aware mode lets you delete or refactor TypeScript code with exact TypeScript checker evidence. It follows exact symbol identity across aliases, re-exports, packages, and tests.

The default fallow analysis is Rust-native and syntactic. It does not need Node.js or the TypeScript compiler. Add `--type-aware` when a cleanup or refactor depends on exact TypeScript symbol identity.

The optional companion adds these project-wide capabilities:

- Exact symbol-use confirmation for existing dead-code candidates.
- Symbol traces with namespaces, aliases, and re-export hops.
- Package API surfaces and private type leaks across files.
- Exact consumers, affected files, and targeted tests.
- Public-signature type coupling, as advisory findings.

Use this pass when a real cleanup or refactor decision depends on TypeScript identity. For fast everyday feedback, keep the normal syntactic run.

```bash
fallow type-aware status --format json --quiet
fallow dead-code --unused-class-members --type-aware --format json --quiet
fallow fix --type-aware --dry-run --format json --quiet
fallow dead-code --type-aware --symbol-impact src/api.ts:Client --format json --quiet
fallow health --type-aware --type-coupling --format json --quiet
fallow dead-code --constant-parameters --type-aware --format json --quiet
```

## What this does not replace

Keep `tsc --noEmit` for compiler correctness and Oxlint for local lint rules. Fallow does not emit TypeScript diagnostics or repeat local typed lint findings.

Type-aware fallow answers project-wide questions that those tools do not:

- Is this exact declaration used through an alias or re-export?
- Which production files and tests depend on this exported symbol?
- Does a public signature expose a package-private type?
- Which public types couple packages or modules together?
- Does a default value of a parameter ever apply, and which calls does a class method have? The opt-in [constant-parameter](/explanations/dead-code#with-type-evidence) rule reads this evidence when `--type-aware` is on.

## Conservative results

Every semantic result reports `complete`, `partial`, or `unavailable`. Fallow removes a dead-code candidate only when the checker resolves the exact identity of its declaration. When the analysis is partial or unavailable, fallow keeps the original finding and reports a stable omission reason.

`fallow fix --type-aware` offers a class-member removal only when two conditions are true: every owning project returns complete negative evidence, and the declaration guard still matches. Always preview with `--dry-run`.

<Warning>
  Evidence that the checker can see does not prove that a published API has no external consumers. For library boundaries, package exports, `publicPackages`, visibility tags, and explicitly selected consumer projects stay authoritative.
</Warning>

To fail the CI job when semantic evidence is incomplete, use `--type-aware-require complete`:

```bash
fallow dead-code --type-aware --type-aware-require complete \
  --format json --quiet
```

When automatic project selection misses a consumer, add a `--type-aware-project` flag for each project. The flag is repeatable:

```bash
fallow dead-code --type-aware \
  --type-aware-project tsconfig.json \
  --type-aware-project packages/web/tsconfig.json \
  --format json --quiet
```

## Svelte virtual-module exports

Svelte language tooling creates virtual TypeScript modules for `.svelte` files. TypeScript-Go does not yet expose the plugin integration that fallow needs to build the same virtual modules. Fallow still supports default component imports, and named exports backed by declarations that the checker can see.

A selected project can use a named import, named re-export, or wildcard re-export whose `.svelte` target does not resolve. In that case, fallow abstains with `svelte-virtual-module-exports` and reports the project and the affected semantic queries as `unavailable`. In best-effort mode, fallow keeps the syntactic result as advisory evidence. With `--type-aware-require complete`, the run fails.

For authoritative Svelte and TypeScript diagnostics, run `svelte-check`. Do not rewrite valid component exports only to satisfy fallow. Keep the Svelte project configuration as it is, and rely on the omission reason until TypeScript-Go provides a supported virtual-module host integration.

## Persistent configuration

Keep the feature opt-in for each repository:

```jsonc
{
  "typeAware": {
    "enabled": true,
    "projects": ["tsconfig.json"],
    "require": "best-effort"
  }
}
```

Start with `best-effort`. Use `complete` only when partial or unavailable semantic evidence must fail the run.

### When the type-aware pass cannot run

The result depends on `typeAware.require` and on the cause:

| Cause | `best-effort` (default) | `complete` |
|:------|:------------------------|:-----------|
| No companion found | Syntactic findings. The kinds that the pass can disprove are reported at `warn` | Exit code 2 |
| The companion failed, timed out, or gave a partial result | Syntactic findings at their configured severity | Exit code 2 |

"No companion found" means that fallow found no `fallow-type-aware` file. There is no file at the `FALLOW_TYPE_AWARE_BIN` path, no companion next to the active `fallow` executable, and no companion in the `fallow type-aware setup` directory.

The kinds that the pass can disprove are `unused-export`, `unused-type`, `unused-class-member` and `private-type-leak`. Without a companion, the run lowers each `error` rule of these kinds to `warn`, in the base rules and in `overrides`. A finding that the pass could remove then does not fail the run.

`--fail-on-issues` and `--ci` usually raise each `warn` finding to `error`. Without a companion, these four kinds stay at `warn` and do not fail the run. These flags still raise every other `warn` rule to `error`. This applies to `fallow dead-code`, `fallow audit` and the bare `fallow` run.

The JSON output of such a run keeps `_meta.type_aware.executed: false` and the warning in `_meta.type_aware.warnings`. `gate_outcomes` gets a `type-aware-fallback` entry with `status: skipped` and `enforced: false`. A companion that starts and then fails adds no `type-aware-fallback` entry.

The editor also shows the syntactic findings when it finds no companion, but at their configured severity.

## Performance

Type-aware analysis builds an additional TypeScript Program and scans checker symbols. On the current public release corpus, the added time is about 92 ms at the median and 2.3 seconds at P95. Large projects can take longer. Editor sessions reuse the loaded Program. One-shot CLI and CI runs pay the cold setup cost each time.

## Installation

The `fallow` npm package does not install the companion, because it brings TypeScript 7 (about 30 MB). Install `fallow-type-aware` at the same version as `fallow` when you use `--type-aware`, `mutation --typecheck`, or the `typeAware` config:

```bash
npm install --save-dev fallow-type-aware@<fallow version>
```

The `fallow` launcher finds the companion next to the `fallow` package, or in the project root when both packages are in the same `node_modules` tree. So pnpm projects work too. A global `fallow` needs a global companion (`npm install --global fallow-type-aware@<fallow version>`). npx and other package runners do not use the project companion. Start both packages together (`npx -p fallow@<version> -p fallow-type-aware@<version> fallow`), or set `FALLOW_TYPE_AWARE_BIN` to its executable. The GitHub Action and the GitLab template install the companion themselves.

### Homebrew, Cargo, and binary installs

A `fallow` binary from Homebrew, `cargo install`, or a release archive has no npm launcher, so it does not find a global companion. On macOS and Linux, run `fallow type-aware setup` once:

```bash
fallow type-aware setup
```

You do not need this step when you install `fallow` from npm. The npm launcher finds the companion package itself.

The command does these steps:

1. It runs `node` from `PATH` to read the platform and the architecture. The companion runs on Node.js 20 or later. An x64 Node on an arm64 Mac gets the x64 bundle.
2. It shows the bundle, the source URL, and the target directory, and asks for approval. Pass `--yes` when no terminal is available.
3. It downloads the bundle of its own fallow version from the GitHub release of fallow. The download honors `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, and `FALLOW_CA_BUNDLE`.
4. It verifies the signature of the bundle with the release key in the binary, before it unpacks the bundle.
5. It installs the companion into a user directory that has the fallow version in its name.

| Platform | Directory |
|:---------|:----------|
| macOS | `~/Library/Application Support/fallow/fallow-type-aware/<version>/` |
| Linux | `$XDG_DATA_HOME/fallow/fallow-type-aware/<version>/`, else `~/.local/share/fallow/fallow-type-aware/<version>/` |

The setup bundles are available from the first fallow release that contains the setup command. An older release has no bundle to download.

For a machine with no access to GitHub, copy the bundle and its `.sig` file to the machine. Then install from the file:

```bash
fallow type-aware setup --from fallow-type-aware-<platform>-<arch>.tar.gz
```

The signature file must be next to the bundle, as `<file>.sig`.

The companion still needs `node` on `PATH` each time it starts. An editor can start `fallow-lsp` with a shorter `PATH` than your shell. Then the companion reports that Node.js 20 or later must be on `PATH`.

After a fallow upgrade, the installed companion stays in use while it uses the same wire protocol as the new fallow version. When the protocol changes, `fallow type-aware status` tells you to run `fallow type-aware setup` again. A companion of an older protocol stops with `unsupported protocol_version`. Fallow then adds this hint: run `fallow type-aware setup`, or install the companion of the current fallow version from npm.

To remove the companions of other fallow versions, run:

```bash
fallow type-aware cleanup
```

The command keeps the companion that fallow uses now. It also removes the temporary directories that an interrupted setup leaves. It asks for approval, or needs `--yes`.

On Windows, `fallow type-aware setup` has no bundle. The npm launcher starts the companion through Node. Install `fallow` and the companion from npm: `npm install --global fallow@<version> fallow-type-aware@<version>`.

On every platform, you can also set `FALLOW_TYPE_AWARE_BIN` to a trusted companion executable. Set it in the environment that starts fallow, for example your shell profile or the environment of your editor.

### How fallow finds the companion

Fallow does not search `node_modules` or `PATH` for the companion. It checks these locations in this order:

1. The path in `FALLOW_TYPE_AWARE_BIN`.
2. A companion next to the active `fallow` executable.
3. The `fallow type-aware setup` directory. Fallow prefers the install of its own version. Otherwise it uses the newest install with the same wire protocol.

The npm launcher, the Node bindings, and the VS Code extension find the companion package themselves, and pass it through `FALLOW_TYPE_AWARE_BIN`.

`fallow type-aware status` checks discovery, protocol version, and backend version, and reports where fallow found the companion. It does not analyze the project. See [fallow type-aware](/cli/type-aware).

### Experimental tsrs backend

Set `FALLOW_TYPE_AWARE_BACKEND=tsrs` to run the semantic pass on tsrs, a Rust port of the TypeScript 7 checker, instead of the default TypeScript-Go backend. The environment variable is the only way to select the backend. There is no `typeAware.backend` config key, and the config file rejects it as an unknown field. The backend stays opt-in while tsrs has no stable release.

Fallow accepts any `tsrs` from `0.18.0` up to (not including) `1.0.0`, and any `tsrs` from `7.1.0` up to (not including) `8.0.0`, so you can reuse the `tsrs` that your project already installs. From `7.1.0-beta.tsrs2`, tsrs uses the version of the TypeScript release that it ports. Both version schemes port TypeScript 7.1. Fallow 3.44.0 and earlier accept only the `0.x` releases. The `tsrs` must be where `fallow-type-aware` can resolve it. To install the version that Fallow tests:

```bash
npm install --save-dev tsrs@7.1.0-beta.tsrs3
FALLOW_TYPE_AWARE_BACKEND=tsrs npx fallow type-aware status
```

#### Select the backend on each surface

Fallow reads the variable once per process. Every Fallow process that you start inherits it from its parent.

| Surface | How to select tsrs |
| --- | --- |
| CLI, npm scripts, and CI | Set `FALLOW_TYPE_AWARE_BACKEND=tsrs` in the script or in the job `env`. |
| MCP | Add the variable to the `env` block of the server entry in the MCP client config. |
| LSP in other editors | Set the variable in the environment of the `fallow-lsp` process. |
| VS Code | Start the editor with `FALLOW_TYPE_AWARE_BACKEND=tsrs` and with `FALLOW_TYPE_AWARE_BIN` set. See below. |

For MCP, use an `env` block like this:

```json
{
  "mcpServers": {
    "fallow": {
      "command": "fallow-mcp",
      "env": { "FALLOW_TYPE_AWARE_BACKEND": "tsrs" }
    }
  }
}
```

The VS Code extension bundles a companion that holds only the default backend. That companion cannot load tsrs. With only the backend variable set, the type-aware pass is unavailable and Fallow shows conservative syntactic findings. To use tsrs in VS Code, set both variables and start the editor from that shell:

```bash
export FALLOW_TYPE_AWARE_BACKEND=tsrs
export FALLOW_TYPE_AWARE_BIN="$PWD/node_modules/.bin/fallow-type-aware"
code .
```

An existing `FALLOW_TYPE_AWARE_BIN` takes precedence over the bundled companion. Use an absolute path, because Fallow resolves a relative path from the working directory. The project must have `tsrs` installed where that companion can resolve it. The extension has no setting for the backend.

#### Check the selection

Run `fallow type-aware status` in the same environment as the surface. It names the backend and the version that ran. `_meta.type_aware` in the JSON output names them too. The command does not read the config file. A version outside the supported range makes the type-aware pass unavailable, and `type-aware status` names the range. An unknown backend value also makes the pass unavailable, and `type-aware status` names the known values.

#### Limits

- The tsrs backend refines findings, but its evidence never makes a fix eligible. Guarded fixes need the evidence of the default backend at the version that Fallow tests.
- tsrs `0.18.0` has no Windows or macOS x64 binaries. Use `0.20.0` or later on those platforms.
- The default backend also accepts any TypeScript 7 release that a package manager override selects.
- Fallow will consider a config key when tsrs has a stable release or when the default backend moves to TypeScript 7.1 with corpus evidence for tsrs.
