`fallow dupes` finds duplicated code blocks in your whole codebase and ranks them, so you know which copies to extract first. It runs in the same audit as the dead code, dependency, complexity, and architecture checks. For raw duplication scans, jscpd v5 is faster on the current README benchmark fixtures.

```bash
fallow dupes
```

## Why built-in duplication matters

Most dead-code analysis tools find only unused exports and unreachable files. Fallow also detects duplication in the same binary, with the same module graph. You can therefore compare dead code with duplication in one pass.

`fallow dead-code --include-dupes` finds code blocks that are duplicated and unused. These are the best blocks to clean up first. When you delete one, you remove dead code and duplication in one change.

One run for duplication and dead code also gives you:

- **One tool, one config, one CI step.** You do not install and configure a separate duplication detector.
- **Shared file discovery.** The same ignore patterns, entry points, and workspace config apply to both analyses.
- **Combined findings.** Fallow reports clone families in unused files as combined findings.
- **The same output formats.** JSON, SARIF, markdown, compact, and CodeClimate output work the same way for duplication and for dead code.

## Detection modes

<Tabs>
  <Tab title="Strict">
    Only exact token-for-token clones. Fallow applies no normalization. The code must be character-identical after tokenization.

    ```bash
    fallow dupes --mode strict
    ```

    Use it to find exact copies with no changes.
  </Tab>
  <Tab title="Mild (default)">
    The default mode. Strict and mild modes give identical results, because AST-based tokenization already removes whitespace and comments before the comparison.

    ```bash
    fallow dupes --mode mild
    ```

    Start with this mode for general detection.
  </Tab>
  <Tab title="Weak">
    Matches clones also when string literal values differ. Variable names must still match.

    ```bash
    fallow dupes --mode weak
    ```

    Use it to find copied code where only the strings (URLs, messages, labels) changed.
  </Tab>
  <Tab title="Semantic">
    Finds clones with renamed variables and different literal values. Token-type normalization matches code with the same structure.

    ```bash
    fallow dupes --mode semantic
    ```

    The broadest mode. Finds code that someone copied and then changed with new variable names and values.
  </Tab>
</Tabs>

<Info>
  `dupes --mode semantic` still compares normalized code structure. To find
  complete functions that can have the same intent with a different structure,
  use the separate, opt-in [`fallow similar-code`](/analysis/similar-code)
  workflow. Its model-backed results are always unverified, and you must review them.
</Info>

### Near-miss clones

To also report function-scoped clones with small structural edits, add `--near`:

```bash
fallow dupes --near
```

Near-miss detection uses semantic token normalization. Every pair in a group must have at least 80% shingle similarity. It runs next to exact clone detection. It is opt-in, because it does more work and can report code that a person must review. To turn it on by default, set `duplicates.near` to `true`, or use `fallow.duplication.near` in VS Code.

Typical output:


## Thresholds and limits

```bash
fallow dupes --min-tokens 50        # Minimum tokens per clone (default: 50)
fallow dupes --min-lines 5          # Minimum lines per clone (default: 5)
fallow dupes --min-occurrences 3    # Only report clones repeated 3+ times (default: 2)
fallow dupes --threshold 5          # Fail if duplication exceeds 5%
fallow dupes --skip-local           # Only cross-directory duplicates
```

### Minimum occurrences

By default, fallow reports every duplicated pair (`minOccurrences: 2`). If you follow the "rule of three" and refactor logic only when it appears in three or more places, raise the threshold:

```jsonc
{
  "duplicates": {
    "minOccurrences": 3
  }
}
```

Fallow rejects values below `2`, because a single occurrence is not a duplicate. A higher value skips pairs that can depend on context, and keeps the copies that are worth an abstraction. The VS Code extension has the same control as the `fallow.duplication.minOccurrences` setting.

### Spread-aware ranking

Fallow ranks clone groups so the most expensive copies come first. It multiplies the duplicated token count by the occurrence count, then adds a spread boost. Spread is the maximum directory-tree distance between copies. For copies in the same file, each 250 lines between them count as one spread step. The boost is at most 15%, so larger and more repeated clones stay the main priority.

The default report and `--top` use this order. The JSON output has `spread` on every clone group, and `similarity` on near-miss groups.

### Reviewed clone groups

When a clone group is intentional, add it to `duplicates.ignoredClones`. Fallow still reports all other duplication findings:

```jsonc
{
  "duplicates": {
    "ignoredClones": ["dup:6f12ab34:2"]
  }
}
```

Each entry is the `fingerprint` of the group plus its instance count. Copy the fingerprint from the human listing or from `clone_groups[].fingerprint` in JSON, then add `:<instance_count>`. After a token change or a new copy, fallow reports the group again. An edit that changes only formatting keeps the same fingerprint.

When fallow hides reviewed groups, the JSON output sets `stats.clone_groups_ignored`. When work limits skip candidate comparisons in a near-miss run, fallow sets `stats.near_candidates_skipped`. The near-miss result can then be incomplete.

#### Migrating collision handles

Ordinary `dup:<8hex>` handles and widened `dup:<16hex>` handles do not change. When groups have the same full content fingerprint, their handles use `dup:<16hex>-rN`. A collision handle stays the same when you produce an identical report from another checkout location. It can change when the colliding groups change.

Older numeric collision handles such as `dup:<16hex>-1` still load in `ignoredClones`, but they no longer hide or select a group. With a baseline that has these handles, the affected findings also appear again. To migrate:

1. Run `fallow dupes` again.
2. Review each affected group.
3. Copy its reported handle into your configuration, or refresh the baseline.

Do not replace `-1` with `-r1` without a review. The number can point to a different group.

Before you add `-rN` keys to `ignoredClones`, upgrade every runner that reads a shared configuration. Older binaries reject that syntax.

## Clone families

Fallow puts clone groups with the same set of files into a **clone family** and suggests a refactoring:

- **Extract function**: the clones are in the same file.
- **Extract module**: the clones are in more than one file.

## Cross-language detection

To compare TypeScript and JavaScript files, pass `--cross-language`. Fallow removes type annotations before it compares:

```bash
fallow dupes --cross-language
```

Fallow converts `.ts` files to their `.js` equivalent for the comparison. This finds clones where someone converted one copy from TypeScript to JavaScript, or the reverse.

## Ignoring imports

Two files with the same imports are not copy-paste. By default, fallow removes this module wiring from the token stream. This covers ES imports, re-export declarations, and top-level static `require()` binding declarations.

To count module wiring as clone candidates again, use the command-line flag:

```bash
fallow dupes --no-ignore-imports
```

Or set it in the config:

```jsonc
{
  "duplicates": {
    "ignoreImports": false
  }
}
```

Fallow still counts these:

- runtime code
- local exports
- side-effect `require()` calls
- nested `require()` calls
- dynamic require arguments
- mixed declarations

## Incremental analysis

To check duplication only in the files that changed since a git ref, pass `--changed-since`:

```bash
fallow dupes --changed-since main
```

In CI, this reports only the duplication that a pull request adds.

## Baseline comparison

To add duplication limits to an existing codebase, save the current duplication as a baseline. Fallow then fails only on new duplication:

```bash
# Save current duplication as baseline
fallow dupes --save-baseline fallow-baselines/dupes.json

# Fail only on new duplication
fallow dupes --baseline fallow-baselines/dupes.json
```

## Debugging

To see all clones of one code location, trace it:

```bash
fallow dupes --trace src/utils.ts:42
```

All runs are cold (no cache), so each tool starts from zero. Bold marks the fastest tool per row.

| [astro](https://github.com/withastro/astro) | 2,859 | 549ms | **189ms** | jscpd 2.9x |
| [fastify](https://github.com/fastify/fastify) | 286 | 90ms | **64ms** | jscpd 1.4x |
| [next.js](https://github.com/vercel/next.js) | 20,552 | 12.66s | **861ms** | jscpd 14.7x |
| [preact](https://github.com/preactjs/preact) | 244 | 58ms | **49ms** | jscpd 1.2x |

The Rust rewrite of jscpd (v5) is faster than fallow for raw duplication scans on these projects. Fallow runs duplication in the same audit pass as the dead code, dependency, complexity, CSS, framework, and security checks.

Fallow finds clones with a <Tooltip tip="A sorted array of all suffixes of a string. It finds patterns without a comparison of each pair.">suffix array</Tooltip> and an <Tooltip tip="Longest Common Prefix array. With a suffix array, it finds the longest shared sequences between code blocks.">LCP</Tooltip> array. This avoids a quadratic comparison of each pair.
