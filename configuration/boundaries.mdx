The `boundaries` key of the [config file](/configuration/overview) sets which parts of the code may import which other parts. [Architecture](/analysis/architecture) explains the analysis and how to act on a finding.

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "zones": [
      { "name": "services", "patterns": ["src/services/**"] },
      { "name": "reports", "patterns": ["src/reports/**"] },
      { "name": "shared", "patterns": ["src/lib/**", "src/utils/**"] }
    ],
    "rules": [
      { "from": "services", "allow": ["shared"] },
      { "from": "reports", "allow": ["shared"] },
      { "from": "shared", "allow": [] }
    ]
  }
}
```

`fallow architecture` reports each import that a rule does not allow as a `boundary-violation` finding:

```text
● Boundary violations (2)
  src/reports/invoice.ts:1 → src/services/orders.ts (reports → services)
  src/reports/receipt.ts:1 → src/services/orders.ts (reports → services)
```

The [`boundaries` reference](/reference/config-architecture#boundaries) has the type of each key.

## Zones {#zones}

A zone is a named set of files. Each entry of `zones` has these keys:

| Key | Content |
|:--|:--|
| `name` | The name that rules use. |
| `patterns` | Globs of the files in the zone, relative to the project root or to `root`. |
| `autoDiscover` | Directories. Each child directory becomes its own zone. See [Auto-discovered zones](#auto-discovered-zones). |
| `root` | A subdirectory. `patterns` and `autoDiscover` are then relative to it. |
| `publicFiles` | Globs of the files that other zones may import. See [Public entry files](#public-entry-files). |

- A file belongs to the first zone with a matching pattern. Put a specific zone before a broad zone.
- A file that matches no zone has no restrictions. It can import each zone, and each zone can import it.
- The patterns follow the [glob rules](/configuration/overview#path-globs).
- A zone that matches no file gives the warning `boundary zone '<zone>' matched 0 files`.

### One zone for each package {#monorepo-zones}

In a [monorepo](/configuration/workspaces), give each package a zone with `root`. The `patterns` and the `publicFiles` of the zone are then relative to the package directory:

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "zones": [
      { "name": "ui", "root": "packages/ui", "patterns": ["src/**"], "publicFiles": ["src/index.ts"] },
      { "name": "web", "root": "apps/web", "patterns": ["src/**"] }
    ],
    "rules": [{ "from": "web", "allow": ["ui"] }]
  }
}
```

An import from `apps/web` into `packages/ui/src/internal/x.ts` is then a finding with `reason: "internal_file"`. [Public entry files](#public-entry-files) explains this reason.

## Rules {#rules}

Each entry of `rules` restricts one zone:

| Key | Content |
|:--|:--|
| `from` | The zone that imports. |
| `allow` | The zones that `from` may import. |
| `allowTypeOnly` | Zones that `from` may import types from. See [Type-only imports](#type-only-imports-across-boundaries). |

- A file can always import a file of its own zone.
- A zone without a rule has no restrictions.
- A rule with an empty `allow` list isolates the zone. It can import no other zone.
- The rules apply to each analyzed file, also to a file that no entry point reaches.
- A named or default import through a barrel file counts against the zone of the module that declares the name. The finding names the barrel in `via_path`. A namespace import or a side-effect import counts against its direct target.

## Type-only imports {#type-only-imports-across-boundaries}

`allowTypeOnly` allows imports of types from a zone that is not in `allow`. TypeScript removes these imports, so they add no runtime dependency.

| Allowed by `allowTypeOnly` | Not allowed |
|:--|:--|
| `import type { Foo } from "..."` | `import { type Foo, Bar } from "..."`: `Bar` is a value |
| `import type * as ns from "..."` | `import { Foo } from "..."` |
| `import { type Foo } from "..."`, when each name has `type` | `import "..."`: a side-effect import |
| `export type { Foo } from "..."` | |

A type-only import is allowed when its target zone is in `allow` or in `allowTypeOnly`. No preset sets `allowTypeOnly`.

## Public entry files {#public-entry-files}

`publicFiles` lists the files of a zone that other zones may import, for example an `index.ts`:

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "zones": [
      { "name": "billing", "patterns": ["src/modules/billing/**"], "publicFiles": ["src/modules/billing/index.ts"] },
      { "name": "orders", "patterns": ["src/modules/orders/**"] }
    ],
    "rules": [{ "from": "orders", "allow": ["billing"] }]
  }
}
```

- An import from another zone into a file that is not public is a finding with `reason: "internal_file"`. The `public_files` field names the files to import.
- An import that a rule does not allow is a finding without `reason`, also when the target is public.
- A re-export chain stops at a public file. Fallow judges the import by the public file.
- The check applies to imports from each other zone, also from a zone without a rule. Files outside each zone are not checked.
- When no file of a zone matches its `publicFiles` globs, fallow writes a warning.
- On an `autoDiscover` zone, each glob is relative to each discovered directory. `["index.ts"]` gives each child zone its own `index.ts`.

## Auto-discovered zones {#auto-discovered-zones}

`autoDiscover` makes each child directory its own zone, named `<zone>/<directory>`:

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "zones": [
      { "name": "features", "patterns": ["src/features/**"], "autoDiscover": ["src/features"] },
      { "name": "shared", "patterns": ["src/shared/**"] }
    ],
    "rules": [{ "from": "features", "allow": ["shared"] }]
  }
}
```

With `src/features/auth` and `src/features/billing`, the zones are `features/auth` and `features/billing`. An import from one feature into another is then a finding.

- A rule for the parent zone applies to each child zone. A rule for a child zone, such as `from: "features/auth"`, replaces it for that child.
- The parent zone may import its child zones, so a barrel file in `src/features` can export each feature.
- When the zone also has `patterns`, the files directly in `src/features` belong to the parent zone. Without `patterns`, these files are in no zone.

## Presets {#presets}

`preset` gives a set of zones and rules for a common architecture:

```jsonc
// .fallowrc.json
{ "boundaries": { "preset": "bulletproof" } }
```

| Preset | Zones | Rules |
|:--|:--|:--|
| `layered` | `presentation`, `application`, `domain`, `infrastructure` | `presentation` may import `application`. `application` may import `domain`. `infrastructure` may import `domain` and `application`. `domain` is isolated. |
| `hexagonal` | `adapters`, `ports`, `domain` | `adapters` may import `ports`. `ports` may import `domain`. `domain` is isolated. |
| `feature-sliced` | `app`, `pages`, `widgets`, `features`, `entities`, `shared` | Each layer may import each layer below it in this list. |
| `bulletproof` | `app`, `features` (auto-discovered), `shared`, `server` | `app` may import `features`, `shared` and `server`. `features` may import `shared` and `server`. `server` may import `shared`. `shared` is isolated. |

A preset zone has the pattern `<root>/<zone>/**`. The `shared` zone of `bulletproof` covers `components`, `hooks`, `lib`, `utils`, `utilities`, `providers`, `shared`, `types`, `styles` and `i18n`. `<root>` is the `compilerOptions.rootDir` of the `tsconfig.json` in the project root. When that value is missing, `.`, absolute or outside the project, `<root>` is `src`. Custom zones do not use `rootDir`.

## Merge a preset with your zones {#merging-presets-with-custom-config}

You can set `preset` together with `zones` and `rules`:

- A zone with the name of a preset zone replaces the preset zone. It takes the place of your zone in the list.
- A rule with the `from` of a preset rule replaces the preset rule.
- Other zones and rules come after the preset zones and rules.

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "preset": "hexagonal",
    "zones": [{ "name": "domain", "patterns": ["src/core/**"] }]
  }
}
```

This config keeps `adapters`, `ports` and the three rules, and puts the `domain` zone in `src/core`.

## Zone coverage {#boundary-coverage}

`coverage` reports the files that are in no zone:

| Key | Content |
|:--|:--|
| `requireAllFiles` | When `true`, each analyzed source file outside each zone is a `boundary-coverage` finding. Default `false`. |
| `allowUnmatched` | Globs of the files that may stay outside each zone, for example generated code. |

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "zones": [{ "name": "domain", "patterns": ["src/domain/**"] }],
    "coverage": { "requireAllFiles": true, "allowUnmatched": ["src/generated/**"] }
  }
}
```

## Forbidden calls {#forbidden-calls}

`calls.forbidden` bans calls in the files of a zone:

```jsonc
// .fallowrc.json
{
  "boundaries": {
    "zones": [{ "name": "domain", "patterns": ["src/domain/**"] }],
    "calls": {
      "forbidden": [
        { "from": "domain", "callee": "child_process.*" },
        { "from": "domain", "callee": ["console.*", "process.exit"] }
      ]
    }
  }
}
```

Each matching call or `new` expression is a `boundary-call-violation` finding. The finding names the callee, the pattern and the zone.

- A pattern compares whole name segments. `fetch` matches `fetch` and not `myfetch`.
- `object.*` matches each member of the object. `*.member` matches the member on each object.
- A pattern follows imports: `child_process.*` also matches `execSync` from `import { execSync } from "node:child_process"`.
- Fallow matches direct callee paths, also with `?.`. It does not follow a callee in a variable, a computed member or an injected object.
- The policy applies only to files in a zone. Use `coverage.requireAllFiles` to put each file in a zone.
- When two entries match a call, the first entry wins. A bare `*` pattern stops the config load.

## Severity and suppression

The import findings, the coverage findings and the call findings all use the `boundary-violation` rule. Its default is `error`. The `boundary-violation` token in a [suppression comment](/configuration/suppression) hides each of these findings on the line or in the file.

## Check the config {#inspect}

`fallow list --boundaries` prints the zones after preset expansion and merge, with the number of files in each zone:

```text
Boundaries: 3 zones, 3 rules

Zones:
  services             3 files  src/services/**
  reports              3 files  src/reports/**
  shared               6 files  src/lib/**, src/utils/**

Rules:
  services             → shared
  reports              → shared
  shared               (isolated, no imports allowed)
```

Add `--format json` for the same data as JSON. See [JSON output](/reference/json-output#list).

## Accepted cycles {#accepted-cycles}

`circularDependencies.allow` lists [circular dependencies](/rules/circular-dependency) that you accept. Each entry is the list of files of one cycle, in import order, relative to the project root:

```jsonc
// .fallowrc.json
{ "circularDependencies": { "allow": [["src/a.ts", "src/b.ts", "src/c.ts"]] } }
```

The entry accepts only the cycle with these files in this order. The cycle can start at any of its files. An entry that matches no cycle gives a `circular-dependencies-allow-unmatched` warning. [`circularDependencies.allow`](/reference/config-architecture#circulardependencies-allow) has the limits.

## Shared-state allowlist {#shared-state-allowlist}

`sharedStateAllowlist` removes global properties from the shared-state report of `fallow architecture --shared-state`. Each entry is a pair: the global object and its property. Fallow compares each pair exactly, without globs.

```jsonc
// .fallowrc.json
{ "sharedStateAllowlist": [["window", "analyticsQueue"]] }
```
