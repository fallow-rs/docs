Fallow works with no configuration. Add a config file when the defaults do not fit your project, for example to add entry points, ignore generated files, or change rule severity. To create one, run:

```bash
fallow init          # Creates .fallowrc.json
fallow init --toml   # Creates fallow.toml
```

## Config file formats

Fallow looks for config files in this order:

1. `.fallowrc.json` (JSONC, comments allowed)
2. `.fallowrc.jsonc` (same JSONC parser; editors detect the JSON-with-comments syntax from the extension)
3. `fallow.toml`
4. `.fallow.toml`

Fallow checks each directory up to the workspace root, and the first match wins. `.fallowrc.json` and `.fallowrc.jsonc` behave the same. The `.jsonc` extension only tells editors to expect comments.

If one directory has more than one of these files, fallow loads the file with the higher precedence. It prints a warning on stderr that names the ignored file. An old config from a migration therefore cannot take effect without a message.

Fallow parses both JSON forms as JSONC, and the published schema declares this (`allowComments`, `allowTrailingCommas`). Editors that use the JSON language service, such as VS Code and Zed, therefore accept comments and trailing commas in a config that references `schema.json`.

## Config fields

<Accordion title="entry">
Extra entry point glob patterns. Fallow detects entry points from `package.json` (`main`, `module`, `bin`, `exports`) and from framework plugins. Add the files that fallow does not detect.

```jsonc
{
  "entry": ["src/workers/*.ts", "scripts/*.ts", "src/cli.ts"]
}
```
</Accordion>

<Accordion title="Entry point auto-detection">
Without an `entry` config, fallow still finds entry points in your `package.json` fields. These files are the roots of the module graph. Fallow treats all code that they reach as "used."

Fallow reads these `package.json` fields:

| Field | Description |
|:------|:------------|
| `main` | CJS entry point |
| `module` | ESM entry point |
| `types` / `typings` | TypeScript declaration entry point |
| `source` | Source entry point before the build (a common convention for dev tooling) |
| `browser` | Browser entry point (a string, or an object with per-path overrides) |
| `bin` | CLI binaries (a string for one binary, an object for multiple) |
| `exports` | Modern entry point map (resolved recursively, including conditional exports and subpath patterns) |

Fallow resolves the `exports` field recursively. It follows nested conditions such as `"import"`, `"require"`, `"types"`, and `"default"` to their target files. It also includes subpath exports (for example `"./utils"`).

When these fields point at output directories (`dist/`, `build/`, `out/`, `esm/`, `cjs/`), fallow maps the paths back to the same files in `src/` and tries the source extensions. Fallow ignores output directories by default.

Framework plugins add their own entry points to the `package.json` entry points. For example, Next.js adds `pages/**` and `app/**/page.tsx`, and Vitest adds `**/*.test.ts`. Run `fallow list` to see all detected entry points.
</Accordion>

<Accordion title="ignorePatterns">
Glob patterns for files that fallow does not analyze at all.

```jsonc
{
  "ignorePatterns": ["**/*.generated.ts", "**/*.d.ts", "legacy/**"]
}
```

The built-in ignores apply at any depth: `**/node_modules/**`, `**/dist/**`, `**/build/**`, `**/coverage/**`, and the minified-bundle globs. Since 3.26.0, the `build` default is recursive like the others. Fallow therefore also skips a nested `build/` directory with hand-written source. `ignorePatterns` has no negation, so rename or move such a directory, or analyze it as a separate project with `fallow --root <dir>`.

To see which built-in pattern removed files, and how many, run with `--explain-skipped`.
</Accordion>

<Accordion title="ignoreFindings">
Glob patterns for files where fallow does not report dead-code findings. Fallow still discovers and parses matching files and keeps them in the module graph, so everything they import stays reachable. To remove files from the analysis fully, use `ignorePatterns`.

```jsonc
{
  "ignoreFindings": [
    "vitest.config.ts",
    "src/generated/**",
    // a leading ! keeps matching paths reportable
    "!src/generated/keep.ts"
  ]
}
```

Patterns are relative to the project root and use `/` on every platform, including Windows. Matching is case sensitive. `*` and `?` match across `/`, so `src/*` covers the whole `src` subtree. Fallow rejects absolute paths, `..` segments, and a bare `"!"` when it loads the config.

Order does not matter. A negation wins over any positive match, in any position in the array. An array with only negations hides every path except the paths that a negation matches.

Fallow hides findings before it applies rules, severities, and `--fail-on-issues`. A hidden finding therefore cannot fail a run and does not show in any output format.

Some findings belong to several files: circular dependencies, re-export cycles, duplicate exports, prop drilling chains, and unlisted dependencies (which belong to their import sites). Fallow hides such a finding only when every owning file matches.

These findings stay visible even when their path matches:

- Dependency findings that belong to a manifest (unused, dev, optional, type-only, test-only, catalog, override).
- Architecture boundary violations and policy violations.
- Stale suppressions.
- Framework correctness findings, such as client and server directives and route collisions.
- Security candidates.

Human output prints a note on stderr that names patterns that matched no finding, so you can find typos. `--quiet` and the machine formats do not print this note.
</Accordion>

<Accordion title="ignoreDependencies">
Package names that fallow always treats as used and as available.
Fallow does not report listed dependencies as unused or as unlisted.
Use it for packages that the runtime provides, such as `bun:sqlite`, and for other dependencies that are available without a declaration.

```jsonc
{
  "ignoreDependencies": ["autoprefixer", "@types/node", "bun:sqlite"]
}
```
</Accordion>

<Accordion title="ignoreCatalogReferences">
Entries that suppress `unresolved-catalog-reference` findings. This finding is a `catalog:` dependency that points at a catalog that does not declare the package. The findings are in `package.json`, and JSON has no comments. `// fallow-ignore-next-line` cannot work there, so a config entry is the only way to suppress them.

```jsonc
{
  "ignoreCatalogReferences": [
    // Placeholder package; the `upcoming` catalog lands in a later change.
    {
      "package": "future-dep",
      "catalog": "upcoming",
      "consumer": "packages/placeholder/package.json"
    },
    // Staged migration: any catalog, every workspace package.
    { "package": "old-react", "consumer": "packages/**/package.json" }
  ]
}
```

`package` is required. Fallow compares it to the dependency key as an exact, case-sensitive string, so `"@scope/*"` matches nothing. `catalog` and `consumer` are optional. When you leave one out, it matches any value.

Fallow compares `catalog` to the normalized catalog name. `"react": "catalog:"` and `"react": "catalog:default"` are both `default`, and `"catalog:react17"` is `react17`.

`consumer` is a glob for the path of the `package.json` that uses the catalog. The path is relative to the project root and uses `/` on every platform: `package.json` for the root manifest, `packages/app/package.json` for a workspace member. The glob must match the whole path, and `*` and `?` match across `/`.

All fields of one entry must match. Any matching entry in the array suppresses the finding.

Each `unresolved-catalog-reference` finding in `fallow dead-code --format json` output has an `add-to-config` action with `package`, `catalog`, and `consumer` already filled in.

This field changes only `unresolved-catalog-reference`. `unused-catalog-entries` and `empty-catalog-groups` do not change. To turn off the rule for a path, use `overrides` with `"unresolved-catalog-references": "off"`. To turn it off everywhere, set `rules.unresolved-catalog-references` to `"off"`.

`ignoreFindings` does not apply here, because findings that belong to a manifest stay visible when their path matches. A `consumer` value with invalid glob syntax, an absolute path, or a `..` segment makes the config load fail.
</Accordion>

<Accordion title="ignoreDependencyOverrides">
Package-manager override entries that fallow does not report, for example a CVE pin that must stay. The field suppresses `unused-dependency-override` and `misconfigured-dependency-override` for matching entries in these places:

- `overrides` (`pnpm-workspace.yaml`)
- `pnpm.overrides`
- npm `overrides`
- bun `resolutions`

These findings are in manifests, not in source files. `// fallow-ignore-next-line` cannot work there, so a config entry is the only way to suppress them.

```jsonc
{
  "ignoreDependencyOverrides": [
    // overrides: { "lodash": "^4.17.21" } in pnpm-workspace.yaml
    // No source filter, so the entry matches in either file
    { "package": "lodash" },
    // pnpm.overrides: { "@scope/legacy-pkg": "^1.0.0" } in package.json
    { "package": "@scope/legacy-pkg", "source": "package.json" },
    // resolutions: { "**/trim-newlines": "^3.0.1" } in a bun package.json
    { "package": "trim-newlines", "source": "package.json" }
  ]
}
```

Fallow compares `package` to the target package of the override as an exact, case-sensitive string. It is not a glob and not the raw key. Write `react-dom` for `"react>react-dom"` and `@types/react` for `"@types/react@<18"`.

Fallow removes the `**` path segments from bun `resolutions` keys, so `"**/trim-newlines"` matches as `trim-newlines`. Fallow does not remove a `**/` prefix from an `overrides` key. When fallow cannot parse a key, it compares the key as written, so `"react>"` needs `{ "package": "react>" }`.

`source` is the label of the file that declares the override: `"pnpm-workspace.yaml"` or `"package.json"`. It is not a path. Leave it out to match both. Any other value loads without an error and never matches. `pnpm.overrides`, npm `overrides`, and bun `resolutions` all report `"package.json"`, so `source` cannot tell them apart.

Fallow reads the `resolutions` of a bun project only when the root manifest declares no `overrides` key. When `overrides` exists, fallow ignores `resolutions` and never reports them, so an entry for them matches nothing.

Both fields must match. Any matching entry in the array suppresses the finding.

Both findings have an `add-to-config` action in JSON output, with `package` and `source` already filled in. An entry that matches nothing gives no warning. To turn off either finding fully, set `rules.unused-dependency-overrides` or `rules.misconfigured-dependency-overrides` to `"off"`. `ignoreFindings` does not apply here, because findings that belong to a manifest stay visible when their path matches.
</Accordion>

<Accordion title="ignoreUnresolvedImports">
Glob patterns that fallow matches against the import specifier as written, not against a file path. Fallow never reports a matching specifier as `unresolved-import`. Use it for imports that fallow cannot resolve on disk:

- Code that a later build step generates.
- A package with an `exports` map that points at build artifacts that are not in the checkout.
- A bundler alias that fallow does not model.

```jsonc
{
  "ignoreUnresolvedImports": [
    "@example/icons",     // the bare specifier
    "@example/icons/**",  // its subpaths, not the bare name
    "../generated/**"     // parent-relative codegen output
  ]
}
```

Matching is case-sensitive, and a pattern must match the whole specifier. `*` and `?` match across `/`, but a trailing `/**` requires the separator. To match the package and its subpaths, list the bare package name and the subpath pattern. Fallow removes a leading `./` from each pattern and tries each specifier with and without its own `./`. `"./generated/x.js"` and `"generated/x.js"` therefore cover the same imports.

A `..` segment is allowed here, because these patterns match specifiers, not paths. The file-path glob fields do not allow it. There is no negation syntax and no ordering. Fallow suppresses a specifier if any pattern matches. A pattern with invalid glob syntax makes the config load fail, with a message that names the field and the pattern.

The field covers static imports, dynamic imports, and re-export sources, for value imports and type-only imports. Resolution and the module graph do not change, and neither does the dependency usage count. `unlisted-dependency` therefore does not change. For that finding, use `ignoreDependencies`, which matches package names as exact strings.

Each `unresolved-import` finding in JSON output has an `add-to-config` action for this field with the reported specifier. When you move an import here from an inline `// fallow-ignore-next-line unresolved-import` comment, delete the comment. The config check runs first, so fallow then reports the comment as `stale-suppression`.
</Accordion>

<Accordion title="ignoreExports">
Entries that tell fallow to ignore specific exports. Use them for public API packages. Use them also for UI libraries with namespace barrels (shadcn, Radix, bits-ui), where many `components/ui/<name>/index.ts` files export the same short names on purpose.

`ignoreExports` suppresses `unused-export` findings and `duplicate-export` grouping for matching files. Use `exports: ["*"]` to exclude every export from the matched files. Use a list of names to exclude only those names.

```jsonc
{
  "ignoreExports": [
    { "file": "src/index.ts", "exports": ["*"] },
    { "file": "src/utils/*.ts", "exports": ["default"] },
    // shadcn / Radix / bits-ui barrels
    { "file": "src/lib/components/ui/**", "exports": ["*"] }
  ]
}
```

A per-file `overrides.rules.duplicate-exports = "off"` has no effect, because the rule spans multiple files. A duplicate-export finding groups N locations in N files. When fallow detects this override, it prints a warning at load time and points you to `ignoreExports`.
</Accordion>

<Accordion title="ignoreExportsUsedInFile">
Suppress unused-export findings when the file that declares the export also uses it. Fallow still reports exports with no references at all. This is the same as the [`ignoreExportsUsedInFile`](https://knip.dev/reference/configuration#ignoreexportsusedinfile) option of knip.

```jsonc
{
  "ignoreExportsUsedInFile": true
}
```

For knip compatibility, fallow also accepts an object form:

```jsonc
{
  "ignoreExportsUsedInFile": { "type": true, "interface": true }
}
```

Fallow reports type aliases and interfaces under the same `unused-types` issue. `{ "type": true }`, `{ "interface": true }`, and `{ "type": true, "interface": true }` therefore behave the same: fallow suppresses any type export that the same file uses. The two fields exist only for knip-config compatibility.

A reference in the export specifier itself (`export { foo }`, `export { foo as bar }`, `export default foo`) does not count as a same-file use. Fallow still reports such an export when no other file and no other expression in the file references the binding.
</Accordion>

<Accordion title="includeEntryExports">
Report unused exports in entry files (package.json `main` and `exports`, framework pages, and so on). By default, fallow marks these exports as used. This option finds typos in framework-convention exports, such as `meatdata` instead of `metadata`.

```jsonc
{
  "includeEntryExports": true
}
```

The global CLI flag `--include-entry-exports` does the same. When both are set, the CLI flag takes precedence.
</Accordion>

<Accordion title="typeAware">
Use the TypeScript type checker for more exact results. With this option, fallow
gets checker evidence for exact symbol use, class contracts, cross-file private
type leaks, affected tests, and public-signature coupling. The option is off by
default, so the normal analysis stays fast and does not need the TypeScript
companion.

```jsonc
{
  "typeAware": {
    "enabled": true,
    "projects": ["tsconfig.json"],
    "require": "best-effort"
  }
}
```

`projects` is optional and takes tsconfig paths relative to the project root.
With an empty list, fallow discovers the projects automatically. Start with
`best-effort`. It keeps conservative findings when the checker evidence is
partial or not available. Choose `complete` only when an incomplete checker pass
must fail the run.

This option does not replace `tsc` or Oxlint. For installation, performance,
safety, and library-consumer boundaries, see
[Type-aware TypeScript analysis](/analysis/type-aware).
</Accordion>

<Accordion title="security">
Configure the catalogue of `fallow security`. `security.categories` selects the candidate categories that run. `security.requestReceivers` adds the names of your own HTTP request objects to the built-in receiver allowlist (`req`, `request`, `ctx`, `context`, `event`).

`requestReceivers` only adds names. It does not replace the built-in names. Fallow trims the values and matches them case-insensitively for `*.query`, `*.params`, and `*.body` source reads. The field has no effect on `*.searchParams`.

```jsonc
{
  "security": {
    "requestReceivers": ["h", "httpReq"],
    "categories": {
      "include": ["command-injection"],
      "exclude": ["dynamic-regex"]
    }
  }
}
```
</Accordion>

<Accordion title="autoImports">
Resolve framework auto-imports (Nuxt components) as real edges in the module graph. Frameworks such as Nuxt make components available to templates by file name, with no `import` statement: `<Card001 />` resolves to `components/Card001.vue`.

```jsonc
{
  "autoImports": true
}
```

Fallow always creates the edges for these tag references, so `includeEntryExports` counts a default export that a `<Card />` tag uses. The rules below do not change this. A template tag or a composable call marks its file as used, whatever your `nuxt.config` says.

`autoImports: true` also removes the convention entry patterns. A convention file is then no longer an entry point, and fallow reports it as `unused-file` when nothing references it.

Fallow reads two settings from `nuxt.config.ts` or `nuxt.config.js` and handles each one separately:

- `components:` controls the component patterns.
- `imports:` controls the composable, util, `shared/utils`, and `shared/types` patterns.

Fallow removes the patterns of a setting when the config does not have the key, or when the value scans no more than the Nuxt defaults:

- `components: false`, `components: null`, `components: []`, `components: true`, or `components: { dirs: [] }`. `components: true` gives the same directories as a missing key. Other keys next to an empty `dirs` do not change the result.
- `imports: {}`, `imports: { dirs: [] }`, or `imports: { scan: false }` with no `imports.dirs` or an empty array. The first two are the Nuxt defaults: `imports.dirs` starts empty, and Nuxt registers the convention directories itself.

Fallow reads every other shape as a custom layout. That setting keeps its entry patterns:

- `components: {}`, the array form (`components: [{ path: '~/ui' }]`), and an object with no empty `dirs`. A non-empty `dirs`, or only a `prefix` or `pathPrefix`, keeps the patterns. Any other value is also custom.
- `imports: { scan: true }`, a non-empty `imports.dirs`, and `imports: { scan: false }` next to a non-empty `imports.dirs`, which Nuxt scans either way.
- `imports: { autoImport: false }` alone. It turns off the injection, not the scan, and the documented replacement (`import { useThing } from '#imports'`) resolves to no file.
- A config with a top-level `extends`, a spread or a repeated key in either object, or a config object that fallow cannot resolve statically.
- A top-level property that fallow cannot read statically: a spread such as `{ ...base, devtools: {} }`, a computed key such as `['imports']`, an accessor, or a shorthand method. That property can configure either setting, so both settings keep their patterns for that root.

Only a top-level property counts when the config object is readable. A nested key, such as a `routeRules` path that ends in `components` or `imports`, does not keep a fallback on its own.

Two nested locations still count for a setting, because Nuxt reads them the same way as the top level:

- `$production`, `$development`, `$test`, and each `$env.<name>` override, when it carries a nested `components` or `imports` key.
- A `hooks` entry for `components` or `imports`, in the flat form (`'components:dirs': fn`) and in the nested form (`components: { dirs() {} }`), because Nuxt joins nested hook names with `:`.

An override object or a `hooks` object that fallow cannot read statically falls back to a text match for the `components` and `imports` keys, inside that object. An unrelated hook or override does not change the static reading.

For each setting that fallow reads as custom, it adds a `plugin-effect-not-modeled` entry to `workspace_diagnostics[]`, one entry per config file and setting. The entry has `plugin`, `key`, and `reason`, with the config file in `path`. The entry does not make the analysis less complete, and fallow prints no warning for it. For the diagnostic kinds, see [Debugging](/analysis/debugging).

Fallow reads the config of each root separately: the project root and every workspace root, plus each [local layer](/frameworks/built-in#nuxt-local-layers) of that root. The config of the root, and of its local layers, that contains a pattern decides that pattern. One custom `nuxt.config` in a monorepo does not keep the patterns of another app.

Component names follow Nuxt. Nuxt names a component directly under `components/global/` or `components/islands/` after its own directory. `components/global/Foo.vue` is then `<Foo>`, and `components/base/global/Card.vue` stays `<BaseGlobalCard>`. Fallow removes the `.client`, `.server`, `.global`, and `.island` suffixes.

A name that you import or re-export by hand from `#components` or `#imports` marks its convention file as used, like a template tag. A member access on a namespace import, such as `C.Card` on `import * as C from '#components'`, marks `components/Card.vue` as used. A file with `export * from '#components'` or `export * from '#imports'` passes on the names that its importers take from it. When fallow cannot read which names a file takes, for example a spread of the namespace, every name of that module counts as used. A `plugin-effect-not-modeled` diagnostic then names the file, with `key` set to the module. `#layers/<name>/` resolves to a [local layer](/frameworks/built-in#nuxt-local-layers) by its `$meta.name`.

An auto-import name marks as used only the files of the app that renders or calls it, and of the layers that this app extends. In a monorepo, a `<Card />` in one app does not keep the unused `Card.vue` of another app. See [Nuxt auto-import scope](/frameworks/built-in#nuxt-auto-import-scope).

Some component files stay entry points with `autoImports` on, because fallow cannot see how they render:

- `components/global/` files and `*.global.vue` files. A string reference such as `resolveComponent('Name')` can render a global component.
- `components/content/` files of the project and of each local layer, when `@nuxt/content` is in `modules` (as a string or as a `['@nuxt/content', { ... }]` entry), or when a [package layer](/frameworks/built-in#nuxt-local-layers) such as `docus` registers it. Markdown content renders these components, and fallow does not read Markdown.

An OG image template that a `defineOgImage('Name')` or `defineOgImageComponent('Name')` call names with a static string counts as used. See [Nuxt auto-import scope](/frameworks/built-in#nuxt-auto-import-scope).

The default is `false`. Fallow tracks Pinia store auto-imports separately.
</Accordion>

<Accordion title="ignoreDecorators">
Decorator names that do not mean reflective use. By default, fallow skips every class member with a decorator. Fallow checks a member that has only listed decorators like a member with no decorators. A member with any decorator that is not in the list stays skipped, so framework defaults (NestJS, Angular, TypeORM) do not change.

Use this for utility decorators that do not mean runtime reflection. Examples are `@step("label")` from Playwright, internal labeling decorators such as `@measure`, `@log`, and `@retry`, and custom decorators that wrap a method for logging or tracing.

```jsonc
{
  "ignoreDecorators": ["@step"]
}
```

The behavior is conservative. A method with both `@step` and `@Inject` stays skipped, because `@Inject` is not in the list. Fallow applies the standard usage check only to methods where every decorator is in the list.

### Matching

- **Bare entries** (`"step"` or `"decorators"`) match the leftmost segment of the decorator path. One bare `"decorators"` entry covers every `@decorators.*` decorator. Use this when an internal namespace has many utility decorators that are all non-reflective.
- **Dotted entries** (`"decorators.log"`) match the full dotted path exactly. A sibling such as `@decorators.audit` stays skipped, unless you also list `"decorators.audit"` or use the bare `"decorators"` form.
- `"@step"` and `"step"` are the same. Fallow removes a leading `@` before matching.

### Unmatched-entry warning

When an entry matches no decorator in the analyzed codebase, fallow prints one warning at the end of the run. `usedClassMembers` does the same for unmatched patterns. Remove unmatched entries, because they have no effect.

The default is an empty list, which keeps the behavior that skips all decorated members. Existing NestJS, Angular, and TypeORM projects see no change. The first run after you enable this option can report new `unused-class-members` findings on members that fallow skipped before.
</Accordion>

<Accordion title="unusedComponentProps">
Options for the `unused-component-props` rule. Some props stay in the public API but are not used inside the component. To stop fallow from reporting them, set `ignorePattern` to a regex. Fallow skips each prop where the local destructure binding name matches.

This supports the convention that a leading underscore marks an accepted but intentionally unused value. TypeScript `noUnusedParameters` and the `varsIgnorePattern` and `argsIgnorePattern` options of ESLint `@typescript-eslint/no-unused-vars` use the same convention:

```jsonc
{
  "rules": { "unused-component-props": "warn" },
  "unusedComponentProps": {
    "ignorePattern": "^_"
  }
}
```

```svelte
<script lang="ts">
  interface Props { stage: string; variant?: string }
  // `_stage` is exempted by `^_`; `variant` is still reported if unused.
  let { stage: _stage, variant }: Props = $props();
</script>
```

This applies to Vue, Svelte, Astro, React, and Preact props. The default behavior does not change: with no `ignorePattern`, fallow reports every unused prop.

### Matching

- Fallow matches the regex against the **local destructure binding name** (`_stage` in `let { stage: _stage } = $props()`). It does not match the public prop name that the finding reports (`stage`). When a prop has no alias, the local name is the public name.
- Matching is **unanchored** (like `RegExp.test` in ESLint). `_` with no anchor matches any prop that contains an underscore (`on_click`, `aria_label`). To match a leading underscore, use `^_`.
- An invalid regex makes the config load fail with a clear error.

When the pattern skips at least one prop, fallow prints a one-line note with the count. If the note does not show, your pattern matches nothing, which is often a typo.

The Angular rules `unused-component-input` and `unused-component-output` do not change, because their declarations are class fields, not destructured locals.
</Accordion>

<Accordion title="usedClassMembers">
Names of class methods and properties that fallow never reports as unused. The names add to the built-in Angular and React lifecycle allowlist, for methods that third-party libraries call.

Use this when a library calls methods on your class at runtime through an interface or contract. Common examples are ag-Grid (`agInit`, `refresh`), TypeORM migrations (`up`, `down`), and Web Components (`connectedCallback`, `disconnectedCallback`, `attributeChangedCallback`).

Each entry is one of these:

- A plain member name, which applies to all classes.
- A scoped object, which matches only classes with the configured `extends` or `implements` identifier in their heritage clause.

Strings can be exact names or glob patterns:

```jsonc
{
  "usedClassMembers": [
    "agInit",
    { "implements": "ICellRendererAngularComp", "members": ["refresh"] },
    { "extends": "BaseCommand", "members": ["execute"] },
    { "implements": "CanActivate", "members": ["canActivate"] },
    { "extends": "GrammarBaseListener", "members": ["enter*", "exit*"] }
  ]
}
```

A name such as `agInit` is unique enough to suppress for all classes. A common name such as `refresh` or `execute` would hide real findings in unrelated classes, so scope it with `implements` or `extends`. A scoped rule needs at least one of `extends` or `implements`. Fallow rejects an object rule with no heritage field (`{ "members": [...] }`) at load time.

Heritage matching is syntactic. Fallow compares the identifier in the `extends Foo` or `implements IBar` clause of the source to the string in the rule. For a renamed import (`import { IBar as IBaz }`), use the identifier that the class declaration shows.

### Glob patterns

Fallow treats a member string that contains `*` or `?` as a glob pattern. Exact strings keep their meaning.

- `"*"` matches every member of a matching class.
- `"enter*"` matches any member with a name that starts with `enter`.
- `"*Handler"` matches any member with a name that ends with `Handler`.
- `"on*Event"` combines a prefix and a suffix.

Use glob patterns for parser-generator listeners (ANTLR), generated bridges, and abstract framework base classes that call members by a name prefix.

When a glob pattern matches zero members in the codebase, fallow prints a `WARN` at the end of the run, so you can remove the entry. Exact-string entries give no warning, because they are common boilerplate that can match in some configurations and not in others.

The allowlist applies only to class methods and properties. Fallow still checks enum members with the same names.

For an allowlist that applies only when a library is installed, use a plugin file with the `usedClassMembers` field. For the plugin format, see [Custom plugins](/frameworks/custom-plugins).
</Accordion>

<Accordion title="extends">
Inherit from one or more base config files. Use it to share one config across projects, or to keep a base config with per-project overrides.

```jsonc
{
  "extends": ["./configs/base.json", "./configs/strict.json"]
}
```

```toml
extends = ["./configs/base.json", "./configs/strict.toml"]
```

The `extends` field accepts these source types:

| Source | Example | Description |
|:-------|:--------|:------------|
| Relative path | `"./configs/base.json"` | Local file, relative to the config file |
| npm package | `"npm:@my-org/fallow-config"` | Reads the main entry of the package from `node_modules` |
| HTTPS URL | `"https://example.com/fallow-base.json"` | Remote file, fetched over HTTPS |

```jsonc
{
  "extends": [
    "./configs/local-overrides.json",
    "npm:@my-org/fallow-config",
    "https://example.com/shared/fallow-base.json"
  ]
}
```

How `extends` works:

- **Deep merge:** fallow deep-merges object fields (such as `rules`). The child config overrides the base, and the child inherits the fields that it does not set.
- **Array replacement:** array fields (such as `entry` and `ignorePatterns`) replace the base value. Fallow does not concatenate them. If the child sets `entry`, it overrides the base `entry`.
- **Cross-format support:** a JSON config can extend a TOML config, and a TOML config can extend a JSON config.
- **Circular detection:** fallow detects circular extends chains and reports an error.
- **Max depth:** an extends chain can have 10 levels at most, to prevent accidental deep nesting.
- **String shorthand:** you can pass one path as a string instead of an array: `"extends": "./base.json"`.

Fallow resolves paths relative to the config file that contains the `extends` field.

### URL extends

URL sources must use `https://`. Fallow rejects plain HTTP. It fetches the config on every run, with no cache.

- **Timeout:** 5 seconds by default. Change it with `FALLOW_EXTENDS_TIMEOUT_SECS`.
- **Body limit:** 1 MB maximum response size.
- **Chaining:** a config from a URL can extend other URLs or `npm:` packages. It cannot extend relative paths, because there is no file system location to resolve them against.

<Warning>
Fallow fetches URL extends on every run. If the remote server is slow or not available, your analysis fails. For important shared configs, use a versioned URL or an `npm:` package.
</Warning>
</Accordion>

<Accordion title="minimumVersion">
The lowest fallow version that this config needs, as `MAJOR.MINOR.PATCH`. It gives a clear upgrade message instead of an "unknown field" error on older fallow versions.

An unknown config key fails the run with exit 2. This catches mistakes such as `ignorePaths` instead of `ignorePatterns`. It also means that every new config field needs a coordinated upgrade.

When a team commits a field from a newer version, every runner on an older version breaks. The failure comes on the commit that adds the field, not on an upgrade. The error names the field, so the first guess is a typo.

With `minimumVersion`, the older runner shows a clear message instead.

```jsonc
{
  "minimumVersion": "3.21.0",
  "entry": ["src/main.ts"]
}
```

A fallow binary below the minimum version stops before it reports any unknown field:

```
fallow.json requires fallow 3.21.0 or newer, running 3.19.0.
Upgrade fallow, or remove minimumVersion and the fields that need it.
```

How `minimumVersion` works:

- **Inherited through `extends`:** a monorepo base config sets it once, and every config that extends the base inherits the minimum version.
- **Checked before unknown keys:** the version message replaces the misleading field-name error. It does not only come first.
- **No other effect:** at or above the minimum version, an unknown key still fails, because there it is a real typo.
- **Optional:** unset by default. Without it, nothing changes.
- **Validated:** a value that is not `MAJOR.MINOR.PATCH` (for example `v3.21`) is a config error.

<Tip>
Set it in the same change that adds a field from a newer version. Do not set it in advance. A minimum version higher than the config needs blocks runners for no reason.
</Tip>
</Accordion>

</Accordion>

<Accordion title="rulePacks">
Rule packs let you ban specific calls, imports, and effects across your project. A rule pack is a standalone JSON or JSONC file with `banned-call`, `banned-import`, and `banned-effect` rules. Fallow loads packs as data only and never runs project code. Paths are relative to the project root. Fallow reports matches as `policy-violation` findings with the ID `<pack>/<rule-id>`.

```jsonc
{
  "rulePacks": ["./rule-packs/team-policy.jsonc"]
}
```

A pack file declares `version: 1`, a unique `name`, and a non-empty `rules` array. Pack names and rule IDs must use ASCII letters, digits, `.`, `_`, or `-`, so that scoped suppression comments can name them without ambiguity.

- `banned-call` rules match callee paths per segment, through imports. `child_process.*` covers named, namespace, and default imports from `child_process` and `node:child_process`.
- `banned-import` rules match import specifiers as written, per segment. `moment` covers `moment/locale/nl`, never `moment-timezone`.
- Optional `files` and `exclude` globs limit where a rule applies.
- `"ignoreTypeOnly": true` skips type-only imports.
- An optional per-rule `severity` overrides the main `rules."policy-violation"` severity (default `warn`).

To suppress one rule, use `// fallow-ignore-next-line policy-violation:<pack>/<rule-id>` or the file-level form. Bare `policy-violation` still suppresses all rule-pack findings.

For editor autocomplete, run `fallow rule-pack-schema` to print the pack JSON Schema, or point `$schema` at `https://raw.githubusercontent.com/fallow-rs/fallow/main/rule-pack-schema.json`. An invalid or missing pack makes the config load fail with exit code 2. Fallow does not continue with a pack that enforces nothing.

Keep pack files in a committed directory such as `rule-packs/`. `.fallow/` is the gitignored cache directory, so packs there are missing from the checkouts of your teammates.

For details on the issue type, see [Policy violations](/explanations/dead-code#policy-violations).
</Accordion>

<Accordion title="rules">
Severity per issue type: `error` (fails CI with exit code 1), `warn` (reports but exits 0), or `off` (no detection). Each rule has its own default. See [Rules](/configuration/rules#available-rule-names) for the default of each rule.

```jsonc
{
  "rules": {
    "unused-files": "warn",
    "unused-exports": "error",
    "circular-dependency": "off",
    "css-token-drift": "warn",
    "css-duplicate-block": "warn",
    "css-selector-complexity": "warn",
    "css-dead-surface": "warn",
    "css-broken-reference": "warn"
  }
}
```

The `complexity-cyclomatic`, `complexity-cognitive`, and `complexity-crap` rules decide if a complexity finding fails `fallow health` and `fallow audit`. See [Complexity rules](/configuration/rules#complexity-rules).

Styling audit findings use the same severity map. The styling rules are `css-token-drift`, `css-duplicate-block`, `css-selector-complexity`, `css-dead-surface`, and `css-broken-reference`. They default to `warn`, so they show in the output but do not change the verdict, unless you set them to `error` or `off`.

[Rules and severity](/configuration/rules) has the full list of issue types, with the default severities. It includes the pnpm catalog rules such as `unused-catalog-entries` and `empty-catalog-groups`. For per-glob severities, use the `overrides` field.
</Accordion>

<Accordion title="flags">
Customize feature flag detection. Fallow detects the SDKs of LaunchDarkly, Statsig, Unleash, GrowthBook, Split, PostHog, Vercel Flags, ConfigCat, Flagsmith, Optimizely, and Eppo by default. With this field you can:

- Add SDK call patterns.
- Declare environment variable prefixes.
- Enable opt-in heuristic detection.

| Field | Type | Default | Description |
|:------|:-----|:--------|:------------|
| `sdkPatterns` | `SdkPattern[]` | `[]` | Extra SDK call patterns to detect as feature flags, added to the built-ins. Each entry has `function` (function name to match), `nameArg` (zero-based index of the argument with the flag name, default `0`), and `provider` (optional label in the output). |
| `envPrefixes` | `string[]` | `[]` | Environment variable prefixes that mark feature flags, added to the built-ins. Fallow reports only `process.env.*` accesses that match these prefixes. |
| `configObjectHeuristics` | `boolean` | `false` | Enable heuristic detection. Fallow reports property accesses on objects with "feature", "flag", or "toggle" in the name as low-confidence flags. Opt-in, because it gives more false positives. |

```jsonc
{
  "flags": {
    "sdkPatterns": [
      { "function": "useFlag", "nameArg": 0, "provider": "LaunchDarkly" },
      { "function": "client.getFeatureValue", "nameArg": 0 }
    ],
    "envPrefixes": ["FEATURE_", "NEXT_PUBLIC_ENABLE_"],
    "configObjectHeuristics": false
  }
}
```

[`fallow flags`](/cli/flags) is the command that uses this configuration.
</Accordion>

<Accordion title="resolve">
Module resolver configuration. It controls how fallow matches the `exports` and `imports` maps of `package.json`.

| Field | Type | Default | Description |
|:------|:-----|:--------|:------------|
| `conditions` | `string[]` | `[]` | Extra export and import condition names that fallow uses during resolution. They add to the built-in set: `development`, `import`, `require`, `default`, `types`, `node` (plus `react-native` and `browser` when the React Native or Expo plugin is active). Your conditions have a higher priority than the built-in set. |

Use this for community conditions such as `worker`, `edge-light`, and `deno`, or for any custom condition that your bundler uses. The built-in set already has `development`. A package with a `development` branch therefore resolves to source with no config. This is common in monorepos, where `development` points at source and `import` points at compiled output.

```jsonc
{
  "resolve": {
    "conditions": ["worker", "edge-light"]
  }
}
```

With this config, a `package.json` like:

```jsonc
{
  "exports": {
    "./api": {
      "worker": "./src/api.worker.ts",
      "import": "./dist/api.js"
    }
  }
}
```

resolves `./api` to `src/api.worker.ts` instead of `dist/api.js`.

For the full list of established condition names, see the [Node.js community conditions reference](https://nodejs.org/api/packages.html#community-conditions-definitions).
</Accordion>

<Accordion title="codeowners">
Path to a CODEOWNERS file for `--group-by owner`. When unset, fallow looks for `CODEOWNERS`, `.github/CODEOWNERS`, `.gitlab/CODEOWNERS`, and `docs/CODEOWNERS`. Set this field when your file is in a different location.

```jsonc
{
  "codeowners": ".github/CODEOWNERS"
}
```
</Accordion>

<Accordion title="framework">
Inline framework plugin definitions. Define custom entry points, ignored files, or test patterns without a separate plugin file.

```jsonc
{
  "framework": [
    {
      "name": "my-framework",
      "entry": ["src/server.ts"],
      "ignore": ["**/*.internal.ts"]
    }
  ]
}
```
</Accordion>

<Accordion title="plugins">
Paths to external plugin files or directories. Fallow also finds `*.toml`, `*.json`, and `*.jsonc` files in `.fallow/plugins/`, and `fallow-plugin-*.{toml,json,jsonc}` in the project root, automatically.

```jsonc
{
  "plugins": ["./my-plugins/custom.toml", "./plugins/"]
}
```
</Accordion>

<Accordion title="cache">
Settings for the incremental cache. Use `dir` to move the extraction cache. Use `maxSizeMb` to limit its serialized size. Above the limit, fallow removes the least recently used entries when it saves.

```jsonc
{
  "cache": {
    "dir": "/tmp/fallow-cache",
    "maxSizeMb": 64
  }
}
```

The default cache file is `.fallow/cache.bin` under the project root. When `cache.dir` is set, fallow stores the cache file in that directory. When both are set, the env var `FALLOW_CACHE_DIR` overrides `cache.dir`.

The default limit is 256 MB. The limit applies to the serialized extraction cache. When a save goes past 80% of the limit, fallow removes the oldest entries until the cache is at 60%. When both are set, the env var `FALLOW_CACHE_MAX_SIZE` overrides `cache.maxSizeMb`. Both values are in whole megabytes.

Fallow rebuilds the cache automatically when config that affects extraction
changes: the active plugin names and the inline framework definition names.
Fields that affect only detection, such as `entry`, `ignorePatterns`, and
severity overrides, do not invalidate the extraction cache.

`--no-cache` turns off the cache fully. This section then has no effect.
</Accordion>

<Accordion title="regression">
Regression baseline in the config. It stores the issue counts of a known-good state, so CI can fail when the counts go up. `--save-regression-baseline` (with no path argument) writes it, and `--fail-on-regression` reads it.

The count keys use camelCase, for example `totalIssues` and `unusedExports`. Fallow ignores snake_case keys such as `unused_exports` and treats a missing count as `0`.

```jsonc
{
  "regression": {
    "baseline": {
      "totalIssues": 68,
      "unusedFiles": 11,
      "unusedExports": 48,
      "unusedTypes": 5,
      "unusedDependencies": 3,
      "circularDependencies": 1
    }
  }
}
```
</Accordion>

## JSON Schema

Add the `$schema` field to get autocomplete and validation in your editor:

```jsonc
{
  "$schema": "https://raw.githubusercontent.com/fallow-rs/fallow/main/schema.json"
}
```

To generate the schema locally, run:

```bash
fallow config-schema > schema.json
```
