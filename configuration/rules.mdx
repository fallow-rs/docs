The `rules` object of the [config file](/configuration/overview) sets the severity of each issue type. [Findings](/concepts/findings#rules-and-severities) defines rules, severities and gates.

## The `rules` object

Each key is a rule name, and each value is a severity:

| Severity | Effect |
|:--|:--|
| `error` | Fallow reports the finding, and the run exits with code 1. |
| `warn` | Fallow reports the finding, and the run exits with code 0. |
| `off` | Fallow does not look for the issue type. |

```jsonc
// .fallowrc.json
{
  "rules": {
    "unused-files": "error",
    "unused-exports": "warn",
    "unused-types": "off",
    "private-type-leaks": "warn"
  }
}
```

```toml
# fallow.toml
[rules]
unused-files = "error"
unused-exports = "warn"
unused-types = "off"
private-type-leaks = "warn"
```

A rule that you do not set keeps its default. An unknown rule name gives a warning on stderr, and fallow ignores the entry.

## Rule names {#available-rule-names}

The rule name is the plural form of the issue type in most cases, for example `unused-exports` for the issue type `unused-export`. Most rules also accept the other form as an alias, for example `circular-dependency` for `circular-dependencies`. The page of each issue type gives its key in the row "Config key in `rules`". [Issue types](/reference/issue-types) lists each issue type with its default severity. The [`rules` reference](/reference/config-rules#rules) lists each key.

## Defaults

Most issue types default to `error`. These groups have another default:

- `off`: the checks that you turn on yourself. Examples are `private-type-leaks`, `deprecated-exports-in-use`, `unused-protected-class-members`, `absent-component-props`, `constant-parameters`, `prop-drilling`, `thin-wrapper`, `duplicate-prop-shape`, `coverage-gaps`, `feature-flags`, `require-suppression-reason`, `security-sink`, `security-client-server-leak`, `diverged-clone-sibling` and `added-dependency`.
- `warn`: these groups of rules.
  - `unused-dev-dependencies`, `unused-optional-dependencies`, `type-only-dependencies`, `test-only-dependencies` and `dev-dependencies-in-production`.
  - The framework component rules, for example `unused-component-props`, and the Effect rules.
  - The client and server directive rules, and the styling rules (`css-*`).
  - `unused-catalog-entries`, `empty-catalog-groups` and `unused-dependency-overrides`.
  - The change checks of `fallow audit` that are not `off`: `weakened-tests`, `added-suppression`, `test-only-branch` and `introduced-clone-group`.
  - `unlisted-binaries`, `unused-namespace-members`, `duplicate-export-aliases`, `re-export-cycle`, `package-cycle`, `stale-suppressions` and `policy-violation`.

To see the severity of each rule for your project, run `fallow config`. The `rules` object of its output holds the result after `extends` and the defaults.

## Overrides {#overrides}

`overrides` sets other severities for the files that its globs match. The globs follow the [glob rules](/configuration/overview#path-globs).

```jsonc
// .fallowrc.json
{
  "rules": { "unused-exports": "error" },
  "overrides": [
    {
      "files": ["**/*.test.ts", "src/generated/**"],
      "rules": { "unused-exports": "off" }
    },
    {
      "files": ["src/legacy/**"],
      "rules": { "complexity-cyclomatic": "warn" }
    }
  ]
}
```

- Fallow applies the entries in list order. When two entries match a file and set the same rule, the later entry wins.
- An override cannot start a check that the top-level `rules` turns off. Set the rule on at the top level, then set it to `off` for the other files.
- These rules read only the top-level severity: `unused-dependencies`, `unused-dev-dependencies`, `unused-optional-dependencies`, `unlisted-dependencies`, `unlisted-binaries`, `type-only-dependencies`, `test-only-dependencies`, `dev-dependencies-in-production`, `duplicate-exports`, `re-export-cycle` and `unused-catalog-entries`.

Fallow reports an override entry that has no effect as an [override rule with no effect](/configuration/overview#override-rules-with-no-effect). The [`overrides` reference](/reference/config-rules#overrides) has the details.

## Production mode

[Production mode](/concepts/production-mode) changes some dependency rules:

- `unused-dev-dependencies` and `unused-optional-dependencies` are `off`.
- Fallow reports `type-only-dependencies` only in production mode.
- Fallow reports `test-only-dependencies` only outside production mode.

## Complexity rules {#complexity-rules}

The health limits, for example `health.maxCyclomatic`, decide if a function has a complexity finding. The rules `complexity-cyclomatic`, `complexity-cognitive`, `complexity-crap` and `complexity-file-lines` decide if that finding fails the run.

- A rule at `warn` keeps the finding in the report. `fallow health` then exits with code 0, and the verdict of `fallow audit` is `warn`.
- A rule at `off` removes the finding from the report.
- A function above more than one limit takes the most severe rule of those limits.
- In JSON output, `effective_severity` holds the rule severity. `severity` holds the band: `moderate`, `high` or `critical`.

After you set a complexity rule to `off`, save the health baseline again. Its entries for the removed findings no longer match.

## Change the result for one run

The config file stays the same for these options:

- `--fail-on-issues` makes a `warn` finding fail the run too. `--ci` includes it. `fallow audit` ignores it and keeps its own verdict.
- An issue type filter, such as `--unused-deps`, does not turn on a rule that is `off`. Fallow then adds a [requested rule that is off](/configuration/overview#requested-rules-that-are-off) warning.
- When the config sets their rule to `off`, these filters of `fallow dead-code` turn it on at `warn`: `--private-type-leaks`, `--deprecated-exports-in-use`, `--unused-protected-class-members`, `--absent-component-props` and `--constant-parameters`.

[Exit codes](/reference/exit-codes) lists each code.

## Levels in CI formats {#levels-in-ci-formats}

The CI formats take the level of a finding from its rule severity, also from an `overrides` entry. A complexity finding takes its level from its `complexity-*` rule, not from its band.

| Rule severity | `github-annotations` | SARIF | CodeClimate |
|:--|:--|:--|:--|
| `error` | `::error` | `error` | `major` |
| `warn` | `::warning` | `warning` | `minor` |
