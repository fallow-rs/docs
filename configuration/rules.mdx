Rules let you decide which findings fail CI. You set a severity per issue type, so you can adopt fallow one issue type at a time.

<Tip>
Start with all rules as `warn`. Promote one type at a time to `error` when you have fixed its findings.
</Tip>

## Severity levels

| Level | Behavior |
|:------|:---------|
| `error` | Report and fail CI (non-zero exit code) |
| `warn` | Report but exit 0 |
| `off` | Do not detect or report |

When you do not configure a rule, most issue types default to `error`. These are the exceptions:

- Default `off`: `private-type-leaks`, `coverage-gaps`, `prop-drilling`, `thin-wrapper`, `duplicate-prop-shape`, and `require-suppression-reason`.
- Default `warn`: `stale-suppressions` and `policy-violation`.

```jsonc .fallowrc.json

    "unused-files": "error",
    "unused-exports": "warn",
    "unused-types": "off",
    "private-type-leaks": "off",
    "unused-dependencies": "error",
    "unused-dev-dependencies": "warn",
    "unused-optional-dependencies": "warn",
    "unused-enum-members": "warn",
    "unused-class-members": "off",
```

## Available rule names

| Rule | Description |
|:-----|:------------|
| `unused-files` | Files not reachable from any entry point |
| `unused-exports` | Exported symbols never imported |
| `unused-types` | Type aliases and interfaces never referenced |
| `private-type-leaks` | Opt-in API hygiene check. Finds exported signatures that reference a private type from the same file (default `off`) |
| `unused-dependencies` | Packages in `dependencies` never used |
| `unused-dev-dependencies` | Packages in `devDependencies` never used |
| `unused-optional-dependencies` | Packages in `optionalDependencies` never used |
| `unused-enum-members` | Enum values never referenced |
| `unused-class-members` | Class members never referenced |
| `unused-store-members` | Pinia store members (state, getters, actions) that no code accesses. Runs only when `pinia` or `@pinia/nuxt` is a dependency (default `warn`) |
| `unused-catalog-entries` | Entries in the `catalog:` or `catalogs:` maps of `pnpm-workspace.yaml` that no workspace package references with the `catalog:` protocol (default `warn`) |
| `empty-catalog-groups` | Named `catalogs.<name>:` groups in `pnpm-workspace.yaml` that contain no package entries (default `warn`; top-level `catalog:` placeholders are ignored) |
| `unresolved-catalog-references` | `package.json` references to `catalog:` or `catalog:<name>` where the catalog does not declare the package. `pnpm install` would fail (default `error`) |
| `unused-dependency-overrides` | Entries in `pnpm-workspace.yaml#overrides` or `package.json#pnpm.overrides` for a package that no workspace package declares and that is not in `pnpm-lock.yaml` (default `warn`). Without a lockfile, fallow checks the manifests only and sets the `hint` field on these less certain findings |
| `misconfigured-dependency-overrides` | `pnpm.overrides` entries with a key that fallow cannot parse or with no value. `pnpm install` would fail (default `error`) |
| `unresolved-imports` | Imports that fallow cannot resolve |
| `unlisted-dependencies` | Imported packages not in `package.json` |
| `duplicate-exports` | Same symbol exported from multiple files |
| `circular-dependencies` | Modules that import each other, directly or transitively |
| `re-export-cycle` | Barrel files that re-export from each other in a loop (`kind: "multi-node"`), or one barrel that re-exports from itself (`kind: "self-loop"`). A re-export cycle does nothing and is almost always a bug. `circular-dependencies` covers runtime import loops instead. Default `warn`. The cycle spans multiple files, so a per-file `overrides.rules.re-export-cycle` has no effect. Use the project-wide `rules` block, or `// fallow-ignore-file re-export-cycle` on any file in the cycle. Fallow also accepts the aliases `re-export-cycles`, `reexport-cycle`, and `reexport-cycles`. |
| `boundary-violation` | Imports that cross user-defined architecture zone boundaries |
| `policy-violation` | Calls, imports, or catalogue-derived effects that a rule pack bans (the `rulePacks` config key). Default `warn`, so a new pack does not fail CI on its first run. A per-rule `severity` in the pack overrides this value for each finding, and the exit code uses that per-finding severity. `off` turns off all rule-pack checks. |
| `type-only-dependencies` | Production dependencies that are only imported with `import type` |
| `test-only-dependencies` | Production dependencies that only test files import |
| `dev-dependencies-in-production` | Packages in `devDependencies` that production code imports at runtime. Move them to `dependencies` (default `warn`) |
| `coverage-gaps` | Runtime files and exports that no test reaches through the import graph (default `off`) |
| `stale-suppressions` | `fallow-ignore` comments or `@expected-unused` JSDoc tags that no longer match any issue (default `warn`) |
| `require-suppression-reason` | Opt-in suppression hygiene check. When you enable it, every `fallow-ignore-*` comment and `@expected-unused` tag must end with `-- <reason>`. Fallow reports a suppression without a reason as `missing-suppression-reason` (default `off`) |

<Note>
  `circular-dependencies` and `circular-dependency` are the same rule. You can use either form in `rules`, `overrides[].rules`, and inline directives.
</Note>

<Accordion title="Incremental adoption strategy">
In an existing codebase, adopt fallow in steps:

1. **Start permissive.** Set all rules to `warn` so you see issues without blocking CI.
2. **Fix high-confidence rules first.** Promote `unresolved-imports` and `unlisted-dependencies` to `error`. These rules almost never give false positives.
3. **Fix unused files.** Promote `unused-files` to `error`. You can safely remove unreachable files.
4. **Fix unused exports.** This is usually the largest category. Promote `unused-exports` to `error` when the count is manageable.
5. **Enable the remaining rules.** Promote `unused-types`, `unused-enum-members`, and `unused-class-members` as you clean up each category. Enable `private-type-leaks` only for packages where the public API or the declaration files matter.

Use [baselines](/analysis/dead-code#baseline-comparison) to enforce rules on new code without failing CI on existing issues.
</Accordion>

<Info>
To treat all warnings as errors for one run, pass `--fail-on-issues`. The config file stays the same. Use it for pre-merge gates on critical branches.
</Info>

```bash
fallow dead-code --fail-on-issues
```

## Exit codes

| Code | Meaning |
|:-----|:--------|
| `0` | No error-severity issues |
| `1` | Error-severity issues found |
| `2` | Fatal error (invalid config, parse failure) |
