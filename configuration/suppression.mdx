Inline suppression removes one finding from the report and keeps the rule on for the rest of the codebase. Use it for a false positive or an intentional exception. You add a comment or a JSDoc tag next to the code.

<Tip>
For broad patterns, use config-level rules. Keep inline suppression for single exceptions. For library exports that other projects use, add [JSDoc visibility tags](#jsdoc-visibility-tags) (`@public`, `@internal`, `@beta`, `@alpha`) instead of suppression comments.
</Tip>

## JSDoc visibility tags

Fallow never reports an export with a JSDoc visibility tag as unused. It recognizes `@public`, `@internal`, `@beta`, and `@alpha`. Use these tags for library APIs that external projects use, and for exports that you keep for a specific audience. These exports have no references in your repo, but they are part of your public API.

```ts
/** @public */
export function createClient() {
  // Not imported anywhere in this repo, but consumed by users of the library
}

/**
 * Configuration options for the client.
 * @public
 */
export interface ClientOptions {
  baseUrl: string;
  timeout?: number;
}

/** @internal */
export function resetState() {
  // Used by sibling packages in the monorepo, not public API
}

/** @beta */
export function experimentalFeature() {
  // Available to early adopters, not yet stable
}

/** @alpha */
export function unstableApi() {
  // Early-stage API, subject to breaking changes
}

/** @api public */
export type UserId = string; // TSDoc @api convention also supported
```

The tags work with all export types: named, default, classes, interfaces, enums, type aliases, and multi-specifier exports (`export { foo, bar }`).

On a decorated class, put the JSDoc block before the first decorator, as TypeScript does. The block then applies to the export. This is also true for `@deprecated`.

```ts
/** @public */
@Component({ selector: "app-card" })
export class CardComponent {}
```

A JSDoc block between a decorator and `export` does not apply to the export. A block before an earlier, unrelated statement does not apply either.

<Note>
Fallow recognizes only `/** */` JSDoc block comments. Line comments (`// @public`) and regular block comments (`/* @public */`) have no effect.
</Note>

## `@expected-unused` JSDoc tag

To mark an export as intentionally unused, add `/** @expected-unused */`. Fallow checks this tag for staleness, which it does not do for visibility tags (`@public`, `@internal`). If another module imports the export later, fallow reports the tag as a stale suppression.

```ts
/** @expected-unused */
export const deprecatedHelper = () => {
  // Intentionally kept but not used anywhere
};
```

Use `@expected-unused` when you want to:

- Suppress an unused export finding.
- Get a finding when the export is used again (through the `stale-suppressions` rule).

The `stale-suppressions` rule (default: `warn`) sets the severity of stale `@expected-unused` tags. For details, see [dead code explained](/explanations/dead-code#stale-suppressions).

## Comment syntax

```ts
// Suppress all issues on the next line
// fallow-ignore-next-line
export const keepThis = 1;

// Suppress a specific issue type
// fallow-ignore-next-line unused-export
export const keepThisToo = 2;

// Suppress all issues in the entire file
// fallow-ignore-file

// Suppress a specific issue type file-wide
// fallow-ignore-file unused-export
```

### Suppressing complexity findings

To remove one function from the complexity report of `fallow health`, suppress `complexity` on it. The comment suppresses the cyclomatic and the cognitive metric together.

```ts
// fallow-ignore-next-line complexity
function* parseCsv(text) {
  // intentionally complex parser, not worth refactoring
  // ...
}

function processRow(row) {
  // this function is NOT suppressed, still appears in health output
  // ...
}
```

A file-level suppression removes all functions in the file from the complexity findings. File health scores do not change:

```ts
// fallow-ignore-file complexity
```

## Reference

| Comment | Scope |
|:--------|:------|
| `// fallow-ignore-next-line` | All issues on the next line |
| `// fallow-ignore-next-line <type>` | One issue type on the next line |
| `// fallow-ignore-next-line <type>, <type>` | Multiple issue types on the next line (separated by commas or spaces) |
| `// fallow-ignore-file` | All issues in the file |
| `// fallow-ignore-file <type>` | One issue type in the file |

### Multi-kind markers and typos

A marker can list more than one token. A token may not match a known issue kind, for example because of a typo or because a newer fallow release renamed the kind. The recognized tokens then still apply, and fallow reports each unknown token as a `stale-suppression` finding.

When a known kind is within edit distance 2, the finding includes a "Did you mean ...?" hint. An upgrade across a rename therefore never breaks the whole marker without a message.

```ts
// Recognized + unknown on the same marker:
// fallow-ignore-next-line unused-export, complexity-typo
export const foo = 1;
// `unused-export` still suppresses `foo`; `complexity-typo` surfaces as a stale
// suppression so you can fix the typo or drop the unknown token.
```

In JSON output, the additive `origin.kind_known` field on `stale_suppressions[].origin` tells an unknown-kind token apart from a known token that is stale. The field is present and `false` only for an unknown kind. It is absent when fallow recognizes the kind.

## Documenting suppressions with a reason

A reason tells the next reader why a suppression exists. Add `-- <reason>` at the end of any suppression comment or `@expected-unused` tag:

```ts
// fallow-ignore-next-line unused-export -- public compatibility export
export const legacyHelper = () => {};

// fallow-ignore-file -- generated route map

/** @expected-unused -- kept for the v3 migration */
export const oldApi = () => {};
```

By default, the reason is optional. Fallow records it in the suppression hygiene output. To require a reason on every suppression, enable the opt-in `require-suppression-reason` rule (default `off`):

```jsonc .fallowrc.json
{ "rules": { "require-suppression-reason": "warn" } }
```

With the rule at `warn` (or `error` to fail CI), fallow reports each `fallow-ignore-*` comment or `@expected-unused` tag without a `-- <reason>` as a `missing-suppression-reason` finding. You can then find the suppressions that have no reason and add one. For the rule reference, see [Rules & Severity](/configuration/rules#available-rule-names).

## When to use suppression

For broad patterns, use the config ([rules](/configuration/rules), [ignoreExports](/configuration/overview#ignoreexports)). Use inline suppression for:

- Individual false positives
- Temporary suppression during migration

<Warning>
Do not suppress an issue that repeats across the codebase. If a pattern affects many files, configure it at the project level.
</Warning>

## Config-level vs inline suppression

<CodeGroup>
```ts Bad: many inline suppressions
// src/components/Button.tsx
// fallow-ignore-next-line unused-export
export const Button = () => { /* ... */ };

// src/components/Input.tsx
// fallow-ignore-next-line unused-export
export const Input = () => { /* ... */ };

// src/components/Modal.tsx
// fallow-ignore-next-line unused-export
export const Modal = () => { /* ... */ };

// Repeated across dozens of component files...
```

```jsonc Good: config-level ignoreExports
// .fallowrc.json
{
  "ignoreExports": [
    {
      "file": "src/components/**/*.tsx",
      "exports": ["*"]
    }
  ]
}
```
</CodeGroup>
