The demo project reports `formatPercent` in `src/lib/format.ts` as an unused export, and you keep it for a report page that you add next month. A `warn` [rule](/configuration/rules) would also soften `cancelOrder` and each new unused export. A suppression hides one [finding](/concepts/findings) and keeps the rule on for the rest of the code. [Suppress findings](/guides/suppress) shows the steps and helps you choose a form.

## Comment forms

A comment in the source file is the most direct form, because it sits next to the code that it explains.

| Comment | Hides |
|:--|:--|
| `// fallow-ignore-next-line` | Each finding on the next line. |
| `// fallow-ignore-next-line <token>` | The findings of one issue type on the next line. |
| `// fallow-ignore-next-line <token>, <token>` | The findings of each listed issue type on the next line. |
| `// fallow-ignore-file` | Each finding in the file. |
| `// fallow-ignore-file <token>` | The findings of one issue type in the file. |
| `// fallow-ignore-start code-duplication` and `// fallow-ignore-end code-duplication` | The clones in the range. See [Ranges](#suppressing-one-clone-with-a-range). |

```ts
// src/lib/format.ts
// fallow-ignore-next-line unused-export -- kept for the report page
export const formatPercent = (ratio: number): string => `${Math.round(ratio * 100)}%`;
```

The comment hides the finding on the next line and nothing else. The re-export of the same name in the [barrel file](/concepts/entry-points) `src/lib/index.ts` is a second finding, so `fallow dead-code --unused-exports` still reports it:

```text
● Unused exports (2)
  src/lib/index.ts
    :1 formatPercent (re-export)
  src/services/orders.ts
    :18 cancelOrder
  Exported symbols with no known consumers
  https://fallow.tools/docs/explanations/dead-code/#unused-exports

✗ 2 exports (0.04s)
  2 issues · 1 suppressed
```

- Separate two or more tokens with commas or spaces.
- Fallow reads the markers in `//`, `/* */`, `/** */` and `<!-- -->` comments.
- Text after ` -- ` is the reason. See [Reasons](#documenting-suppressions-with-a-reason).

## Tokens

The word after the marker decides which findings the comment hides. A token is the id of an issue type, for example `unused-export`. The page of each issue type gives its comment in the row "Suppression comment". [Issue types](/reference/issue-types) lists them all.

Some tokens are different from the issue type id, or work only in one form:

| Token | Note |
|:--|:--|
| `complexity` | `// fallow-ignore-next-line complexity` above a function hides each complexity finding of the function: cyclomatic, cognitive and CRAP. `// fallow-ignore-file complexity` at the top of the file hides the complexity findings of each function in the file and the file length finding. No other token hides a complexity finding: `crap` and `cognitive` are not tokens. |
| `coverage-gaps` | File level only. |
| `boundary-violation` | Hides each boundary finding: import direction, zone coverage and forbidden calls. |
| `policy-violation:<pack>/<rule-id>` | Hides one rule of a rule pack. `policy-violation` alone hides each rule. |
| `unused-file`, `duplicate-export`, `duplicate-export-alias`, `re-export-cycle`, `route-collision`, `dynamic-segment-name-conflict`, `security-client-server-leak` | File level only. For `re-export-cycle`, put the comment in one file of the cycle. |
| `unused-catalog-entry` | A YAML comment, `# fallow-ignore-next-line unused-catalog-entry`, on the line above the entry in `pnpm-workspace.yaml`. |

A comment in a source file cannot hide a finding that belongs to `package.json`, for example an unused dependency. Use the [config keys](#config-keys) for these findings.

## Unknown tokens and stale suppressions {#stale-suppressions}

A suppression stays in the code after the reason for it is gone, and a typo in a token hides nothing. A suppression that hides no finding is a **stale suppression**. The `stale-suppressions` rule reports it, at `warn` by default. A token that is not an issue type is also stale, and the other tokens of the same comment still apply. Here the demo comment has the typo `unused-exprt`:

```text
● Stale suppressions (1)
  src/lib/format.ts:3:0 // fallow-ignore-next-line unused-exprt -- kept for the report page ('unused-exprt' is not a recognized fallow issue kind. Did you mean 'unused-export'? Other tokens on this line still apply.)
```

In JSON output, `origin.kind_known` is `false` on such an entry. [`fallow suppressions`](/cli/suppressions) lists each suppression of the project.

## Ranges {#suppressing-one-clone-with-a-range}

Duplication needs another form, because a clone covers many lines. A `fallow-ignore-next-line code-duplication` comment hides each clone that touches the next line, also a clone of the code above. A range hides only the clones inside it:

```ts
// src/i18n/fields.ts
// fallow-ignore-start code-duplication -- one field block per locale
export const en = { title: "", body: "", footer: "" };
export const nl = { title: "", body: "", footer: "" };
// fallow-ignore-end code-duplication
```

- A clone that is fully inside the range is not reported.
- A clone that reaches into the range stops at the border. When the part outside is below `minTokens` or `minLines`, fallow does not report it.
- Ranges take only the `code-duplication` token, on both markers. Put the reason on the start marker.
- Put each marker on its own line. A marker after code on the same line, or in a string, has no effect.
- A range changes the [handle](/analysis/duplication) of each clone group that it cuts. Save the duplication [baseline](/concepts/changed-code#baselines) again after you add a range.

`fallow dupes` and `fallow audit` report a marker with a problem in the `range_marker_problems` array:

| `problem` | Cause |
|:--|:--|
| `unclosed_start` | A start marker has no end marker after it. |
| `unmatched_end` | An end marker has no open start marker before it. |
| `nested_start` | A start marker is inside an open range. The outer range applies. |
| `missing_kind` | The marker has no token. |
| `unsupported_kind` | The marker names a token other than `code-duplication`. |
| `not_own_line` | The marker shares its line with code. |

## Reasons {#documenting-suppressions-with-a-reason}

A suppression without a reason forces the next reader to guess why the code stays. Add ` -- <reason>` at the end of a comment or an `@expected-unused` tag. A reason is optional. To require one, turn on the `require-suppression-reason` rule:

```jsonc
// .fallowrc.json
{ "rules": { "require-suppression-reason": "warn" } }
```

Fallow then reports each suppression without a reason as [`missing-suppression-reason`](/rules/missing-suppression-reason). In JSON output, the entry is in `stale_suppressions` with `missing_reason: true`.

## JSDoc tags {#jsdoc-visibility-tags}

A library exports names that only code outside the project uses, and a comment above each export repeats the same fact many times. A JSDoc tag on an export tells fallow how to treat the export when no code uses it:

| Tag | Effect |
|:--|:--|
| `@public`, `@api public` | Fallow does not report the export. Use it for an API that code outside the project uses. |
| `@internal`, `@beta`, `@alpha` | Fallow does not report the export. Use it for an API with a limited audience. |
| `@expected-unused` | Fallow does not report the export. When code uses the export again, the tag is a stale suppression. |

```ts
// src/client.ts
/** @public */
export function createClient() {}

/** @expected-unused -- kept for the next major version */
export const legacyClient = () => {};
```

- Fallow reads only `/** */` blocks. `// @public` and `/* @public */` have no effect.
- A tag works on each export form, and on a re-export such as `export { a } from "./a"`. `export * from "./a"` takes no tag.
- On a decorated class, put the block before the first decorator.

## Config keys {#config-keys}

A comment or a tag works for one place in the code. For a package in `package.json`, or for many files at once, use a config key. The table lists each need with the smallest form that covers it:

| Need | Use |
|:--|:--|
| One finding in code that you keep | A `fallow-ignore-next-line` comment |
| All findings of one issue type in one file | A `fallow-ignore-file <token>` comment |
| An export that code outside the project uses | `@public`, or [`ignoreExports`](/reference/config-dead-code#ignoreexports) for many files |
| An unused export that you keep on purpose | `@expected-unused` |
| A package in `package.json` | [`ignoreDependencies`](/reference/config-dead-code#ignoredependencies) |
| A `catalog:` reference or a package manager override | [`ignoreCatalogReferences`](/reference/config-dead-code#ignorecatalogreferences), [`ignoreDependencyOverrides`](/reference/config-dead-code#ignoredependencyoverrides) |
| All dead code findings in some files, with the files still analyzed | [`ignoreFindings`](/reference/config-dead-code#ignorefindings) |
| Files that fallow must not read | [`ignorePatterns`](/reference/config-files#ignorepatterns) |
| An issue type in some directories | [`overrides`](/configuration/rules#overrides) |

### One reason in many files {#config-level-vs-inline-suppression}

When many comments give the same reason, the reason is a fact about the project. Put it in the config file once. Do not do this:

```ts
// src/components/Button.tsx
// fallow-ignore-next-line unused-export
export const Button = () => { /* ... */ };

// src/components/Input.tsx
// fallow-ignore-next-line unused-export
export const Input = () => { /* ... */ };
```

Write one config entry, and remove the comments:

```jsonc
// .fallowrc.json
{
  "ignoreExports": [
    { "file": "src/components/**/*.tsx", "exports": ["*"] }
  ]
}
```
