`fallow dead-code` reports the files, exports, dependencies and members that no [entry point](/concepts/entry-points) reaches.

For the concepts and the workflow, read [Dead code](/analysis/dead-code).

## Synopsis

{/* generated:start cli-synopsis dead-code */}

```bash
fallow dead-code [OPTIONS] [PATH]
```

{/* generated:end */}

`fallow check` is a hidden alias of `fallow dead-code`.

- A filter option such as `--unused-exports` reports only its [issue type](/reference/issue-types). You can give more than one filter. When a filter asks for a rule that the config sets to `off`, fallow does not run that check. It prints a note on stderr, and the JSON output gets a `requested-rule-off` entry in `workspace_diagnostics`.
- Without a filter option, `fallow dead-code` also reports the findings of [`fallow architecture`](/cli/architecture): cycles, boundary violations and policy violations.
- `--file` leaves out the findings that belong to no file, for example an unused dependency. It prints a warning for a path that does not exist.
- `--symbol-impact` needs `--type-aware`. Without it, fallow prints `Error: --symbol-impact requires --type-aware`.

- The first line counts the entry points by source.
- Each section is one issue type. It lists the findings, then a description, a link, and the commands that fix or suppress a finding.
- The last line counts the findings of each issue type, and gives the run time.

With `--format json`, the output has these top-level fields:

| Field | Content |
|:--|:--|
| `kind` | `"dead-code"`. A `--group-by` run gives `"dead-code-grouped"`. |
| `schema_version`, `version`, `elapsed_ms` | The version of this output format, the fallow version and the run time. |
| `total_issues` | The number of findings in all arrays. |
| `summary` | The number of findings for each issue type. Each key is always present. |
| `entry_points` | The number of entry points, in total and for each source. |
| `unused_files`, `unused_exports`, and the other issue arrays | One array for each issue type. An opt-in issue type has its array only when its rule is on. |
| `cascade_hidden` | The number of unused exports, types and members in unused files that the report hides. Absent when it is 0. `--show-cascade` reports them. |
| `baseline`, `baseline_staleness` | The entries of the loaded baseline, how many matched, and how many are stale. Present only with `--baseline`. |
| `regression` | The result of `--fail-on-regression`. |
| `finding_id_query` | The answer to `--finding-id`. See [Finding ids](#finding-id). |
| `gate_outcomes` | One entry for each gate of the run, with `status` and `enforced`. Always present. |
| `request_outcomes` | The result of each scope request. See [Request outcomes](/cli/global-flags#request-outcomes). |
| `workspace_diagnostics` | Problems with the project setup, for example a config pattern that matches nothing. |
| `next_steps` | Commands to run next. |
| `baseline_deltas` | The change of each count against the loaded baseline. Present only in a baseline run. |
| `package_baselines` | The Git ref that each workspace package used as its base. Absent when no package base applies. |
| `shared_state` | The shared-state inventory of [`fallow architecture`](/cli/architecture#shared-state-inventory). It does not count in `total_issues` or in a gate. Optional. |
| `_meta` | Metadata of the run, for example `telemetry.analysis_run_id`. |

Each finding has `path`, a position (`line`, `col`), a `finding_id`, an `effective_severity` (`error` or `warn`) and an `actions` array. The [JSON output reference](/reference/json-output) has each field.

### Actions {#fix-suggestions-in-json-output}

Each action in the `actions` array of a finding has these fields:

| Field | Content |
|:--|:--|
| `type` | The action, for example `remove-export`, `delete-file`, `remove-dependency`, `suppress-line`, `suppress-file` or `add-to-config`. |
| `auto_fixable` | `true` when `fallow fix` applies the action. Fallow sets it for each finding, so one `type` can be `true` on one finding and `false` on another. |
| `description` | What the action does. |
| `comment` | The suppression comment to add. Optional. |
| `note` | More context, when `fallow fix` cannot apply the action. Optional. |
| `config_key`, `value`, `value_schema` | The config key to change, the value to write, and the URL of the JSON Schema of the value. Optional. |
| `scope` | `"per-location"` on a suppress action that applies to one location of a finding. Optional. |

### Finding ids {#finding-id}

Each finding has a `finding_id` of the form `dc1:<rule>:<16 hex digits>`, for example `dc1:unused-export:b650995c7b5b87c1`. Fallow computes it from the rule, the root-relative path and the name. A line change, a new format or a new order of declarations keeps the id. A new file name or a new symbol name gives a new id. When two findings have the same subject, the second id gets the suffix `~1`.

### Finding id query {#finding-id-query}

`--finding-id` reports only the findings with the ids that you give. The JSON output then has a `finding_id_query` object:

| Field | Content |
|:--|:--|
| `requested` | The requested ids, in the order of the arguments. |
| `found` | The requested ids that the report holds. |
| `missing` | The requested ids that the report does not hold. |
| `filtered` | The requested ids that a filter of this run removed. These findings still exist. |
| `conclusive` | `true` when no option of the run can hide a finding that still exists. |
| `inconclusive_reasons` | The reasons when `conclusive` is `false`. An open set of names. |
| `analysis_fingerprint` | A hash (`af1:<16 hex digits>`) of the inputs other than the source code: the fallow version, the config, the plugins, and the manifest and `tsconfig` files. |

A missing id means that the finding is gone only when `conclusive` is `true` and the `analysis_fingerprint` is the same as in your earlier run. A scope option, a filter option, production mode, `--baseline` or a rule at `off` makes the answer inconclusive. A malformed id exits with code 2.

### Trace output {#search-visibility-in-traces}

`--trace FILE:EXPORT` shows why an export is used or unused. In the JSON output, each entry of `direct_references` has these fields:

| Field | Content |
|:--|:--|
| `from_file`, `kind`, `line` | The consumer, the kind of import, and the 1-based line of the import. |
| `search_visibility` | `found`: a whole-word text search for the export name finds the consumer. `renamed`: the consumer has the name, but uses the export under another name. `missed`: the consumer does not have the name. |
| `reason` | Why a search does not find the use: `import-alias`, `default-import`, `re-export-alias`, `namespace-use`, `dynamic-import` or `pass-through`. |
| `search_as` | The name to search for in this consumer. Absent when no single name finds the use. |

The trace object also has `is_used`, `reason`, `re_export_chains` (each barrel file that exports the name again) and `plugin_credits` (the plugin and the file pattern that mark the export as used, for example a Next.js page).

The `coordination_gap` entries of `--impact-closure` have the same `search_visibility`, `reason` and `search_as` fields, and a `search_symbol` field.

### Baseline file {#baseline-file}

`--save-baseline` writes a JSON file with `"kind": "dead-code"`, `"identity": "dc1"` and one array of keys for each issue type. A key has the form `<rule>:<path>:<name>`, for example `unused-export:src/lib/format.ts:formatPercent`, or `<rule>:<path>` for a file, for example `unused-file:src/utils/legacy-currency.ts`. A key has no line and no column, so a line shift does not make it stale. A key that occurs N times hides at most N current findings. A save to a file of another `kind` exits with code 2. [Baselines](/guides/baselines) shows the workflow.

## Exit codes

| Code | Meaning |
|:--|:--|
| `0` | No finding at `error` severity, and no other gate failed. |
| `1` | A finding has a rule at `error`, in every output format. `--fail-on-issues` and `--ci` also count the rules at `warn`. `--fail-on-regression`, `--fail-on-stale-baseline`, `--fail-on-baseline-growth` and `--fail-on-parse-error` also set code 1. |
| `2` | Invalid input, for example a malformed `--finding-id` or an unknown baseline `identity`. |

The bare `fallow` run has another rule for the machine formats. See [The bare run](/cli#bare-run). [Exit codes](/reference/exit-codes) has the codes that all commands share.

## Examples

```bash
# Report all dead code findings
fallow dead-code

# Report only unused exports, as JSON for a script
fallow dead-code --unused-exports --format json --quiet

# Report only the findings in two files
fallow dead-code --file src/utils.ts --file src/helpers.ts

# Show why an export is reported
fallow dead-code --trace src/lib/format.ts:formatPercent

# Show where a package is imported
fallow dead-code --trace-dependency lodash

# Check if one finding still exists
fallow dead-code --finding-id dc1:unused-export:b650995c7b5b87c1 --format json --quiet

# Save the current findings, then fail only on new findings
fallow dead-code --save-baseline fallow-baselines/dead-code.json
fallow dead-code --baseline fallow-baselines/dead-code.json
```
