`fallow security` reports unverified security candidates: places where a secret can reach client code, or where input can reach a dangerous call.

For the concepts and the workflow, read [Security](/analysis/security).

## Synopsis

{/* generated:start cli-synopsis security */}

```bash
fallow security [OPTIONS] [PATH] [COMMAND]
```

{/* generated:end */}

The command is opt-in. Bare `fallow` and `fallow audit` do not run it. It runs two issue types: [`client-server-leak`](/rules/client-server-leak) and [`tainted-sink`](/rules/tainted-sink), with the categories that [`security.categories`](/reference/config-other#security-categories) selects.

### survivors {#survivors}

{/* generated:start cli-synopsis security survivors */}

```bash
fallow security survivors [OPTIONS] --candidates <PATH> --verdicts <PATH>
```

{/* generated:end */}

{/* generated:start cli-options security survivors */}

| Option | Description |
|:--|:--|
| `--candidates <PATH>` | Raw `fallow security --format json` candidate output |
| `--verdicts <PATH>` | Verifier verdict JSON file |
| `--require-verdict-for-each-candidate` | Fail when any candidate has no matching verdict |

{/* generated:end */}

`survivors` joins the saved candidates with the verdicts of a reviewer, and shows the candidates that the reviewer kept. [Security agent verification](/cli/security-agent-verification) has the verdict format. It exits with code 2 when the candidate file has a duplicate `finding_id`, when two verdicts name one candidate, or when a verdict names a candidate that the file does not have. It accepts the `human` and `json` formats.

### blind-spots {#blind-spots}

{/* generated:start cli-synopsis security blind-spots */}

```bash
fallow security blind-spots [OPTIONS]
```

{/* generated:end */}

{/* generated:start cli-options security blind-spots */}

| Option | Description |
|:--|:--|
| `--file <PATH>` | Scope diagnostics to selected files |

{/* generated:end */}

`blind-spots` groups the calls that fallow could not resolve, for example dynamic dispatch, by reason and by file. A candidate can hide behind such a call. It accepts the `human` and `json` formats.

`fallow security` accepts the `human`, `json`, `sarif`, `github-annotations` and `github-summary` formats. Another format exits with code 2.

### Regression gate {#regression-gate}

| `--gate` value | Exits with code 8 when | Needs |
|:--|:--|:--|
| `new` | the change adds a candidate on a changed line | `--changed-since`, `--diff-file` or `--diff-stdin` |
| `newly-reachable` | a candidate that the base already has becomes reachable from an entry point | `--changed-since` |

A gate run that cannot compute the diff exits with code 2, for example with a ref that a shallow clone does not have. The human output marks a gated candidate `REVIEW REQUIRED`. SARIF keeps each result at level `note` and puts the verdict in `run.properties.fallowGate`. The JSON output adds a `gate` object with `mode`, `verdict` and `new_count`.

### Severity for each path {#per-path-severity}

`fallow security` raises the rules `security-sink` and `security-client-server-leak` from `off` to `warn`, so that the command always reports. An `overrides[].rules` entry sets another severity for the files that it matches. `off` removes the candidates in those files. `error` makes the run exit with code 1 when a candidate in those files stays.

### Suppression {#suppression}

`// fallow-ignore-file security-client-server-leak` and `// fallow-ignore-file security-sink` suppress the candidates in one file. One `security-sink` token covers each category of `tainted-sink`.

## Output

```text
Security review: 1 item to check.
These are unverified security candidates, not confirmed vulnerabilities. Check whether the listed code can run with unsafe input, secrets, or settings, and whether anything blocks the risk.

[H] high OS command injection sink (CWE-78)  src/services/runner.ts:4
    evidence: Untrusted source reaches this sink (an argument traces to process arguments). Non-literal command passed to node:child_process.exec(). Candidate for verification: confirm the command/args are not attacker-controlled.
    code path: reachable from a runtime entry point (blast radius 1)
    input path: this module is reachable from a module that receives untrusted input via 0 import hops
    input import trace:
      src/services/runner.ts:4 (untrusted source)
      src/services/runner.ts:4 (sink site)
    import trace:
      src/services/runner.ts:4 (sink site)
    Next: check whether unsafe input, secrets, or settings can reach this risky call without a safe guard. If not, mark it as a false positive.

[I] Blind spot: 9 call sites use code patterns that fallow could not resolve, such as dynamic dispatch, computed members, or aliased bindings.
    Most unresolved callees: dynamic-dispatch in src/index.ts.

Result: 1 security item to check. Review the listed evidence and trace before changing code.
```

- Each candidate starts with its review priority (`[H]`, `[M]` or `[L]`), its category, its CWE number and its location.
- The `evidence`, `code path` and `input path` lines tell why fallow reports the candidate. The traces list the files from the input to the call.
- The `[I] Blind spot` lines count the calls that fallow could not follow.

With `--format json`, the output has these top-level fields:

| Field | Content |
|:--|:--|
| `kind` | `"security"`. `survivors` gives `"security-survivors"`, and `blind-spots` gives `"security-blind-spots"`. |
| `schema_version`, `version`, `elapsed_ms` | The version of this output format, the fallow version and the run time. |
| `config` | The configured and the effective severity of the two rules, and the selected categories. |
| `security_findings` | One object for each candidate. See [Candidate fields](#agent-actionable-candidate-record). |
| `unresolved_edge_files`, `unresolved_callee_sites`, `unresolved_callee_diagnostics` | The blind spots: the counts, and a bounded sample of the calls that fallow could not resolve. |
| `attack_surface` | The entry points, the inputs and the defensive checks on each trace. Present only with `--surface`. |
| `gate`, `gate_outcomes` | The result of `--gate`, and of each other gate of the run. |
| `request_outcomes` | The `sarif-file` entry, when the run wrote `--sarif-file`. |
| `workspace_diagnostics` | Problems with the project setup. |

With `--summary`, `summary` replaces the candidate arrays: the counts by severity, by category, by reachability and by runtime state. The [JSON output reference](/reference/json-output) has each field.

### Candidate fields {#agent-actionable-candidate-record}

| Field | Content |
|:--|:--|
| `finding_id` | A hash of the rule, the path, the line and the column. It is the same as the SARIF `partialFingerprints["fallowSecurity/v2"]`. A line change gives a new id. |
| `stable_finding_id` | `sec1:<16 hex digits>`: a hash without the line. A line change keeps it. Absent when fallow does not know the exact text of the call, for example in template markup. |
| `kind`, `category`, `cwe` | `client-server-leak` or `tainted-sink`, the category (for example `command-injection`), and the CWE number of a `tainted-sink` category. |
| `path`, `line`, `col` | The location of the candidate. |
| `severity` | The review priority: `high`, `medium` or `low`. It is not a verdict, and it does not change the exit code. |
| `evidence`, `trace` | The reason in words, and the files from the input to the call. Do not parse `evidence`. |
| `reachability` | Whether an entry point or an untrusted input reaches the call. `taint_confidence` is `arg-level` (the argument comes from the input in the same module) or `module-level` (only the module is reachable from the input). |
| `candidate` | `source_kind` (for example `http-request-input` or `process-argv`; an open set), `sink` (`path`, `line`, `col`, `category`, `cwe`, `callee`) and `boundary` (`client_server`, `cross_module`). `secret-to-network` candidates also have `network.destination`. |
| `taint_flow` | `source`, `sink` and `path` (`intra_module`, `cross_module_hops`), when an untrusted input reaches the call. |
| `source_backed` | `true` when fallow traced the argument of the call to a known untrusted input in the same module, for example `req.query` or `process.argv`. It raises the rank, and `false` does not hide the candidate. Absent when `false`. |
| `actions` | The suppression actions. |

[Security agent verification](/cli/security-agent-verification#finding-identity-migration) describes how fallow computes `stable_finding_id`.

## Exit codes

| Code | Meaning |
|:--|:--|
| `0` | The run completed. Candidates at `warn` do not change the exit code. |
| `1` | A candidate has a rule at `error`, or `--fail-on-issues` is set and the run has a candidate. |
| `2` | Invalid input, for example an unsupported format, or a gate run that cannot compute the diff. |
| `3` to `6` | With `--runtime-coverage`: the license is not valid, or the runtime coverage step failed. |
| `8` | `--gate` found a new candidate. A pipeline can allow this code alone, for example with GitLab `allow_failure: exit_codes: [8]`. |

[Exit codes](/reference/exit-codes) has the meaning of each code.

## Examples

```bash
# Report the security candidates
fallow security

# Save the candidates with the attack surface for a reviewer
fallow security --format json --surface --quiet > candidates.json

# Fail when a change adds a candidate on a changed line
fallow security --gate new --changed-since origin/main

# Check the staged changes in a pre-commit hook
git diff --cached --unified=0 | fallow security --gate new --diff-stdin

# Show the candidates that the reviewer kept
fallow security survivors --candidates candidates.json --verdicts verdicts.json

# List the calls that fallow could not follow
fallow security blind-spots --format json --quiet
```
