Create, list and test rule packs. A rule pack is a JSON or JSONC file with project policy rules, for example a banned import or a banned call. The `rulePacks` config key names the packs.

For policy rules and their findings, read [Architecture](/analysis/architecture).

## Option details {#option-details}

### Pack file {#pack-file}

`init` writes a pack file, and `test` reads one. A pack has `version: 1`, a unique `name`, an optional `description` and a non-empty `rules` array. Fallow loads a pack as data and never runs project code.

```jsonc
// rule-packs/team-policy.jsonc
{
  "$schema": "../node_modules/fallow/rule-pack-schema.json",
  "version": 1,
  "name": "team-policy",
  "rules": [
    { "id": "no-moment", "kind": "banned-import", "specifiers": ["moment"], "message": "Use date-fns." },
    { "id": "no-child-process", "kind": "banned-call", "callees": ["child_process.*"], "severity": "error" }
  ]
}
```

- Pack names and rule ids use only ASCII letters, digits, `.`, `_` and `-`. A finding has the id `<pack>/<rule-id>`.
- A field on the wrong rule kind is a load error. An invalid or missing pack stops the config load with exit code 2.
- `files` and `exclude` globs limit where a rule applies. `zones` limits it to files in the named [boundary zones](/configuration/boundaries). The three combine.
- `severity` overrides the `policy-violation` rule for one rule, and `off` turns the rule off. When the `policy-violation` rule is `off`, no pack rule runs. The exit code uses the severity of each finding.
- Keep pack files in a committed directory, not in the gitignored `.fallow/` directory.

### Rule kinds {#rule-kinds}

| `kind` | Key | Matches |
|:--|:--|:--|
| `banned-call` | `callees` | Calls and `new` expressions whose callee path matches a pattern. |
| `banned-import` | `specifiers` | Imports and re-exports whose specifier matches, as written. `moment` covers `moment/locale/nl`, and not `moment-timezone`. `@org/ui/*` matches the subpaths only. |
| `banned-effect` | `effects` | Calls with an effect class of the security catalogue: `read`, `write`, `network`, `storage`, `process`, `shell`, `crypto`, `randomness`, `dom`, `database` and others. Calls only, not `new` expressions. |
| `banned-export` | `exports` | Exported names. `default` matches the default export, and a trailing `*` matches a name prefix. |
| `gdp-proof-producer` | `allowedFiles` | Calls to `@gdp-ts/core.defineProof` outside the allowed files. See [gdp-ts proof producers](#gdp-proof-producers). |

`"ignoreTypeOnly": true` skips type-only imports for `banned-import`, and type-only exports for `banned-export`.

### Call forms {#call-forms}

- A `banned-call` pattern matches whole name segments, and follows imports, as a [forbidden call](/configuration/boundaries#forbidden-calls) does. `child_process.*` covers named, namespace and default imports from `child_process` and `node:child_process`.
- A pattern matches a call and a `new` expression, so `Date` covers `Date()` and `new Date()`. A `new` finding has `matched` set to `new Date`. Write the pattern as `Date`, not as `new Date`.
- A bare pattern matches the written name, so it also matches a local function or class with that name.
- Each call site is one finding. A `fallow-ignore-next-line` comment covers only the site on its next line.
- `banned-call` does not follow a callee in a variable (`const D = Date; new D()`), `Reflect.construct`, a subclass (`class X extends Date`) or `globalThis.Date`.
- `banned-import` does not match a rewritten specifier such as `npm:moment`. The rules do not read `require()`, dynamic `import()` or `import x = require()`.

### Allowed names {#allow-names}

`allowNames` on a `banned-import` rule bans a package and keeps some of its exports:

```json
{ "id": "three-math-only", "kind": "banned-import", "specifiers": ["three"], "allowNames": ["Vector3", "Quaternion"] }
```

- `import { Vector3 } from "three"` is allowed, and `import { Mesh } from "three"` is a finding.
- Each entry is an exact imported name, without globs. `default` allows a default import. The rule compares the name in the package, so `import { Mesh as Vector3 }` reports `three: Mesh`.
- A namespace import, a star re-export and a side-effect import always report, because fallow cannot prove that they stay in the list.
- A finding has `matched` set to `<specifier>: <binding>`, for example `three: Mesh`, `three: default`, `three: *` or `three: side-effect`. So `allowNames` changes the baseline keys and finding ids of the rule. Save the baseline again in the same commit.
- A blank entry, an entry with `*`, and `allowNames` on another rule kind are load errors.
- To ban only some exports, use `banned-call` with a pattern such as `three.Mesh`. It reports calls and `new` expressions, but not the import, a re-export, `extends Mesh` or a value reference.

### gdp-ts proof producers {#gdp-proof-producers}

A `gdp-proof-producer` rule restricts the files that create proof factories with `@gdp-ts/core.defineProof`. A global rule allows factories only in your authorization modules. A rule with `proofKinds` requires the factory of one proof kind in one owner file:

```json
{
  "version": 1,
  "name": "gdp",
  "rules": [
    { "id": "trusted-producers", "kind": "gdp-proof-producer", "allowedFiles": ["src/auth/**"], "severity": "error" },
    { "id": "delete-project-owner", "kind": "gdp-proof-producer", "allowedFiles": ["src/auth/project.ts"], "proofKinds": ["CanDeleteProject"], "severity": "error" }
  ]
}
```

- Each rule reports on its own. A call outside `src/auth/**` can break both rules. A call in `src/auth/other.ts` breaks only the owner rule.
- `allowedFiles` needs at least one glob relative to the project root. It grants the permission. `files`, `exclude` and `zones` still limit where the rule checks code.
- An absent or empty `proofKinds` checks each factory call, also a call with a dynamic label. A list matches exact static labels only, so keep the global rule for the dynamic labels.
- The rule follows named and namespace imports, renamed imports and unambiguous re-exports through project modules and workspace packages. It checks each analyzed file, also a file that no entry point reaches.
- It does not follow wrappers, local value aliases, `require()` or dynamic imports. It skips optional calls, computed member calls such as `gdp["defineProof"](...)` and ambiguous re-exports.
- The check is about the place of the factories. It does not check the authorization or the runtime permission. Keep the gdp-ts lint rules, such as `no-exported-prover`, and your TypeScript checks.

`fallow rule-pack list --format json` and [`fallow guard`](/cli/guard) show the permissions of the rules.

## Output

```bash
fallow rule-pack test
```

```text
error  ai-safe-repo/no-dynamic-code  1 finding
  src/utils/summary.ts:24:37  matched "eval"
error  ai-safe-repo/no-shell  1 finding
  src/utils/summary.ts:24:37  matched "process: eval"
no findings:
  error  ai-safe-repo/no-raw-html  banned-call
```

Each rule with matches gives its severity, its id as `<pack>/<rule>`, and the number of matches. An indented line gives the file, the line, the column and the matched token of each match. `no findings:` lists the rules without a match.

```bash
fallow rule-pack list
```

```text
ai-safe-repo (rule-packs/ai-safe-repo.jsonc): 3 rules
  Guardrails for repositories where AI agents write code: no dynamic code execution, no shelling out, no raw HTML sinks.
  - no-dynamic-code [error] banned-call: eval, Function
    Dynamic code execution is banned in this repository.
```

With `--format json`, `list` prints `kind: "rule-pack-list"` with `packs`. Each rule has `id`, `kind`, `severity`, `patterns`, `files`, `exclude` and `message`, and `allowNames` for a `banned-import` rule that has it. `test` prints `kind: "rule-pack-test"` with `packs`, `rules` (the number of matches of each rule), `findings` and `forced_severity`. The [JSON output reference](/reference/json-output) has each field.

## Exit codes

| Code | Meaning |
|:--|:--|
| `0` | The command completed. `test` also exits with `0` when it finds matches. |
| `2` | Invalid input, for example `test` without a configured pack, a pack that does not parse, or a pack file that `init` would overwrite. |

To fail a CI run on a policy violation, run [`fallow architecture`](/cli/architecture). See [Exit codes](/reference/exit-codes).

## Examples

```bash
# Create rule-packs/team-policy.jsonc from the starter template
fallow rule-pack init

# Create a pack from a template, and do not change the config file
fallow rule-pack init --template ai-safe-repo --no-config

# Test one pack file against the project
fallow rule-pack test rule-packs/team-policy.jsonc

# List the configured packs as JSON
fallow rule-pack list --format json
```
