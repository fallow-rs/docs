These options set the project root, the config file, the output format, the scope and the gates of a run. Most commands exit with code 2 when they get an option that they do not use.

## Options {#reference}

### Project {#options-project}

| Option | Description |
|:--|:--|
| `-r, --root <ROOT>` | Project root directory |
| `-c, --config <CONFIG>` | Path to config file (`.fallowrc.json`, `.fallowrc.jsonc`, `fallow.toml`, or `.fallow.toml`) |

### Scope {#options-scope}

| Option | Description |
|:--|:--|
| `--changed-since <CHANGED_SINCE>` (alias `--base <CHANGED_SINCE>`) | Only report issues in files changed since this git ref (e.g., main, HEAD~5). For this run, the ref replaces the per-package refs of `workspaces.changedSince` in the config. |
| `--no-package-baselines` | Ignore the per-package refs of `workspaces.changedSince` for this run. Every workspace package is then analyzed in full scope, for example to save or gate a whole-project baseline. |
| `--diff-file <PATH>` | Unified diff for line-level scoping. Use `-` to read from stdin. |
| `--diff-stdin` | Read the unified diff from stdin. Equivalent to `--diff-file -` |
| `--max-file-size <MB>` | Skip source files larger than this many megabytes (default 5) instead of parsing them, guarding against the out-of-memory blowup a single multi-MB generated/vendored/bundled file causes on large repos. Use `0` for no limit. |
| `--production`, `--no-production` | Production mode: exclude test/story/dev files, only start/build scripts, report type-only dependencies |
| `-w, --workspace <WORKSPACE>` | Scope output to selected workspaces. Accepts exact names, glob patterns, and `!`-prefixed negations. |
| `--changed-workspaces <REF>` | Scope output to workspaces touched since the given git ref. Git is required. |
| `--include-entry-exports` | Report unused exports in entry files instead of auto-marking them as used |

### Baselines {#options-baselines}

| Option | Description |
|:--|:--|
| `--baseline <BASELINE>` | Compare against a previously saved baseline file. Used by bare `fallow`, `dead-code`, `architecture`, `dupes` and `health`; other subcommands reject it. |
| `--baseline-mode <BASELINE_MODE>` | How `--baseline` matches health findings: per file and category (`count`, the default) or per function identity (`identity`, strict, and only against a baseline that was saved with `--baseline-mode identity`; such a baseline still reads in count mode). A finding's identity is its file path plus its function name, so renaming or moving a function that is still in the baseline reports it as new. Defaults to `count` when omitted. |
| `--save-baseline <SAVE_BASELINE>` | Save the current results as a baseline file. Used by bare `fallow`, `dead-code`, `architecture`, `dupes` and `health`; other subcommands reject it. |
| `--regression-baseline <PATH>` | Path to the regression baseline file |
| `--save-regression-baseline <PATH>` | Save the current issue counts as a regression baseline. Omit PATH to update regression.baseline in the discovered fallow config, or create `.fallowrc.json` when none exists. |

### Gates {#options-gates}

| Option | Default | Description |
|:--|:--|:--|
| `--ci` |  | CI mode: equivalent to `--format` sarif `--fail-on-issues` `--quiet` |
| `--fail-on-issues` |  | Exit 1 on issues, also where the default is 0: `dupes`, and bare `fallow` in the json, sarif, codeclimate, GitHub, comment and review formats |
| `--fail-on-regression` |  | Fail if issue count increased beyond tolerance compared to a regression baseline. With `list --entry-weight`, fail when the eager source bytes of an entry grew beyond the tolerance. |
| `--fail-on-stale-baseline` |  | Exit with code 1 if a loaded `--baseline` has entries that match nothing in this run. Stricter than the default advisory warning: any stale entry fails, not just a quarter of the baseline. |
| `--fail-on-baseline-growth` |  | Exit with code 1 if a loaded baseline has a key that the same file at the base ref does not have. Makes a committed baseline shrink-only. |
| `--baseline-base <REF>` |  | The git ref that `--fail-on-baseline-growth` compares the baseline with. Defaults to the `fallow audit` base resolution. |
| `--fail-on-parse-error` |  | Exit with code 1 if fallow could not parse a source file cleanly. Arms the `parse-error` gate: a file with a `source-parse-degraded` or `source-nesting-too-deep` entry in `workspace_diagnostics[]` fails the run, and the gate entry in `gate_outcomes["parse-error"]` names each such file. Off by default, because the parser also rejects valid syntax that is newer than the parser. |
| `--tolerance <TOLERANCE>` | `0` | Allowed issue count increase before a regression is flagged. With `list --entry-weight`, the value is the allowed growth of eager source bytes per entry: a byte count such as `1024`, or a percentage such as `5%`. |

## Option details {#option-details}

### Lean JSON {#lean}

Only `fallow dead-code`, `fallow health` and the bare `fallow` run accept `--lean`, and only with JSON output. Another command, for example `fallow dupes` or `fallow audit`, exits with code 2. A run without `--format json` exits with code 2 too.

### Scope rules {#path-scope}

- `--changed-since` reports only the findings in the files that changed since the git ref. Each command applies it in its own way: [Changed code](/concepts/changed-code) explains the scope of a run.
- `--diff-file` and `--diff-stdin` keep only the findings on added lines. A finding that covers more than one file, for example a cycle, stays when the diff touches one of its files. Findings in `package.json` and other project files stay in the report.
- A path argument (`fallow health src/api`) and `--workspace` narrow only the report. Fallow still builds the graph of the whole project. A path outside the project root exits with code 2.
- `--workspace` and `--changed-workspaces` together exit with code 2. `--changed-workspaces` with a ref that git cannot resolve exits with code 2.

### Gate rules {#gates}

A gate makes the run exit with code 1. The [gate](/concepts/findings) options are `--fail-on-issues`, `--ci`, `--fail-on-regression`, `--fail-on-stale-baseline`, `--fail-on-baseline-growth` and `--fail-on-parse-error`. The JSON output names the result of each gate in `gate_outcomes`.

#### Parse error gate {#parse-error-gate}

`--fail-on-parse-error`, or `failOnParseError: true` in the config file, exits with code 1 when fallow cannot parse a source file. The gate counts each file with a `source-parse-degraded` or `source-nesting-too-deep` entry in `workspace_diagnostics`. `gate_outcomes["parse-error"].files` names each file. The gate works with `dead-code`, `architecture`, `health`, `audit` and the bare run. `fallow audit` checks each file that it parsed, also the files that the change did not touch.

#### Baseline growth gate {#baseline-growth-gate}

`--fail-on-baseline-growth` exits with code 1 when a loaded baseline has a key that the same file at the base ref does not have. A committed baseline can then only shrink.

- `--baseline-base <REF>` sets the base ref. The default is the base of `fallow audit`.
- A baseline that the base ref does not have passes, with a note.
- A base ref that git cannot resolve exits with code 2, for example in a shallow clone. A default base that resolves to `HEAD` also exits with code 2.
- The result is `gate_outcomes["baseline-growth"]`, with the number of new keys in `observed`.

### Output files {#save-destinations}

`--save-baseline`, `--save-regression-baseline`, `--save-snapshot`, `--output-file` and `--sarif-file` write only inside these directories:

- the project root, and its git work tree when the working directory is inside it
- `GITHUB_WORKSPACE` and `CI_PROJECT_DIR`, when they are set
- `RUNNER_TEMP` and the system temp directory

Another path exits with code 2 before the analysis runs. A device such as `/dev/null` or `/dev/stdout` is always allowed. `--sarif-file` works with `dead-code`, `architecture`, `security` and a bare run that includes dead code. With another command, use `--format sarif --output-file`.

### Quiet runs {#quiet-runs}

`--quiet`, `--ci` and `FALLOW_QUIET` hide the progress output and the stderr warnings that repeat a `workspace_diagnostics` entry. The JSON output does not change. The gate lines and the config warnings still print. `fallow audit` also prints a shorter report.

### Production mode for one analysis {#per-analysis-production-mode}

`--production-dead-code`, `--production-health` and `--production-dupes` turn on [production mode](/concepts/production-mode) for one analysis. Only the bare run and `fallow audit` accept them. Fallow takes the first value that it finds in this order:

1. the options `--production` and `--production-<analysis>`
2. the environment variables `FALLOW_PRODUCTION_DEAD_CODE`, `FALLOW_PRODUCTION_HEALTH` and `FALLOW_PRODUCTION_DUPES`
3. the environment variable `FALLOW_PRODUCTION`
4. the [`production`](/reference/config) key of the config file

### Grouped output {#grouped-output}

`--group-by` splits the findings into groups. These are the values:

| Value | Group key |
|:--|:--|
| `owner` | The first owner of the file in `CODEOWNERS`, `.github/CODEOWNERS`, `.gitlab/CODEOWNERS` or `docs/CODEOWNERS`. |
| `directory` | The first path segment, for example `src`. |
| `package` | The [workspace](/concepts/workspaces) package. |
| `section` | The `[Section]` header of a GitLab `CODEOWNERS` file. Each group also has an `owners` array. |

The `json`, `human`, `sarif` and `codeclimate` formats show the groups. The JSON output has a `grouped_by` field and a `groups` array. For `dead-code` and `architecture`, the kind changes to `dead-code-grouped` and `architecture-grouped`. The other formats print one report and a note on stderr. `fallow flags` ignores the option.

### Cache {#incremental-caching}

Fallow keeps the parse results of each file in `.fallow/` and parses only the files that changed. `--no-cache` parses each file again. `cache.dir` in the config file or `FALLOW_CACHE_DIR` moves the cache. `--performance` shows the time of each step and the cache hits.

## Output

Each command page describes the output of that command. The options on this page add the parts below.

### Loaded config file {#loaded-config-disclosure}

In the `human` format, fallow prints the config file that it loaded on stderr, for example `loaded config: /repo/.fallowrc.json`. `--quiet` and the other formats hide the line. [`fallow config`](/cli/config) shows the merged config.

### Request outcomes {#request-outcomes}

When a run cannot apply `--changed-since`, a diff or `--sarif-file`, it continues and keeps its exit code. The JSON output then names the result in a `request_outcomes` object, keyed by request:

```json
{
  "request_outcomes": {
    "changed-since": {
      "status": "not-applied",
      "affects": "scope",
      "requested": "main",
      "reason": "not-a-repository",
      "message": "--changed-since 'main' was ignored because not a git repository, so this report covers the whole project instead of the changed files. Run fallow from inside the repository, or drop --changed-since."
    }
  }
}
```

| Member | Content |
|:--|:--|
| `status` | `applied`, or `not-applied` when the run could not do the request. |
| `affects` | `scope`: the report is wider than you asked. `artifact`: the run wrote no file. |
| `requested` | The value as you wrote it. |
| `scope_size` | How much the request left in scope, when the run measured it. `changed-since` counts the changed files that the run analyzed, `diff-filter` counts the added lines. `0` means that nothing was in scope. |
| `reason` | A kebab-case token. Present only when `status` is not `applied`. |
| `message` | The fix, the same text as on stderr. Present only when `status` is not `applied`. |

| Request | Asked by | `affects` | `reason` values |
|:--|:--|:--|:--|
| `changed-since` | `--changed-since`, `--base` | `scope` | `git-missing`, `not-a-repository`, `git-failed` |
| `diff-filter` | `--diff-file`, `--diff-stdin`, `FALLOW_DIFF_FILE` | `scope` | `oversize`, `unreadable`, `not-utf8`, `foreign-namespace`, `ambiguous-base` |
| `sarif-file` | `--sarif-file` | `artifact` | `directory-create-failed`, `write-failed`, `serialize-failed` |

An absent object means that the run received no request. The set of names and values is open: read an unknown value as "not applied". `fallow audit` has no `request_outcomes`, because it exits with code 2 when its base ref does not resolve.

## Exit codes

| Code | Meaning |
|:--|:--|
| `0` | No enforced gate failed. |
| `1` | An enforced [gate](#gates) failed. |
| `2` | Invalid input, for example an option that the command does not use, a path outside the project root, or `--workspace` together with `--changed-workspaces`. |

[Exit codes](/reference/exit-codes) has the codes of each command.

## Examples

```bash
# Report only the findings in the files that changed since main, as JSON
fallow dead-code --changed-since main --format json --quiet

# Group the health findings by the first directory of each path
fallow health --group-by directory

# Write an indented JSON report to a file
fallow dead-code --format json --pretty --output-file fallow-results.json
```
