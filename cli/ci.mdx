Post the comment, the review or the check run that an earlier fallow run rendered to a GitHub pull request or a GitLab merge request. These commands analyze nothing.

For the CI setup, read [CI comments](/integrations/ci-comments). The GitHub Action and the GitLab template run these commands for you.

### plan-pr-comment {#plan-pr-comment}

Compute the action for the summary comment: `create`, `update` or `skip`. The command calls no API.

## Options

Each input file comes from an earlier fallow run:

| File | Source |
|:--|:--|
| Comment body | An analysis with `--format pr-comment-github` or `pr-comment-gitlab`. The body holds a `<!-- fallow-id: <marker> -->` line. |
| Comment envelope | The path in `FALLOW_PR_COMMENT_ENVELOPE_FILE` while fallow renders the body. |
| Decision file | The path in `FALLOW_PR_DECISION_FILE` while fallow renders the body. |
| Review file | An analysis with `--format review-github` or `review-gitlab`. |

GitHub needs a token in `GH_TOKEN` or `GITHUB_TOKEN`, and the repository from `--repo`, `GH_REPO` or `GITHUB_REPOSITORY`. GitLab needs a token with the `api` scope in `GITLAB_TOKEN`, and the project from `--project-id` or `CI_PROJECT_ID`. The GitLab `CI_JOB_TOKEN` cannot write a merge request note. The posting commands need a token also with `--dry-run`, because they read the existing comments. `FALLOW_BOT_LOGIN`, `FALLOW_API_RETRIES`, `FALLOW_API_RETRY_DELAY` and `FALLOW_CONSOLIDATED_STATUS` change how fallow posts. See [Environment variables](/configuration/environment).

## Output

```bash
fallow ci plan-pr-comment --body comment.md --marker-id fallow-results --existing-comment-id 1 --existing-body comment.md
```

```text
{"action":"skip","marker_id":"fallow-results","skip_reason":"unchanged"}
```

The output is JSON for each subcommand. A comment plan has `action`, `marker_id`, and `body` for `create` and `update`. A `skip` action has a `skip_reason`: `clean_no_existing_comment` or `unchanged`. A review result has `comments_posted`, `comments_skipped`, `stale_fingerprints` and `threads_resolved`. A comment or a thread that the provider refuses goes into `post_errors` or `apply_errors`, and the exit code stays `0`.

With `--split-gates`, `post-check-run` posts one check for each gate, named `Fallow / <gate>`. Set `FALLOW_CONSOLIDATED_STATUS` to also post one check for all gates.

## Exit codes

| Code | Meaning |
|:--|:--|
| `0` | The command completed. A skipped post is a success. |
| `2` | Invalid input, for example a file that fallow cannot read, an invalid review file, or `--provider gitlab` for `post-check-run`. |
| `7` | A missing token, or a failed request to the provider API. |

With `--format json`, an error is a JSON object with `"error": true`. See [Exit codes](/reference/exit-codes).

## Examples

```bash
# Render the comment, then post or update it on pull request 42
fallow dead-code --format pr-comment-github --quiet > fallow-comment.md
fallow ci post-pr-comment --provider github --pr 42 --body fallow-comment.md --marker-id fallow-results

# Post the inline review comments on merge request 7
fallow audit --format review-gitlab --quiet > fallow-review.json
fallow ci post-review --provider gitlab --mr 7 --envelope fallow-review.json

# Post one GitHub check for each gate
FALLOW_PR_DECISION_FILE=fallow-pr-decision.json fallow dead-code --format pr-comment-github --quiet > fallow-comment.md
fallow ci post-check-run --provider github --decision fallow-pr-decision.json --repo acme/app --head-sha "$GITHUB_SHA" --split-gates
```
