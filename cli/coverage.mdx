Set up [runtime coverage](/analysis/runtime-coverage), analyze it, and upload the data that Fallow Cloud joins with it.

For what runtime coverage reports and how to collect it, read [Runtime coverage](/analysis/runtime-coverage). One local capture is free. Continuous capture needs a [license](/cli/license). The commands that read from or upload to Fallow Cloud need an API key.

### setup {#setup}

Check the license, find or install `fallow-cov` (the separate program that reads coverage data), write a collection recipe to `docs/collect-coverage.md`, and run the analysis when coverage data exists. A second run continues where the first run stopped.

{/* generated:start cli-synopsis coverage setup */}

```bash
fallow coverage setup [OPTIONS]
```

{/* generated:end */}

{/* generated:start cli-options coverage setup */}

#### Run {#setup-options-run}

| Option | Description |
|:--|:--|
| `-y, --yes` | Accept all prompts automatically |
| `--non-interactive` | Print instructions instead of prompting |

#### Output {#setup-options-output}

| Option | Description |
|:--|:--|
| `--json` | Emit deterministic setup instructions as JSON. Implies `--non-interactive` |

#### Fallow Cloud {#setup-options-fallow-cloud}

| Option | Default | Description |
|:--|:--|:--|
| `--cloud` |  | Plan the Fallow Cloud setup: beacon snippets with the deployed commit SHA, and CI steps that upload the inventory and source maps and register the deployment for that SHA. Writes nothing |
| `--wait` |  | With `--cloud`: poll Fallow Cloud until every setup step is done. Reads `$FALLOW_API_KEY`. |
| `--wait-timeout <SECS>` | `600` | With `--wait`: the longest wait in seconds |
| `--project-id <PROJECT_ID>` |  | With `--cloud`: project identifier (`owner/repo`). Default: $GITHUB_REPOSITORY, then $CI_PROJECT_PATH, then the git remote |
| `--git-sha <SHA>` |  | With `--cloud`: the deployed commit SHA that `--wait` checks. Default: `git rev-parse HEAD` |
| `--api-key <KEY>` |  | With `--wait`: Fallow Cloud API key. Precedence: this flag > $FALLOW_API_KEY |
| `--api-endpoint <URL>` |  | With `--cloud`: Fallow Cloud API base URL. Precedence: this flag > $FALLOW_API_URL > the default Fallow Cloud URL |

{/* generated:end */}

`--json` writes no file, installs nothing and uses no network. `--cloud` prints a plan for Fallow Cloud: the beacon snippets, the CI steps and the key variables, all for one commit SHA. The plan never holds a key value. `--wait` reads the setup state of the deployed SHA from Fallow Cloud every 10 seconds, until each step is done or `--wait-timeout` passes.

Fallow finds `fallow-cov` in this order: `FALLOW_COV_BIN`, `FALLOW_COV_BINARY_PATH`, the project dependencies, `~/.fallow/bin/fallow-cov`, then the `PATH`. Fallow checks the signature of `fallow-cov` each time it starts it. A missing or invalid signature stops the run with code 4.

`--runtime-coverage` takes a V8 directory, a V8 JSON file or an Istanbul coverage map. Cloud mode needs `--cloud`, `--runtime-coverage-cloud` or `FALLOW_RUNTIME_COVERAGE_SOURCE=cloud`.
```bash
fallow coverage upload-inventory [OPTIONS]
```

{/* generated:end */}

{/* generated:start cli-options coverage upload-inventory */}

#### Fallow Cloud {#upload-inventory-options-fallow-cloud}

| Option | Description |
|:--|:--|
| `--api-key <KEY>` | Fallow Cloud API key (bearer token). Precedence: this flag > $FALLOW_API_KEY. |
| `--api-endpoint <URL>` | Override the Fallow Cloud base URL. Useful for staging and on-premise deployments. |
| `--project-id <PROJECT_ID>` | Project identifier, for example `fallow-cloud-api` or `owner/repo`. Defaults to $GITHUB_REPOSITORY, then $CI_PROJECT_PATH, then the parsed origin URL from `git remote get-url origin`. |
| `--git-sha <SHA>` | Explicit git SHA for this inventory. Default: `git rev-parse HEAD`. |
| `--vercel-deployment-id <DEPLOYMENT_ID>` | Bind the upload to a Vercel deployment. Defaults to $VERCEL_DEPLOYMENT_ID only when $VERCEL=1. |

#### Input {#upload-inventory-options-input}

| Option | Description |
|:--|:--|
| `--exclude-paths <GLOB>` | Additional glob patterns to exclude from the walk. Applied after the existing fallow ignore rules. |
| `--path-prefix <PREFIX>` | Prefix for inventory paths to match the runtime beacon, for example `/app` for Docker or `/var/task` for Lambda. Defaults to repo-relative paths. |
| `--with-callers` | Also upload importer edges (which files import each function) and the framework entry routes that can statically reach each function. Opt-in: this builds the import graph by running the full static analysis, whereas the default upload is a fast per-file walk. |

#### Run {#upload-inventory-options-run}

| Option | Description |
|:--|:--|
| `--dry-run` | Print what would be uploaded and exit. No network call |
| `--allow-dirty` | Proceed even when the working tree has uncommitted changes. Warning: the inventory is generated from the working copy, so it may not match the uploaded git SHA. |
| `--ignore-upload-errors` | Treat transient upload failures as warnings instead of errors (exit 0). Validation and auth errors still fail hard; this only downgrades transport and server errors |

{/* generated:end */}

Without `--allow-dirty`, fallow refuses a working tree with uncommitted changes. `--project-id` defaults to `$GITHUB_REPOSITORY`, then `$CI_PROJECT_PATH`, then the `origin` remote. `--git-sha` defaults to `git rev-parse HEAD`. Use `$FALLOW_API_KEY` on a shared runner, because other processes can see a key on the command line. Fallow skips declaration files (`*.d.ts`) and overload signatures. Fallow Cloud refuses an inventory of more than 200,000 functions.

`--path-prefix` must match the directory of the deployed code, for example `/app` for a Docker image with `WORKDIR /app`, `/workspace` for Cloud Run and `/var/task` for AWS Lambda. With a wrong prefix, the dashboard shows no untracked functions.

## Option details

### What setup detects {#setup-detection}

`fallow coverage setup` reads `package.json`, the lockfiles and the scripts, and writes instructions for the project:

| Detection | Use |
|:--|:--|
| Framework | Selects a recipe for Next.js, NestJS, Nuxt, SvelteKit, Astro, Remix, Vite browser apps, plain Node services, or a general recipe. When one `package.json` has a Node server framework (Elysia, Express, Fastify, Hono, Koa, `@trpc/server`) and Vite, the server framework wins, so the recipe targets the API, not the client bundle. |
| Workspaces | Reads `workspaces` (npm, pnpm, yarn, bun) and writes one recipe for each member that runs code. It skips a library member: a member without a `start`, `preview` or `dev` script and without a Node server dependency. |
| Package manager | Uses `packageManager`, the lockfiles, or both, to select the install commands. |
| Coverage data | Finds `coverage/coverage-final.json`, `.nyc_output/coverage-final.json`, or V8 directories with JSON files. |

A project without runtime code, for example a repository that only runs the `dev` scripts of its children, gets no recipe. The JSON then has `framework_detected: "unknown"`, an empty `members` array and the warning `No runtime workspace members were detected; emitted install commands only.`

### The generated recipe {#recipe}

`docs/collect-coverage.md` holds the steps for one capture. For an app with a build script, the steps are:

```text
1. Remove any old dump directory: `rm -rf ./coverage`
2. Build the app: `<build command>`
3. Start the app with V8 coverage enabled: `NODE_V8_COVERAGE=./coverage <start command>`
4. Exercise the routes or jobs you care about.
5. Stop the app and run: `fallow coverage setup`
6. In CI, after the build, run `fallow coverage upload-inventory` with `FALLOW_API_KEY` set. ...
```

Fallow uses the `build`, `start` or `preview` scripts of the project when they exist. Else it uses the usual commands of the framework. A project that matches no recipe still gets a general `docs/collect-coverage.md`. After the capture, the next `fallow coverage setup` runs `fallow health --runtime-coverage` on the data.

### The Fallow Cloud plan {#cloud-plan}

Fallow Cloud joins runtime coverage to your code only when five things name the same commit SHA: the beacon, the inventory, the source maps, the deployment registration and the first runtime data. `--cloud` writes a plan that gives each part that SHA:

- **Beacon snippets.** A server reads the SHA from `FALLOW_COMMIT_SHA`, `VERCEL_GIT_COMMIT_SHA`, `RENDER_GIT_COMMIT` or `RAILWAY_GIT_COMMIT_SHA`. A browser bundle reads `VITE_FALLOW_COMMIT_SHA`, which the build sets. In a workspace, each member gets its own `runtimeSurface` tag.
- **CI steps.** `cloud.ci.steps` holds GitHub Actions steps for the job that builds and deploys: a checkout with `fetch-depth: 0`, `upload-inventory`, `upload-source-maps` for each bundled member, and the deployment registration. `cloud.ci.workflows_detected` names the workflow files that look like a deploy.
- **Keys.** The plan names `FALLOW_API_KEY` for CI and the server, and `VITE_FALLOW_API_KEY` for a browser key that can only send data.

`--wait` retries a network error, a rate limit and a server error. It exits with code 0 when each step is done, 1 when `--wait-timeout` passes first, and 2 on a key, scope or input error. With `--json`, `cloud.wait` holds the result (`complete`, `timeout` or `error`) and the last setup state. Its `next` field names the step to do now. Read the state as open data, because Fallow Cloud can add step ids and states.

### How cloud analysis joins functions {#cloud-join}

`analyze --cloud` gives the same `runtime_coverage` block as a local capture, with `data_source: "cloud"`. Fallow matches each cloud function to a local function in these steps:

1. It matches on stable ids.
2. It maps a runtime path, such as `/app/src/a.ts` of a container, onto the local tree. It compares the file name, then the path segments from the end.
3. It matches a function whose runtime name differs, for example an anonymous callback reported as `map` or `then`, on its position in the file.

Steps 2 and 3 do not guess. When two local files match one runtime path equally well, or two functions start on the same line, the function stays unmatched. Fallow leaves an unmatched function out of the findings and reports it in a `cloud_functions_unmatched` warning. `--debug-unmatched` lists them, highest traffic first.

In cloud mode, each finding and each hot path has a `cloud_context` object with the fields of the cloud row that fallow does not read itself, for example `errors`, `performance.cpu`, `performance.browser`, `branches`, `covered_by_test` and `test_hit_count`. A blast-radius entry from the cloud has `production_callers`, `caller_sites` and the caller counts in its `cloud_context`. `runtime_coverage.cloud_context` holds the top-level fields of the answer, for example `capabilities` and `page`. These fields do not change a verdict. A `null` count or an `untracked` state means "not measured", never zero.

The `actions[].type` of a finding is `delete-cold-code` for the verdict `safe_to_delete` and `review-runtime` for `review_required`. Read an unknown type as a later addition, not as an error.

### Function names in the inventory {#function-naming}

The runtime join needs the same function names on both sides. Fallow selects the name of each function in this order:

1. The parent context: a method key, a variable binding, a property key or `export default`.
2. The name of the function itself, for example `function foo() {}`.
3. `(anonymous_N)`, where `N` counts the functions of the file.

### Entry routes {#entry-routes}

With `--with-callers`, the upload has a `routes` array and a `routeIds` array for each function. Fallow takes each route pattern from a file name or the source code, never from a request.

- **File-based routes.** The Next.js, Remix, SvelteKit and Nuxt plugins find the route files. A route handler gives one route for each exported HTTP method. A TanStack Router file gives the pattern in its `createFileRoute("/repo/$repo")` argument.
- **Elysia routes.** Fallow reads calls such as `app.get("/v1/repos/:repo", handler)` in each file that imports `elysia`, and joins the prefixes of the app, of `.group()` and of each mounted plugin. A route with a path that is not a string literal stays out.

A route in `routeIds` can reach the function through the imports, but a request did not have to reach it. The upload keeps at most 500 routes and at most 50 route ids for each function. The `routeLimits` field and a warning show each cut.

### Path prefix {#path-prefix}

The beacon reports the path of a file as the runtime sees it. In a container, that is the path in the image, for example `/app/src/foo.ts`. The inventory has paths relative to the repository by default. Fallow Cloud joins the two on the path and the function name, so the paths must have the same prefix:

| Target | `--path-prefix` |
|:--|:--|
| Docker image with `WORKDIR /app` | `/app` |
| Cloud Run, Buildpacks | `/workspace` |
| Older official Node images | `/usr/src/app` |
| AWS Lambda | `/var/task` |
| GitHub Actions checkout | `/home/runner/work/<repo>/<repo>` |

The prefix starts with `/` and uses `/` as separator. After the upload, Fallow Cloud compares recent runtime paths with the inventory. When fewer than half of them match, fallow prints a warning: `inventory paths don't overlap with runtime coverage for this SHA (<matched>/<sampled> runtime paths matched).`

### Upload errors {#upload-errors}

For a known error code of Fallow Cloud, `upload-inventory` and `upload-static-findings` print a hint:

| Command and code | Message |
|:--|:--|
| `upload-inventory`, `unauthorized` | ``authentication failed. Generate an API key at https://fallow.cloud/settings#api-keys and set FALLOW_API_KEY on the runner. Note: this key is separate from the license JWT; `fallow license activate --trial` will not fix this error.`` |
| `upload-inventory`, `payload_too_large` | `inventory exceeds the 200,000-function server limit. Scope the walk with --exclude-paths, or open an issue if this is a legitimately large repo.` |
| `upload-static-findings`, `unauthorized` | ``authentication failed. Generate a live API key at https://fallow.cloud/settings#api-keys and set FALLOW_API_KEY on the runner. Note: a publishable ingest key (fallow_pub_k1_) is not accepted here, and `fallow license activate --trial` will not fix this error.`` |
| `upload-static-findings`, `payload_too_large` | `static findings exceed the 200,000-finding server limit. Scope the analysis with your fallow ignore rules, or open an issue if this is a legitimately large repo.` |

### Source maps {#source-maps}

When two maps have the same file name, for example two `index.js.map` files in different folders, fallow sends each one under its path in the build folder, so that no map replaces another. `--dry-run` does not read `FALLOW_API_KEY`. Without `--fail-fast`, fallow uploads the other maps after a failure and prints a summary.

Before the first upload, run the command with `--dry-run`, and fix each warning about `sources` that do not resolve to files of the repository. After the deployed service gets traffic, run `fallow coverage analyze --cloud`. A `coverage_unresolved` warning means that runtime positions did not map to source for this commit. Upload the maps for the same `--git-sha` that the beacon reports.

Run the upload in the CI job that builds the app:

```yaml
# GitHub Actions
- run: npm run build
- run: npx fallow coverage upload-source-maps --dir dist --git-sha "$GITHUB_SHA"
  env:
    FALLOW_API_KEY: ${{ secrets.FALLOW_API_KEY }}
```

```yaml
# GitLab CI
upload_source_maps:
  stage: deploy
  script:
    - npm run build
    - npx fallow coverage upload-source-maps --dir dist --git-sha "$CI_COMMIT_SHA"
```

```yaml
# CircleCI
- run: npm run build
- run:
    name: Upload source maps to fallow
    command: npx fallow coverage upload-source-maps --dir dist --git-sha "$CIRCLE_SHA1"
```

Each job needs `FALLOW_API_KEY` as a secret variable of the CI system.

### Agent-readable JSON {#agent-readable-json}

`fallow coverage setup --json` prints `kind: "coverage-setup"` with these top-level fields. The same project gives the same output.

| Field | Content |
|:--|:--|
| `schema_version` | The version of this output format. |
| `framework_detected` | `nextjs`, `nestjs`, `nuxt`, `sveltekit`, `astro`, `remix`, `vite`, `plain_node` or `unknown`. |
| `package_manager` | `npm`, `pnpm`, `yarn` or `bun`. |
| `runtime_targets` | `node`, `browser` or both, for all members together. |
| `members` | One object for each workspace that runs code: `name`, `path`, `framework_detected`, `package_manager`, `runtime_targets`, `files_to_edit`, `snippets`, `dockerfile_snippet`, `warnings`. A project with one app has one member with path `.`. |
| `commands` | The install commands. |
| `files_to_edit`, `snippets`, `dockerfile_snippet` | Copies of the first member. In a monorepo, read each member. |
| `config_written` | The path of a written config file, or `null`. |
| `next_steps` | Commands to run next. |
| `warnings` | Problems. A project without runtime code has an empty `members` array and a warning. |
| `cloud` | With `--cloud`: `project_id`, `git_sha`, `endpoint`, the key variables, `ci` with the steps, `source_maps`, `activation_url`, `wait_command`, and `wait` after `--wait`. |

`--explain` adds a `_meta` object with the meaning of each field. The `analyze` command with `--format json` gives the `runtime_coverage` object of [`fallow health`](/cli/health). In cloud mode, each finding and each hot path also has `cloud_context`. A `null` count in it means "not measured". `review-packet` and `deployment-changes` print the JSON answer of Fallow Cloud. The [JSON output reference](/reference/json-output) has each field.

## Exit codes {#exit-codes}

| Subcommand | Code | Meaning |
|:--|:--|:--|
| `setup` | `0` | The step completed, or each step is done. |
| `setup` | `1` | `--cloud --wait` passed `--wait-timeout` before each step was done. |
| `setup` | `2` | Invalid input, a rejected key, or a key without the scope. |
| `setup`, `analyze` | `3` | A license is present, but it is not valid, expired more than 30 days ago, or lacks runtime coverage. |
| `setup`, `analyze` | `4` | `fallow-cov` is missing, its signature is not valid, its protocol does not match, or it stopped. |
| `analyze` | `5` | Fallow cannot read the coverage input, or `fallow-cov` refused it. |
| `analyze` | `6` | `fallow-cov` reported an internal error. |
| `upload-inventory`, `upload-static-findings` | `7` | A network failure. |
| `upload-inventory`, `upload-static-findings` | `10` | Validation failed: no API key, no project id, no functions, uncommitted changes without `--allow-dirty`, or an analysis error. |
| `upload-inventory`, `upload-static-findings` | `11` | The upload is larger than the server allows. |
| `upload-inventory`, `upload-static-findings` | `12` | The server refused the key. |
| `upload-inventory`, `upload-static-findings` | `13` | A server error, or an answer that fallow cannot read. |
| `upload-source-maps` | `1` | One or more maps failed to upload. |
| `upload-source-maps` | `2` | Invalid input: no `FALLOW_API_KEY`, no repo or SHA, a missing directory, or no maps. |
| `upload-source-maps` | `7` | Each map failed with a network error, or fallow cannot start the HTTP client. |
| `review-packet`, `deployment-changes` | `2` | Invalid input, for example a `--function` value that is not `FILE:NAME`, or no changed source file. |
| `review-packet`, `deployment-changes` | `3` | No key, a key that is not valid, a plan without the feature, or a repository or deployment that Fallow Cloud does not know. |
| `review-packet`, `deployment-changes` | `7` | A network or server error. |

`--ignore-upload-errors` changes codes 7 and 13 of `upload-inventory` and `upload-static-findings` to 0. On an error, the cloud reads print a JSON object with `error`, `message` and `exit_code`. See [Exit codes](/reference/exit-codes).

## Examples

```bash
# Start the setup, and run it again after you capture traffic
fallow coverage setup

# Print the setup as JSON for an agent
fallow coverage setup --yes --json

# Analyze a local V8 capture
fallow coverage analyze --runtime-coverage ./coverage --format json

# Analyze the runtime data of Fallow Cloud
fallow coverage analyze --cloud --repo acme/web --format json

# Upload the function list from a container build in CI
fallow coverage upload-inventory --path-prefix /app

# Upload the source maps of the build
fallow coverage upload-source-maps --dir dist --git-sha "$GITHUB_SHA"

# Read the production facts of one function
fallow coverage review-packet --function src/cart.ts:addItem

# List the functions that stopped in the current deployment
fallow coverage deployment-changes --change stopped
```
