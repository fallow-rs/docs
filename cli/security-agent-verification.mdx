This protocol joins the candidates of [`fallow security`](/cli/security) with the verdicts of a reviewer, a person or an agent. Fallow makes no model calls and decides no verdict.

For the concepts and the workflow, read [Security](/analysis/security).

## Steps {#steps}

1. Save the candidates: `fallow security --format json --surface --quiet > candidates.json`.
2. For each entry of `security_findings`, the reviewer reads the candidate, its trace and the source code, and writes one verdict.
3. Save the verdicts in one file, for example `verdicts.json`.
4. Join the two files: `fallow security survivors --candidates candidates.json --verdicts verdicts.json`.
5. Optional: run [`fallow security blind-spots`](/cli/security#blind-spots) to see the calls that fallow could not follow.

The MCP `security_candidates` tool gives the same candidates. Its `surface` parameter adds `attack_surface`, and its `paths` parameter keeps only the candidates that touch the given files.

## Input: the candidate file {#candidate-file}

The candidate file is the unchanged JSON output of `fallow security`. [Candidate fields](/cli/security#agent-actionable-candidate-record) lists the fields of each candidate. Do not write verdicts into this file.

With `--surface`, `attack_surface.defensive_boundary.controls` lists the checks that fallow found in the files of the trace. A listed check does not prove that it runs before the call, or that it checks the same value. `attack_surface.defensive_boundary.verification_prompt` is a question for the reviewer, not a verdict.

## Output: the verdict file {#verdict-schema}

The verdict file is a JSON array of verdicts, or an object with `"schema_version": "fallow-security-verdicts/v1"` and a `verdicts` array.

```json
// verdicts.json
{
  "schema_version": "fallow-security-verdicts/v1",
  "verdicts": [
    {
      "schema_version": "fallow-security-verdict/v1",
      "finding_id": "sec1:3fd021dab48c54fc",
      "verdict": "survivor",
      "reason": "process.argv reaches exec without validation",
      "fix_direction": "avoid-shell"
    }
  ]
}
```

| Field | Required | Content |
|:--|:--|:--|
| `schema_version` | yes | `fallow-security-verdict/v1` |
| `finding_id` | yes | The `stable_finding_id` or the `finding_id` of the candidate. Use the stable id, so that the verdict stays valid when the call moves to another line. |
| `verdict` | yes | `survivor`: the reviewer could not dismiss the candidate. `dismissed`: the evidence shows no risk. `needs-human-review`: the evidence is not complete. |
| `reason` | no | A short reason. |
| `rationale` | no | A longer explanation. |
| `confidence` | no | The confidence or the priority that the reviewer gives. |
| `impact` | no | The effect when the candidate is real. |
| `fix_direction` | no | The direction of the fix, for example `avoid-shell`. |

## Result {#result}

```text
Security survivors: 1 verifier-retained candidate.
Verdicts: 1/1 candidates covered, 0 dismissed.
Retained and human-review rows are verifier dispositions, not vulnerabilities proven by fallow.

Survivors:
- src/services/runner.ts:4 (command-injection) [bd283bfd3eec47e6]
  reason: process.argv reaches exec without validation
  fix direction: avoid-shell
  Next: review the original candidate evidence before editing code.
```

With `--format json`, the output has the `kind` `"security-survivors"`, a `summary` (`candidates`, `verdicts`, `survivors`, `dismissed`, `needs_human_review`, `unverdicted`), a `survivors` array and a `needs_human_review` array. A candidate without a verdict counts in `unverdicted`. With `--require-verdict-for-each-candidate`, such a candidate makes the run exit with code 2.

| Code | Meaning |
|:--|:--|
| `0` | The join completed. |
| `2` | Invalid input: a verdict with another `schema_version`, a verdict for an unknown candidate, two verdicts for one candidate, a duplicate `finding_id` in the candidate file, or a missing verdict with `--require-verdict-for-each-candidate`. |

## Finding identity {#finding-identity-migration}

A candidate has two ids:

- `finding_id` hashes the rule, the path, the line and the column. A line change above the call gives a new id. Two calls on one line get different ids. It is the same value as the SARIF `partialFingerprints["fallowSecurity/v2"]`. The CLI, the MCP `security_candidates` tool and the editor give the same id. An editor diagnostic has it in `data.findingId`.
- `stable_finding_id` (`sec1:<16 hex digits>`) hashes the rule, the path and a name that does not depend on the line.

The name of a `stable_finding_id` is one of these:

- For a call or an assignment, the exact source text of the full expression. Whitespace, comments, line endings and a trailing comma do not count. The text in string, template and regex literals counts, so a new quote style gives a new id.
- For a hard-coded secret, the name of the variable or property and the kind of the match, for example the provider. The secret value is not part of the hash.
- For a client-server leak, the paths of the client file and the server module, and the names of the environment variables that the module reads.

When two calls in one file have the same text, the first one gets the base id, and the next ones get the suffix `~1`, `~2`. When you remove the first call, the second call gets the base id and its verdict. Review such calls again after you add or remove one of them.

A candidate in Vue, Svelte or Angular template markup, or in a file that fallow cannot read, has no `stable_finding_id`. Use its `finding_id`.

A verdict for an id that the candidate file does not have makes `survivors` exit with code 2. Save the candidates and the verdicts again together after a change of the id form.
