`fallow health` reports the functions above the complexity thresholds, the health of each file, the hotspots, the refactoring targets and the [health score](/analysis/health).

For the concepts and the workflow, read [Health](/analysis/health).

## Synopsis

{/* generated:start cli-synopsis health */}

```bash
fallow health [OPTIONS] [PATH]
```

## Options {#options}

| Argument | Description |
|:--|:--|

| Option | Default | Description |
|:--|:--|:--|
| `--max-cyclomatic <MAX_CYCLOMATIC>` |  | Maximum cyclomatic complexity threshold (overrides config) |
| `--max-cognitive <MAX_COGNITIVE>` |  | Maximum cognitive complexity threshold (overrides config) |
| `--max-crap <MAX_CRAP>` |  | Maximum CRAP score threshold (overrides config, default 30.0). Functions meeting or exceeding this score are reported alongside complexity findings. |
| `--max-file-lines <LINES>` |  | Maximum physical lines per file (overrides config `health.maxFileLines`, default 0 = off). A longer file is reported as a complexity finding with `exceeded: "file_lines"` |
| `--top <TOP>` |  | Show only the N most complex functions |
| `--sort <SORT>` | `cyclomatic` | Sort by: cyclomatic (default), cognitive, lines, or severity |
| `--complexity` |  | Show only complexity findings (functions exceeding thresholds). By default all sections are shown; use this to select only complexity |
| `--complexity-breakdown` |  | Include the per-decision-point complexity breakdown (`contributions[]`) on each complexity finding in `--format json` output. Each entry names the construct (if, else-if, loop, boolean operator, ...) and its cyclomatic/cognitive weight, so a consumer can explain WHY a function scored high. |
| `--file-scores` |  | Show only per-file health scores (fan-in, fan-out, dead code ratio, maintainability index). Requires full analysis pipeline (graph + dead code detection). |
| `--coverage-gaps` |  | Show only static test coverage gaps: runtime files and exports with no dependency path from any discovered test root. Requires full analysis pipeline |
| `--hotspots` |  | Show only hotspots: files that are both complex and frequently changing. Combines git churn history with complexity data. |
| `--ownership` |  | Attach ownership signals to hotspot entries: bus factor, contributor count, declared CODEOWNERS owner, and ownership drift. Implies `--hotspots`. |
| `--ownership-emails <MODE>` |  | Privacy mode for author emails emitted with `--ownership`. Defaults to `handle` (local-part only). Values: `raw`, `handle`, `anonymized`. |
| `--targets` |  | Show only refactoring targets: ranked recommendations based on complexity, coupling, churn, and dead code signals. Requires full analysis pipeline |
| `--type-coupling` |  | Show advisory project-local public-signature type coupling. Requires type-aware analysis and does not change the health score |
| `--css` |  | Add structural CSS analytics: specificity hotspots, !important density, over-complex selectors, deep nesting, and conservative cleanup candidates. Standard CSS is parsed structurally; preprocessor sources are scanned only where fallow can avoid expanding Sass/Less semantics |
| `--effort <EFFORT>` |  | Filter refactoring targets by effort level (low, medium, high). Implies --targets |
| `--score` |  | Show only the project health score (0–100) with letter grade (A/B/C/D/F). The score is included by default when no section flags are set |
| `--min-score <N>` |  | Fail if the health score is below this threshold (0-100). Implies --score. |
| `--min-severity <LEVEL>` |  | Only exit with error for findings at or above this severity. Use --min-severity critical to ignore moderate/high findings in CI. |
| `--report-only` |  | Print the score and findings but never fail CI (always exit 0). Advisory mode for surfacing health in logs without blocking. |
| `--since <DURATION>` |  | Git history window for hotspot analysis (default: 6m). Accepts durations (6m, 90d, 1y, 2w) or ISO dates (2025-06-01) |
| `--min-commits <N>` |  | Minimum number of commits for a file to be included in hotspot ranking (default: 3) |
| `--save-snapshot <PATH>` |  | Save a vital signs snapshot for trend tracking. Defaults to `.fallow/snapshots/{timestamp}.json` if no path is given. |
| `--trend` |  | Compare current metrics against the most recent saved snapshot. Reads from `.fallow/snapshots/` and shows per-metric deltas with directional indicators. |
| `--trend-from <PATH>` |  | Compare current metrics against this snapshot file instead of the newest file in `.fallow/snapshots/`. Use it to restore a baseline from external storage in CI. |
| `--coverage <PATH>` |  | Path to coverage data for measured per-function CRAP scores. | `--runtime-coverage <PATH>` |  | File or directory containing runtime coverage input. Accepts a V8 coverage directory, a single V8 JSON file, or a single Istanbul coverage map JSON file (commonly coverage-final.json). |

`fallow health` also accepts the [global options](/cli/global-flags). The thresholds take their default from the [`health` config](/reference/config-health).

### Sections {#section-selection}

Without a section option, the run shows the health score, the complexity findings, the file scores, the hotspots and the refactoring targets. A section option shows only its section: `--complexity`, `--file-scores`, `--hotspots`, `--targets`, `--score`, `--coverage-gaps`. You can give more than one. `--ownership` implies `--hotspots`, and `--effort` implies `--targets`.

- `--hotspots` and `--ownership` need git history, or a `--churn-file`. Outside a git repository, the section is empty and the run continues.
- `--score` alone does not read the git history, so the score has no hotspot penalty. Add `--hotspots` for the penalty.
- `--coverage-gaps` and `--type-coupling` are opt-in. `--type-coupling` needs `--type-aware`.
- `--coverage` reads an Istanbul map (`coverage-final.json`, or a directory that holds it) or raw V8 coverage. Without it, fallow looks for `coverage/coverage-final.json`, else it estimates the CRAP score. `FALLOW_COVERAGE` and `health.coverage` also set the path.

### Values {#option-values}

| Option | Values |
|:--|:--|
| `--sort` | `cyclomatic` (default), `cognitive`, `lines`, `severity`. Equal findings sort by path, line, column and name. |
| `--min-severity`, `--effort` | `moderate`, `high`, `critical` for `--min-severity`. `low`, `medium`, `high` for `--effort`. |
| `--ownership-emails` | `handle` (default): the local part of the email. `anonymized`: an `xxh3:<16 hex>` name, which is not a cryptographic hash. `raw`: the full email. `hash` is an old name of `anonymized`. |
| `--since` | A duration (`6m`, `90d`, `1y`, `2w`) or a date (`2025-06-01`). The default is `6m`. |
| `--baseline-mode` | `count` (default): match per file and category. `identity`: match per file and function name, only with a baseline that you saved with `--baseline-mode identity`. |

### Scope {#scoping}

`--workspace` and a path argument compute the score, the vital signs and the file scores again for the files in scope. `--group-by` adds a `groups` array: each group has its own `vital_signs`, `health_score`, `findings`, `file_scores`, `hotspots` and `targets`. The top-level fields stay project-wide. `--group` keeps only the groups that match.

### Baseline {#baseline}

`--save-baseline` saves the complexity findings with `"kind": "health"`. `--baseline` hides the findings in the file. A baseline applies only to complexity findings, not to file scores. The result of the comparison is in `summary.baseline_staleness`.

### Mutation report {#mutation-report}

`--mutation-report <FILE>` reads a saved [`fallow mutation`](/cli/mutation) JSON report, and shows the mutation score of each complexity finding below its CRAP score. The run starts no test. A function whose file changed since the mutation run shows `stale` and no score. The mutation score does not change the CRAP score, the health score or a gate. A plan document, a missing file or an invalid file exits with code 2.

```text
          23 ! cyclomatic   32 ! cognitive   39 lines

  Functions exceeding cyclomatic, cognitive, or CRAP thresholds; ! marks the
  dimension that breached

   86.2    src/services/customers.ts                       risk
             48 LOC    1 fan-in    0 fan-out    0% dead  0.48 density  552.0 risk

● Refactoring targets (1)
  1 low effort
    score = quick-win ROI (higher = better) · pri = absolute priority

   17.4  pri:17.4    src/services/customers.ts

         importers: src/index.ts (classifyCustomer)

```

- `Health score` gives the score, the grade and the largest deductions.
- `Metrics` gives the vital signs of the project.
- Each complexity finding gives the function, its severity band, its metrics and its CRAP score. `!` marks each threshold that the function exceeds.
- Each file score gives the maintainability index, the size, the fan-in and fan-out, the share of unused code, the complexity density and the CRAP risk.
- Each refactoring target gives its score, its priority, its effort and the recommendation.

### JSON output {#json-output}

With `--format json`, the output has these top-level fields. The field of a section is present only when the section ran.

| Field | Content |
|:--|:--|
| `kind` | `"health"` |
| `schema_version`, `version`, `elapsed_ms` | The version of this output format, the fallow version and the run time. |
| `sections` | The sections that the run produced. Use it to tell an empty section from a section that did not run. |
| `summary` | The counts and the thresholds: `files_analyzed`, `functions_analyzed`, `functions_above_threshold`, the `max_*_threshold` values, `average_maintainability`, `coverage_model`, and the count for each severity band. |
| `findings` | The complexity findings: `path`, `name`, `line`, `col`, `cyclomatic`, `cognitive`, `line_count`, `param_count`, `exceeded`, `severity` (the band), `effective_severity` (the rule), `crap`, `coverage_source`, `actions`. `--complexity-breakdown` adds `contributions`. |
| `health_score` | `score`, `grade`, `formula_version` and the `penalties` of each metric. |
| `vital_signs` | The project metrics. See [Vital signs](#vital-signs). |
| `file_scores` | One object for each file: `maintainability_index`, `fan_in`, `fan_out`, `dead_code_ratio`, `complexity_density`, `crap_max` and other metrics. |
| `hotspots`, `hotspot_summary` | The hotspots and the window of the history. See [Hotspots](#hotspots). |
| `change_coupling` | File pairs that change together without an import between them. |
| `targets`, `target_thresholds` | The refactoring targets, with `direct_callers` and `clone_siblings` when present. |
| `coverage_gaps` | The files and exports that no test reaches. Present with `--coverage-gaps`. |
| `runtime_coverage`, `coverage_intelligence` | The result of `--runtime-coverage`. |
| `mutation` | The result of `--mutation-report`. |
| `health_trend` | The comparison with a snapshot. Present with `--trend`. |
| `threshold_overrides` | The state of each `health.thresholdOverrides` entry: `active`, `stale`, `insufficient` or `no_match`. |
| `css_analytics`, `styling_findings`, `styling_health` | The CSS analysis. Present with `--css`. |
| `grouped_by`, `groups`, `group_filter` | The groups of a `--group-by` run. |
| `gate_outcomes` | One entry for each gate of the run. Always present. |
| `workspace_diagnostics` | Problems with the project or the inputs. |
| `next_steps` | Commands to run next. |

The [JSON output reference](/reference/json-output) has each field.

### Degraded inputs {#degraded-inputs}

An input that fallow cannot read gives zeros, for example a project without git or an unreadable snapshot. To tell a measured zero from a missing measurement, read `workspace_diagnostics`: an entry with `degrades_analysis: true` marks a missing input. Select on that field, and not on a list of kinds.

### Vital signs {#vital-signs}

| Field | Content |
|:--|:--|
| `dead_file_pct`, `dead_export_pct` | The percentage of unused files and of unused value exports. |
| `avg_cyclomatic`, `p90_cyclomatic`, `critical_complexity_pct` | The average and the 90th percentile of the cyclomatic complexity, and the percentage of functions at the critical band. |
| `duplication_pct` | The percentage of duplicated code. `null` without `--score`. |
| `hotspot_count`, `hotspot_top_pct_count` | The files with a hotspot score of 50 or more, and the files in the top 1 percent of the ranking. |
| `maintainability_avg`, `maintainability_low_pct` | The average maintainability index, and the percentage of files below 70. |
| `unused_dep_count`, `unused_deps_per_k_files` | The unused dependencies. |
| `circular_dep_count`, `circular_deps_per_k_files` | The circular dependencies. |
| `unit_size_profile`, `functions_over_60_loc_per_k` | The distribution of the functions by size. |
| `unit_interfacing_profile` | The distribution of the functions by parameter count. |
| `p95_fan_in`, `coupling_high_pct` | The 95th percentile of the fan-in, and the percentage of files above the fan-in threshold. |
| `counts` | The numbers behind each percentage. |

### Hotspots {#hotspots}

Each hotspot has `path`, `score` (0 to 100), `commits`, `weighted_commits` (with a half-life of 90 days), `lines_added`, `lines_deleted`, `complexity_density`, `fan_in`, `trend` (`Accelerating`, `Stable` or `Cooling`) and `is_test_path`. `hotspot_summary` has `since`, `min_commits`, `files_analyzed`, `files_excluded` and `shallow_clone`.

With `--ownership`, each hotspot also has these fields:

| Field | Content |
|:--|:--|
| `bus_factor` | The smallest number of authors that made half of the weighted commits. |
| `contributor_count` | The number of authors, without bots. |
| `top_contributor`, `recent_contributors` | The authors with the largest share: `identifier`, `format`, `share`, `stale_days`, `commits`. |
| `suggested_reviewers` | The recent contributors that committed in the last 90 days. |
| `declared_owner`, `unowned` | The owner in `CODEOWNERS`. `unowned` is `null` when the project has no `CODEOWNERS` file. |
| `ownership_state` | `active`, `unowned`, `declared_inactive` or `drifting`. |
| `drift`, `drift_reason` | `true` when the first author has less than 10 percent of the weighted commits of a file that is 30 days old or older. |

The `actions` of a hotspot can then have `low-bus-factor`, `unowned-hotspot` and `ownership-drift`. The [`health.ownership`](/reference/config-health#health-ownership) config key sets the bot patterns and the email mode.

### Snapshot file {#snapshots}

`--save-snapshot` writes `.fallow/snapshots/<timestamp>.json`, or the path that you give. `--trend` reads the newest file in that directory, and `--trend-from` reads one file. A snapshot has these fields:

| Field | Content |
|:--|:--|
| `snapshot_schema_version` | The version of this file format. |
| `version`, `timestamp`, `git_sha`, `git_branch`, `shallow_clone` | The fallow version, the time and the git state of the run. |
| `vital_signs`, `counts` | The [vital signs](#vital-signs) and the numbers behind them. |
| `score`, `grade`, `score_formula_version` | The health score. A trend compares scores only when the formula versions match. |
| `coverage_model` | The source of the CRAP coverage. |
| `groups` | The metrics of each group, when the run used `--group-by`. |

### Churn file {#importing-churn-from-a-non-git-vcs}

`--churn-file <PATH>` reads the change history from a JSON file, for a project without git. The file feeds `--hotspots`, `--ownership` and `--targets`. When the project also has git, the file wins.

```json
// churn.json
{
  "schema": "fallow-churn/v1",
  "events": [
    { "path": "src/foo.ts", "timestamp": 1717459200, "author": "dev@corp", "added": 10, "deleted": 5 }
  ]
}
```

| Field | Required | Content |
|:--|:--|:--|
| `path` | yes | The path from the repository root, with forward slashes. |
| `timestamp` | yes | The commit time in Unix seconds, UTC. A time more than one year in the future exits with code 2. |
| `author` | no | One stable identity for each person, for example the email. Fallow does not apply a mailmap. |
| `added`, `deleted` | yes | The changed lines. The hotspot score counts events, so the line counts are only for display. |

Give one event for each commit and file. Leave out merge commits and binary files. Give a renamed file under its new path only. Fallow ignores other fields.

## Exit codes

| Run | Exit code `0` when | Exit code `1` when |
|:--|:--|:--|
| `fallow health` | no finding has a `complexity-*` rule at `error` | a finding has a rule at `error`, which is the default |
| `--fail-on-issues` | the run has no finding | the run has a finding, also with a rule at `warn` |
| `--min-score N` | the score is `N` or higher | the score is lower than `N` |
| `--min-severity LEVEL` | no finding is at `LEVEL` or higher | a finding is at `LEVEL` or higher |
| `--report-only` | always | never |

With `--min-score` and `--min-severity` together, the run fails when one of them fails. With `--min-score` alone, the findings do not set the exit code. `--report-only` together with `--min-score` or `--min-severity` exits with code 2.

| Code | Meaning |
|:--|:--|
| `2` | Invalid input, for example an invalid `--mutation-report` file or `--trend-from` file. |
| `3` to `6` | With `--runtime-coverage`: the license is not valid, or the runtime coverage step failed. |

[Exit codes](/reference/exit-codes) has the meaning of each code.

## Examples

```bash
# Report the functions above the thresholds
fallow health

# Show only the 10 most complex functions, sorted by cognitive complexity
fallow health --complexity --top 10 --sort cognitive

# Use measured coverage for the CRAP scores
fallow health --coverage coverage/coverage-final.json

# Show the hotspots of the last 3 months, with their owners
fallow health --hotspots --ownership --since 3m

# Fail when the health score is lower than 70
fallow health --min-score 70

# Show the results without a failure
fallow health --report-only

# Save a snapshot, then compare a later run with it
fallow health --save-snapshot
fallow health --trend
```
