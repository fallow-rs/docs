`fallow health` reports the functions above the complexity thresholds, the health of each file, the hotspots, the refactoring targets and the [health score](/analysis/health).

For the concepts and the workflow, read [Health](/analysis/health).

## Synopsis

{/* generated:start cli-synopsis health */}

```bash
fallow health [OPTIONS] [PATH]
```

## Option details {#option-details}

### Section selection {#section-selection}

Without a section option, the run shows the health score, the complexity findings, the file scores, the hotspots and the refactoring targets. A section option shows only its section: `--complexity`, `--file-scores`, `--hotspots`, `--targets`, `--score`, `--coverage-gaps`. You can give more than one. `--ownership` implies `--hotspots`, and `--effort` implies `--targets`.

- `--hotspots` and `--ownership` need git history, or a `--churn-file`. Outside a git repository, the section is empty and the run continues.
- `--score` alone does not read the git history, so the score has no hotspot penalty. Add `--hotspots` for the penalty.
- `--coverage-gaps` and `--type-coupling` are opt-in. `--type-coupling` needs `--type-aware`.
- Fallow takes the coverage path from `--coverage`, else from `FALLOW_COVERAGE`, else from `health.coverage`. When none is set, fallow reads `coverage/coverage-final.json`, then `.nyc_output/coverage-final.json`, in the project root. Without these files, it estimates the CRAP score. An auto-detected file gives the note `using auto-detected coverage at <path>` on stderr. `--coverage-root` follows the same order with `FALLOW_COVERAGE_ROOT` and `health.coverageRoot`, and must be an absolute path.
- `--coverage` reads an Istanbul coverage map (`coverage-final.json`), a directory that holds one, a raw V8 coverage directory, or one V8 coverage JSON file. It does not read LCOV: with `lcov.info`, the run stops with `failed to parse coverage data` and exits with code 2. Add the `json` reporter to the test runner, and pass `coverage-final.json`.

### Coverage input {#coverage-input}

Fallow computes the statement coverage of each function over the statements in the body of that function. The statements of a nested function belong to the nested function, not to the function that holds it.

- For an Istanbul map, fallow counts the statements of each function from the file on disk, and reads the counts from the map. The coverage of a function can therefore differ from the text table of the test runner.
- For V8 input, fallow takes the statements from the file on disk and the counts from the V8 block ranges. It sums the dumps of all test processes. A transpiled script (`tsx`, an esbuild or webpack bundle) maps back to its sources through the source map that Node writes into the dump. A script that is different from the file on disk and has no source map keeps the estimate.
- A function that the coverage data does not describe keeps the estimate. The human output counts the matched functions: `CRAP scores use Istanbul coverage where matched (22/25 functions); the rest fall back to the static estimate.`
- When the coverage data describes files that match no analyzed file, fallow prints `note: the coverage file describes N files that no analyzed file matched`. Set `--coverage-root` to the checkout that made the data.

In the JSON output, `summary.coverage_model` names the model (see [CRAP](#crap-formula)). With measured coverage, `summary.coverage_input_format` names the input: `istanbul` or `v8`. Each CRAP finding has `coverage_source`, and `summary.coverage_source_consistency` is `uniform` when all findings have the same source, else `mixed`.

### Literal membership chains {#literal-membership-chains}

The standard cyclomatic count adds 1 for each `||`. A check of one value against a list of literals therefore gets a high value, although it is one decision:

```ts
if (kind === "a" || kind === "b" || kind === "c" || kind === "d") {
  throw new Error("Unsupported kind");
}
```

The standard value of this function is 5. Set [`health.cyclomaticPolicy`](/reference/config-health#health-cyclomaticpolicy) to `"literal-membership"` to count the chain as one predicate. The function then has the value 2 for the gates. A chain qualifies only when all of these are true:

- Each operator of the chain is `||`. Parentheses do not change the chain.
- Each operand is a `===` check between a plain identifier and a string, number, bigint, boolean or `null` literal, on either side.
- Each operand checks the same identifier, and the chain has two operands or more.

Member access (`obj.kind === "a"`), calls, `==`, `!==` and a chain with another operator keep the standard count. A chain inside a wider condition, such as `flag && (kind === "a" || kind === "b")`, counts as one predicate, and the `&&` still adds 1.

The policy changes the cyclomatic value of the `maxCyclomatic` gate, of each CRAP score and of the CRAP values of the file scores. The health score, the complexity density, the vital signs and the hotspots keep the standard count. The cognitive complexity does not change. In the JSON output, `summary.cyclomatic_policy` names the policy. A finding has the policy value in `cyclomatic`, and the standard value in `standard_cyclomatic` when the two values are different. With `--complexity-breakdown`, each `||` contribution of a chain has `"literal_membership": true`.

### Threshold overrides {#threshold-overrides}

A [`health.thresholdOverrides`](/reference/config-health#health-thresholdoverrides) entry gives some files or functions their own limits. The entry keeps the function in the output, and a suppression comment hides it. A finding checked against an override has `effective_thresholds` and `threshold_source: "override"`.

When an entry affects the run, the JSON output has a `threshold_overrides` array. It has one row for each entry and dimension. The dimension `complexity` covers `maxCyclomatic`, `maxCognitive`, `maxUnitSize` and `maxFileLines`. The dimension `crap` covers only `maxCrap`. To count the entries and not the rows, group on `override_index`.

| Field | Content |
|:--|:--|
| `status` | `active`: the entry raises a limit that the unit needs, or the unit exceeds a limit that the entry lowers. `stale`: the entry changes no result, because the unit passes the global limits or a suppression comment covers it. `insufficient`: the unit still exceeds the raised limit, so the finding stays. `no_match`: the entry matches no analyzed file or function. |
| `override_index` | The position of the entry in `thresholdOverrides`. |
| `dimension` | `complexity` or `crap`. |
| `outstanding` | The dimensions that the unit still exceeds with the entry. Absent when empty. |
| `path`, `function`, `line`, `col` | The matched unit. `line` is 1-based, `col` is 0-based. No position on a `no_match` row. |
| `configured_thresholds`, `effective_thresholds` | The limits of the entry, and the limits after fallow applies each matching entry to the defaults. |
| `metrics` | The current `cyclomatic` and `cognitive` of the unit, `crap` when coverage data exists, and `line_count` on a complexity row. |
| `reason` | The `reason` of the entry, when set. |

For an `insufficient` row, raise the limit more or make the function simpler.

A [`fallow-override-threshold-next-line`](/configuration/suppression#threshold-override-comments) comment sets the limits of the next function. Its rows go to `inline_threshold_overrides`. Its findings have `override_comment_line`.

| Option | Values |
|:--|:--|
| `--sort` | `cyclomatic` (default), `cognitive`, `lines`, `severity`. Equal findings sort by path, line, column and name. |
| `--min-severity`, `--effort` | `moderate`, `high`, `critical` for `--min-severity`. `low`, `medium`, `high` for `--effort`. |
| `--ownership-emails` | `handle` (default): the local part of the email. `anonymized`: an `xxh3:<16 hex>` name, which is not a cryptographic hash. `raw`: the full email. `hash` is an old name of `anonymized`. |

### Scope of the score {#scoping}

`--workspace` and a path argument compute the score, the vital signs and the file scores again for the files in scope. `--group-by` adds a `groups` array: each group has its own `vital_signs`, `health_score`, `findings`, `file_scores`, `hotspots` and `targets`. The top-level fields stay project-wide. `--group` keeps only the groups that match.

### Baseline {#baseline}

`--save-baseline` saves the complexity findings and the refactoring targets with `"kind": "health"`. `--baseline` hides the findings and the targets in the file. A baseline does not apply to file scores. The key of a target is `<path>:<category label>`, for example `src/utils.ts:dead code`. A target stays known while its file and category stay the same, also when its priority or effort changes. The result of the comparison is in `summary.baseline_staleness`.

### Performance timings {#performance}

`--performance` prints the time of each health stage on stderr. In the demo project:

```text
┌─ Health Pipeline Performance ─────────────────────
│  config:                0.0ms
│  discover files:       16.6ms
│  parse/extract:        38.5ms
│  complexity:            0.0ms
│  file scores:           0.2ms
│  git churn:           246.2ms (cold, 597 git log bytes)
│  hotspots:              0.0ms
│  duplication:          20.2ms
│  targets:               0.0ms
│  (other):              33.6ms
│  ────────────────────────────────────────────────
│  TOTAL:               355.4ms
└───────────────────────────────────────────────────
```

- `git churn` shows `cached` when the churn came from the cache, else `cold`. The byte count is the `git log` output that the run read. It is 0 when the cache or a churn file gave all the history.
- `(other)` is `TOTAL` minus the stage rows, at least `0.0ms`.
- In a bare `fallow` run, the health stages reuse the parse of the dead-code pass. `discover files` and `parse/extract` then show `(measured above)`.

With `--format json`, fallow writes the timings as one JSON object on stderr, so stdout keeps one report. The object has the `_ms` field of each stage, `parse_cpu_ms`, `git_churn_cache_hit`, `git_log_bytes`, `total_ms` and `shared_parse`. The times change from run to run, so do not use them as a gate.

### Mutation report {#mutation-report}

`--mutation-report <FILE>` reads a saved [`fallow mutation`](/cli/mutation) JSON report, and shows the mutation score of each complexity finding below its CRAP score. The run starts no test. A function whose file changed since the mutation run shows `stale` and no score. The mutation score does not change the CRAP score, the health score or a gate. A plan document, a missing file or an invalid file exits with code 2.

### Severity bands and labels {#severity-bands}

Each complexity finding gets the highest band of its three values. The bands are fixed. The limits `maxCyclomatic`, `maxCognitive` and `maxCrap` decide only if a function has a finding, and the `complexity-*` rules decide if the finding fails the run.

| Value | `moderate` | `high` | `critical` |
|:--|:--|:--|:--|
| Cyclomatic complexity | below 30 | 30 to 49 | 50 or more |
| Cognitive complexity | below 25 | 25 to 39 | 40 or more |
| CRAP | below 50 | 50 to 99 | 100 or more |

A [long file](/rules/long-file) finding is always `moderate`.

The other labels of the human output:

- `maintainability 92.8 (good)`: `good` for an average maintainability index of 85 or more, `moderate` for 65 or more, `low` below 65. The health score counts a file below 70 as low (`maintainability_low_pct`).
- The `risk` column of a file score shows the highest CRAP score of the file: low below half of `maxCrap`, moderate up to `maxCrap`, high at `maxCrap` or more. With the default limit, that is `low <15`, `moderate 15-30` and `high >=30`. A value above 999 shows as `>999`. The JSON output has the exact value.
- The `risk` or `structure` tag tells which value puts the file in its place: the CRAP risk, or the low maintainability index.

### CSS analysis {#css-analysis}

With `--css`, the output has three fields. [Styling](/analysis/styling) explains the analysis.

- `css_analytics`: the measurements and the cleanup candidates.
- `styling_findings`: the findings of the five styling rules, each with `code`, `sub_kind`, `effective_severity`, the location, the evidence value and read-only actions.
- `styling_health`: the styling score.

### Coverage gaps {#with-coverage-gaps}

With `--coverage-gaps`, the output has `coverage_gaps`:

- `summary`: `runtime_files`, `covered_files`, `file_coverage_pct`, `untested_files` and `untested_exports`.
- `files[]`: the runtime files that no test reaches, with `path`, `value_export_count` and `actions`.
- `exports[]`: the exports that no test reaches in files that tests reach, with `path`, `export_name`, `line`, `col` and `actions`.

The analysis knows test mocks. A `vi.mock` or `jest.mock` call with a closed factory replaces the module: the factory has no `vi.importActual` or `jest.requireActual`, and the test has no other import of the module. Such a test does not reach the module, so the module can be a gap. When fallow cannot prove the replacement, the module keeps its credit:

- A mock without a factory keeps the credit, because the test runner can still load the original module.
- `vi.doMock` and `jest.doMock` keep the credit, because they are not hoisted and depend on the order of the code.

The [`coverage-gaps`](/reference/config-rules) rule sets the severity, and it is `off` by default. To leave one file out, put `// fallow-ignore-file coverage-gaps` in the file.

### Runtime coverage {#runtime-coverage}

With `--runtime-coverage`, the output has `runtime_coverage` with the verdict of the run, the findings for each function and the hot paths. [Runtime coverage](/analysis/runtime-coverage) explains the data and the capture. See [Evidence fields](/explanations/health#coverage-evidence).

### Degraded inputs {#degraded-inputs}

An input that fallow cannot read gives zeros, for example a project without git or an unreadable snapshot. To tell a measured zero from a missing measurement, read `workspace_diagnostics`: an entry with `degrades_analysis: true` marks a missing input. Select on that field, and not on a list of kinds.

```bash
fallow health --format json --quiet | jq '.workspace_diagnostics[] | select(.degrades_analysis)'
```

Fallow writes each entry with or without `--quiet`. These kinds come from the health inputs:

| `kind` | Meaning | `degrades_analysis` |
|:--|:--|:--|
| `file-scores-unavailable` | The file score pass failed. The score list is empty, and each number from the scores is zero. | `true` |
| `hotspots-skipped` | The hotspot, churn and ownership sections report nothing. `cause` is `not-a-repository`, `invalid-since` or `churn-file-unreadable`. | `true` |
| `shallow-clone` | The churn covers only the fetched history. `ownership_requested` tells if the run asked for ownership. | `true` |
| `unpinned-clock` | No commit time is available, so the recency weights move between two runs on the same commit. | `true` |
| `ownership-unavailable` | The ownership inputs did not load. `cause` is `invalid-bot-pattern` or `codeowners-parse-failed`. | `true` |
| `trend-snapshot-unreadable` | Fallow could not read a saved snapshot, so the trend uses fewer snapshots. | `true` |
| `change-coupling-skipped` | `change_coupling.pairs` is empty. `cause` is `shallow-clone` or `too-few-commits`. The other sections still measure. | absent |
| `trend-group-baseline-unavailable` | The baseline snapshot has no group data for the `--group-by` mode. See [Group trends](#group-trends). | absent |
| `coverage-auto-detected` | Not a failure: `path` names the coverage file that fallow found on disk. | absent |

The set of kinds is open. Read a kind that you do not know as one more diagnostic, not as an error.

### Vital signs {#vital-signs}

| Field | Content |
|:--|:--|
| `dead_file_pct`, `dead_export_pct` | The percentage of unused files and of unused value exports. |
| `avg_cyclomatic`, `p90_cyclomatic`, `critical_complexity_pct` | The average and the 90th percentile of the cyclomatic complexity, and the percentage of functions with a cyclomatic complexity of 50 or more. |
| `cyclomatic_population`, `total_loc` | The count, sum and maximum of the cyclomatic complexity for functions, module scopes and templates, and the lines of code. |
| `duplication_pct` | The percentage of duplicated code. `null` without `--score`. |
| `hotspot_count`, `hotspot_top_pct_count` | The files with a hotspot score of 50 or more, and the files with a positive score in the top 1 percent of the ranking. `hotspot_count` feeds the health score. `groups[].hotspot_count` of a `--group-by` run is a different count: the length of the ranked hotspot list of the group, before `--top`. Do not compare the two counts. |
| `maintainability_avg`, `maintainability_low_pct` | The average maintainability index, and the percentage of files below 70. |
| `unused_dep_count`, `unused_deps_per_k_files` | The unused dependencies. |
| `circular_dep_count`, `circular_deps_per_k_files` | The circular dependencies. |
| `unit_size_profile`, `functions_over_60_loc_per_k` | The distribution of the functions by lines, in percent: `low_risk` (1 to 15), `medium_risk` (16 to 30), `high_risk` (31 to 60) and `very_high_risk` (more than 60). `functions_over_60_loc_per_k` is the number of functions over 60 lines for each 1,000 functions. |
| `unit_interfacing_profile` | The distribution of the functions by parameter count, in percent: `low_risk` (0 to 2), `medium_risk` (3 to 4), `high_risk` (5 to 6) and `very_high_risk` (7 or more). |
| `p95_fan_in`, `coupling_high_pct` | The 95th percentile of the fan-in, and the percentage of files with a fan-in above the larger of `p95_fan_in` and 10. |
| `counts` | The numbers behind each percentage. |

### Health score {#health-score-formula}

The score starts at 100. Fallow subtracts each penalty in `health_score.penalties`, rounds to one decimal, and keeps the result between 0 and 100. A penalty of an analysis that did not run is `null` and subtracts nothing.

| Penalty | Formula | Maximum |
|:--|:--|:--|
| `dead_files` | `dead_file_pct` × 0.2 | 15 |
| `dead_exports` | `dead_export_pct` × 0.2 | 15 |
| `complexity` | `critical_complexity_pct` × 4 | 20 |
| `p90_complexity` | (`p90_cyclomatic` − 10), only when `critical_complexity_pct` is absent | 10 |
| `maintainability` | `maintainability_low_pct` × 1.5 | 15 |
| `hotspots` | `hotspot_count` ÷ (1 percent of the files, rounded up, at least 1) × 10 | 10 |
| `unused_deps` | `unused_deps_per_k_files` × 0.5 | 25 |
| `circular_deps` | `circular_deps_per_k_files` × 0.5 | 25 |
| `unit_size` | `functions_over_60_loc_per_k` × 0.5 | 10 |
| `coupling` | `coupling_high_pct` × 0.5 | 5 |
| `duplication` | `duplication_pct` − 5 | 10 |
| `prop_drilling` | 1 for each prop-drilling chain, only with the `prop-drilling` rule | 5 |

The grade is `A` for a score of 85 or more, `B` for 70, `C` for 55, `D` for 40 and `F` below 40. `formula_version` is `3`.

### Maintainability index {#maintainability-index-formula}

`maintainability_index` of a file is:

```text
MI = 100 − complexity_density × 30 × min(lines ÷ 50, 1) − dead_code_ratio × 20 − min(ln(fan_out + 1) × 4, 15)
```

- `complexity_density` is the sum of the cyclomatic complexity of the file divided by its lines.
- `dead_code_ratio` is the share of the value exports that nothing uses. It is 1 for an unused file, and 0 for a file without value exports.
- Fallow keeps the result between 0 and 100.

### CRAP {#crap-formula}

```text
CRAP = CC² × (1 − coverage)³ + CC
```

`CC` is the cyclomatic complexity of the function. With a coverage file, `coverage` is the measured coverage of the function (`coverage_model` `istanbul`). Without one, fallow estimates it (`coverage_model` `static_estimated`): 85 percent for a function that a test imports, 40 percent for another function in a file that a test reaches, and 0 for a function that no test reaches. Only a value import counts as a direct test reference, not an `import type`. An old snapshot can also have `static_binary`, a model that the current version does not produce.

A function with full coverage scores its `CC`, and a function without coverage scores `CC² + CC`. With the default estimate, an untested function with a cyclomatic complexity of 5 scores 5² + 5 = 30, which is the default limit.

Each finding has `coverage_tier`: `none` (no coverage), `partial` (below 70 percent) or `high` (70 percent or more). The first action of a CRAP finding follows from the formula:

| Condition | First action |
|:--|:--|
| `cyclomatic` is below `maxCrap`, and `coverage_tier` is `none` | `add-tests` |
| `cyclomatic` is below `maxCrap`, and `coverage_tier` is `partial` or `high` | `increase-coverage` |
| `cyclomatic` is `maxCrap` or more: full coverage cannot bring the score below the limit | `refactor-function` |

A CRAP-only finding also gets a second `refactor-function` action when its cyclomatic complexity is within [`health.crapRefactorBand`](/reference/config-health#health-craprefactorband) (default 5) of `maxCyclomatic`, and its cognitive complexity is half of `maxCognitive` or more. The cognitive condition keeps this advice away from a flat `switch`, which has many paths and is easy to read.

The `actions` of a finding have no `suppress-line` hint when a baseline is active, or when [`health.suggestInlineSuppression`](/reference/config-health#health-suggestinlinesuppression) is `false`. The output then has `actions_meta` with `"suppression_hints_omitted": true` and a `reason` of `baseline-active` or `config-disabled`.

### Refactoring targets {#refactoring-targets}

```text
priority = min(complexity_density, 1) × 30 + hotspot_score ÷ 100 × 25 + dead_code_ratio × 20 + min(fan_in ÷ fan_in_p95, 1) × 15 + min(fan_out ÷ fan_out_p95, 1) × 10
efficiency = priority ÷ effort
```

`effort` is 1 for `low`, 2 for `medium` and 3 for `high`. The targets are sorted by `efficiency`, highest first.

- `high` effort: 500 lines or more, a fan-in of `fan_in_p95` or more, or 15 functions or more with a complexity density above 0.5.
- `low` effort: fewer than 100 lines, 3 functions or fewer, and a fan-in below the 25th percentile (at least 2).
- `medium` effort: each other file.

`target_thresholds` holds the percentiles of the project: `fan_in_p95` (at least 5), `fan_in_p75` (at least 3), `fan_out_p95` (at least 8) and `fan_out_p90` (at least 5).

Fallow checks the rules of this table in order, and gives a file the category of the first rule that matches. The human output shows the label. The JSON `factors` still list each signal of the file.

| `category` | Label | Rule | `confidence` |
|:--|:--|:--|:--|
| `urgent_churn_complexity` | `churn+complexity` | A hotspot score of 50 or more, the trend `Accelerating`, and a complexity density above 0.5. | `low` |
| `break_circular_dependency` | `circular dependency` | The file is in an import cycle, and has a fan-in of 5 or more. | `high` |
| `split_high_impact` | `high impact` | A complexity density above 0.3, and a fan-in of `fan_in_p95` or more, or of `fan_in_p75` or more with 5 functions or more. | `medium` |
| `remove_dead_code` | `dead code` | Half or more of the value exports are unused, and the file has 3 value exports or more. | `high` |
| `extract_complex_functions` | `complexity` | A function with a cognitive complexity of 30 or more. | `high` |
| `extract_dependencies` | `coupling` | A fan-out of `fan_out_p90` or more and a maintainability index below 60. Entry points do not match. | `medium` |
| `add_test_coverage` | `untested risk` | 2 functions or more at or above `maxCrap`, and a complexity density above 0.3. | `high` |
| `break_circular_dependency` | `circular dependency` | Each other file in an import cycle. | `high` |
| `resolve_hidden_coupling` | `hidden coupling` | A strong [change coupling](#change-coupling) pair (degree 0.5 or more). Only a file that no other rule claims. | `medium` |

A strong pair also adds the `hidden_coupling` factor to the targets of both files, whatever their category. The factor has the degree as `value` and `0.5` as `threshold`.

The `evidence` object links a target to the data behind it. Fallow leaves out `evidence` when it has no data.

| Field | Content |
|:--|:--|
| `unused_exports` | For `remove_dead_code`: the names of the unused exports. |
| `complex_functions` | `name`, `line` and `cognitive` of each function. For `extract_complex_functions`, the functions with a cognitive complexity of 30 or more. For `add_test_coverage`, up to 3 functions with the highest cognitive complexity. |
| `cycle_path` | For `break_circular_dependency`: the files of the cycle. |
| `co_change_partners` | For `resolve_hidden_coupling`: up to 5 files that change together with the target, strongest first, with `path`, `shared_revisions` and `degree`. |
| `direct_callers` | Up to 5 files that import the target, with the symbols that they import. |
| `clone_siblings` | Up to 5 other instances of the clones in the file, with their `dup:` handle for `fallow dupes --trace`. |

### Hotspots {#hotspots}

The hotspot `score` is the weighted commits of the file divided by the largest weighted commits, times its complexity density divided by the largest complexity density, times 100. Each hotspot has `path`, `score` (0 to 100), `commits`, `weighted_commits` (with a half-life of 90 days), `lines_added`, `lines_deleted`, `complexity_density`, `fan_in`, `trend` (`Accelerating` when the newer half of the window has more than 1.5 times the commits of the older half, `Cooling` below 0.67 times, else `Stable`) and `is_test_path`. `hotspot_summary` has `since`, `min_commits`, `files_analyzed`, `files_excluded` and `shallow_clone`.

With `--ownership`, each hotspot also has these fields:

| Field | Content |
|:--|:--|
| `bus_factor` | The smallest number of authors that made half of the weighted commits. |
| `contributor_count` | The number of authors, without bots. |
| `top_contributor`, `recent_contributors` | The authors with the largest share: `identifier`, `format`, `share`, `stale_days`, `commits`. |
| `suggested_reviewers` | The recent contributors that committed in the last 90 days. |
| `declared_owner`, `unowned` | The owner in `CODEOWNERS`. `unowned` is `null` when the project has no `CODEOWNERS` file. |
| `ownership_state` | `active`, `unowned`, `declared_inactive` or `drifting`. |
| `drift`, `drift_reason` | `true` when the first author has less than 10 percent of the weighted commits of a file that is 30 days old or older. |

The `actions` of a hotspot can then have `low-bus-factor`, `unowned-hotspot` and `ownership-drift`. The [`health.ownership`](/reference/config-health#health-ownership) config key sets the bot patterns and the email mode.

| Action | When | Next step |
|:--|:--|:--|
| `low-bus-factor` | `bus_factor` is 1. | Add a second reviewer. The `note` names candidates from `suggested_reviewers` when they exist. |
| `unowned-hotspot` | `unowned` is `true`: a `CODEOWNERS` file exists, and no rule matches. | Add a `CODEOWNERS` entry. `suggested_pattern` gives the deepest directory of the file, and `heuristic` is `directory-deepest`. |
| `ownership-drift` | `ownership_state` is `drifting`. | Update `CODEOWNERS` to the new top contributor. |

The human output marks the [bus factor](/explanations/health#ownership-markers) of each hotspot.

In the `handle` mode, fallow also removes a GitHub noreply prefix: `12345+alice@users.noreply.github.com` shows as `alice`. The `anonymized` mode keeps raw emails out of CI artifacts, but it is not strong privacy: a person with a list of the emails of an organization can compute the same names. The default bot patterns do not include `*noreply*`, because most people commit from a GitHub noreply address.

Fallow computes the ownership signals only for files that pass `--min-commits`. Squash merges make one author look more dominant, and a shallow clone distorts the signals more.

The `[test]` tag and `is_test_path` follow the [test path rules](/explanations/health#test-paths).

### Change coupling {#change-coupling}

The `change_coupling` section lists [hidden pairs](/explanations/health#change-coupling): two files that change together, without an import or re-export chain between them. The section is present when the hotspot section ran on git history, and `sections` then has `change-coupling`. The section is advisory: it has no weight in the health score and never fails a run. With `--group-by`, it stays at the root of the output.

Without `--since`, change coupling and change dispersion read 12 months of history, and hotspots read 6 months. With `--since`, the three read the same window. A commit that changes more analyzed files than `health.changeCoupling.maxFilesPerCommit` does not count.

| Field | Content |
|:--|:--|
| `since` | The window that the section read, for example `"12 months"`. |
| `commits_analyzed`, `commits_skipped` | The commits that count, and the commits with too many files. |
| `total_pairs` | The pairs before `--top`. |
| `thresholds` | `max_files_per_commit`, `min_revisions`, `min_shared_revisions`, `min_degree` and `strong_degree` (0.5). |
| `pairs[]` | `path_a` (sorts first), `path_b`, `revisions_a`, `revisions_b`, `shared_revisions`, `degree` (0 to 1, two decimals) and `strong` (present and `true` at `strong_degree` or more). Sorted by `degree`, then `shared_revisions`, highest first, then by path. |

Each hotspot also has `median_files_per_commit` and `median_lines_per_commit`: the median number of analyzed files, and of added plus deleted lines, in the commits that change the file. They use the change coupling window. They are absent when the history has no commit ids, for example a churn file without `commit` fields. In a churn file, the events with the same `commit` form one commit.

The markdown format adds a `Hidden Change Coupling` table after the hotspots, when pairs exist. The compact format has one line for each pair:

```text
change-coupling:src/a.ts:src/b.ts:degree=1.00,shared=6,commits_a=6,commits_b=6,strong=true
```

### Snapshot file {#snapshots}

`--save-snapshot` writes `.fallow/snapshots/<timestamp>.json`, or the path that you give. `--trend` reads the newest file in that directory, and `--trend-from` reads one file. A snapshot has these fields:

| Field | Content |
|:--|:--|
| `snapshot_schema_version` | The version of this file format. |
| `version`, `timestamp`, `git_sha`, `git_branch`, `shallow_clone` | The fallow version, the time and the git state of the run. |
| `vital_signs`, `counts` | The [vital signs](#vital-signs) and the numbers behind them. |
| `score`, `grade`, `score_formula_version` | The health score. A trend compares scores only when the formula versions match. |
| `coverage_model` | The source of the CRAP coverage. |
| `groups` | The metrics of each group, when the run used `--group-by`. |
| `analysis_identity` | The mode of the analysis, for example `syntactic`, and its completeness. |

`--save-snapshot` computes the file scores and the hotspots, so the saved metrics are complete. A trend without a formula version, or with a different version, has no score delta. The other metrics still compare.

With `--trend`, the output has `health_trend`:

- `compared_to`: the `timestamp`, `git_sha`, `score`, `grade` and `score_formula_version` of the snapshot.
- `metrics[]`: one entry for each metric, with `name`, `label`, `previous`, `current`, `delta`, `unit` and `direction` (`improving`, `declining` or `stable`). A percentage has `previous_count` and `current_count` with `value` and `total`.
- `snapshots_loaded`, and `overall_direction`: `improving` when more metrics improve than decline, `declining` for the reverse, else `stable`.

Without a saved snapshot, the output has no `health_trend`.

#### Group trends {#group-trends}

With `--group-by`, `--trend` and `--trend-from` also compare each group with the same group key in the snapshot. Save the snapshot with the same `--group-by` mode. Each group gets `trend_status`:

- `compared`: the group has a `trend` object with the shape of `health_trend`.
- `new_group`: the snapshot has group data, but not for this key.
- `no_group_baseline`: the snapshot did not measure this group. When it has no group data for the mode, the run adds a `trend-group-baseline-unavailable` diagnostic. The project trend still works.

### Churn file {#importing-churn-from-a-non-git-vcs}

`--churn-file <PATH>` reads the change history from a JSON file, for a project without git. The file feeds `--hotspots`, `--ownership` and `--targets`. When the project also has git, the file wins.

```json
// churn.json
{
  "schema": "fallow-churn/v1",
  "events": [
    { "path": "src/foo.ts", "timestamp": 1717459200, "author": "dev@corp", "added": 10, "deleted": 5 }
  ]
}
```

| Field | Required | Content |
|:--|:--|:--|
| `path` | yes | The path from the repository root, with forward slashes. |
| `timestamp` | yes | The commit time in Unix seconds, UTC. A time more than one year in the future exits with code 2. |
| `author` | no | One stable identity for each person, for example the email. Fallow does not apply a mailmap. |
| `added`, `deleted` | yes | The changed lines. The hotspot score counts events, so the line counts are only for display. |
| `commit` | no | A commit id. The events with the same id form one commit. Change coupling and change dispersion need it. |

For git, fallow runs `git log --numstat --no-merges --no-renames --use-mailmap`. A file from another version control system must follow the same rules, else the hotspots and the ownership signals are wrong:

1. Leave out merge commits. Else the author of the merge looks like a contributor to each merged file.
2. Leave out binary files. Do not write them with `0` lines.
3. Give a renamed file under its new path only, with the real line counts. Do not write a delete of the old path.
4. Give one event for each commit and file, with `timestamp` in seconds.

Fallow ignores other fields. When your version control system records commits under a merge or CI identity, add that identity to `health.ownership.botPatterns`. Else the bus factor is 1 for each file. An empty `events` array is valid and gives no hotspots. A file that is not valid stops the run with exit code 2. The file is resolved from `--root`, and it sets the window, so fallow ignores `--since`.

The file feeds only the churn sections. `--changed-since` needs git: use `--diff-file` or `--diff-stdin` with a unified diff. `fallow audit` and `fallow impact` analyze the base revision again, so they need git.

## Exit codes

| Run | Exit code `0` when | Exit code `1` when |
|:--|:--|:--|
| `fallow health` | no finding has a `complexity-*` rule at `error` | a finding has a rule at `error`, which is the default |
| `--fail-on-issues` | the run has no finding | the run has a finding, also with a rule at `warn` |
| `--min-score N` | the score is `N` or higher | the score is lower than `N` |
| `--min-severity LEVEL` | no finding is at `LEVEL` or higher | a finding is at `LEVEL` or higher |
| `--report-only` | always | never |

With `--min-score` and `--min-severity` together, the run fails when one of them fails. With `--min-score` alone, the findings do not set the exit code. `--report-only` together with `--min-score` or `--min-severity` exits with code 2.

| Code | Meaning |
|:--|:--|
| `2` | Invalid input, for example an invalid `--mutation-report` file or `--trend-from` file. |
| `3` to `6` | With `--runtime-coverage`: the license is not valid, or the runtime coverage step failed. |

[Exit codes](/reference/exit-codes) has the meaning of each code.

## Examples

```bash
# Report the functions above the thresholds
fallow health

# Show only the 10 most complex functions, sorted by cognitive complexity
fallow health --complexity --top 10 --sort cognitive

# Use measured coverage for the CRAP scores
fallow health --coverage coverage/coverage-final.json

# Show the hotspots of the last 3 months, with their owners
fallow health --hotspots --ownership --since 3m

# Fail when the health score is lower than 70
fallow health --min-score 70

# Show the results without a failure
fallow health --report-only

# Save a snapshot, then compare a later run with it
fallow health --save-snapshot
fallow health --trend
```
