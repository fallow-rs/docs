A test keeps code in use, also when the app never runs that code. Production mode leaves the tests and the development tools out of the analysis. The report then shows the code that your users get and that nothing in the shipped app uses.

## The problem

In the example project, `src/utils/test-helpers.ts` holds a helper. Only `src/math.test.ts` imports it. The Vitest [plugin](/concepts/plugins) makes the test file an [entry point](/concepts/entry-points), so the helper is reachable. The default run does not report it.

The helper does not ship to users. Its only user is a test. To see this kind of code, fallow must leave the test out.

## Production mode

**Production mode** is a run with `--production`: fallow leaves out test files and development tools, and checks only the code that ships.

```bash
npx fallow dead-code --production
```

```text
  2 entry points detected (2 package.json)

── Unused Code ─────────────────────────────────────

● Unused files (2)
  src/utils/legacy-currency.ts
  src/utils/test-helpers.ts
  Files not reachable from any entry point
```

The default run finds 3 entry points and 1 unused file. In production mode, the test file is not an entry point, and the helper becomes an unused file.

## What production mode changes

| Behavior | Default run | Production mode |
|:--|:--|:--|
| Test files: `*.test.*`, `*.spec.*`, `*.e2e.*`, `*.e2e-spec.*`, `*.bench.*`, and the folders `__tests__/`, `test/`, `tests/`, `test-d/`, `__snapshots__/` | Analyzed | Left out |
| Story files: `*.stories.*`, `*.story.*` | Analyzed | Left out |
| Mocks and fixtures: `__mocks__/`, `__fixtures__/`, `*.fixture.*` | Analyzed | Left out |
| Config files in the project root (`*.config.*`) and hidden script files (`.*.js`, `.*.ts`, `.*.mjs`, `.*.cjs`) | Analyzed | Left out |
| Files of a `supportEntry` pattern, and support entries of a [custom plugin](/guides/custom-plugins) | Entry points | Left out |
| Files that a `package.json` script runs, for example `node scripts/seed.js` | Entry points | Entry points |
| Scripts that fallow reads for used packages | All scripts | `start`, `build`, `serve`, `preview`, `prepare`, `prepublishOnly`, the `pre` and `post` forms of `start`, `build`, `serve` and `install`, and forms such as `build:prod` |
| Unused `devDependencies` and `optionalDependencies` | Reported | Not reported |
| A dependency in `dependencies` that only tests use | Reported: move it to `devDependencies` | Reported as an unused dependency |
| A dependency that only `import type` uses | Not reported | Reported: move it to `devDependencies` |

The last row has a reason. The compiler removes each `import type`, so the shipped code does not load the package. In the example project with `date-fns` in `dependencies` and only an `import type` of it, production mode adds this group:

```text
● Type-only dependencies (consider moving to devDependencies) (1)
  date-fns
  Dependencies only used for type imports; consider moving to devDependencies
```

## Production mode for one analysis

The bare `fallow` command runs dead code, duplication and health in one run. You can turn on production mode for each analysis. Use the object form of the `production` key in the config file:

```json
// .fallowrc.json
{
  "production": {
    "deadCode": true,
    "health": false,
    "dupes": false,
    "ignore": ["scripts/**"]
  }
}
```

- `deadCode`, `health` and `dupes` turn on production mode for that analysis. They apply to the bare run, to `fallow audit`, and to the command of that analysis, for example `fallow dead-code`.
- `ignore` adds paths that production mode leaves out, for example build scripts and seed data. A run without production mode still analyzes them.
- `"production": true` turns it on for each analysis.

For one run, use `--production`, or `--production-dead-code`, `--production-health` or `--production-dupes` on the bare run and on `fallow audit`. `--no-production` turns production mode off for each analysis. A flag wins over an environment variable, and an environment variable wins over the config file. [`production`](/reference/config-files#production) in the config reference has each key, and [Environment variables](/configuration/environment) has the `FALLOW_PRODUCTION` variables.

## What production mode does not change

Production mode does not find code that the shipped app never runs. It removes the tests, so it shows code that only tests keep in use. A reachable function in shipped code stays reachable. To see which functions ran for real users, use [runtime coverage](/concepts/evidence#runtime-coverage).

Production mode uses file name patterns. A pattern can match production source, for example `src/runner/test/case.ts` matches `**/test/**`. Fallow then does not analyze that file. When shipped code imports such a file, fallow prints a warning on stderr that names the pattern and the file. Move the file out of the matched path, or turn production mode off for that analysis.
