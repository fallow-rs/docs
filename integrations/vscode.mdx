The VS Code extension shows fallow findings in your editor while you write code, so you can fix them before you commit. The fallow LSP server gives real-time diagnostics for unused code, duplication, complexity, and boundary violations.

Sidebar views and status-bar items cover more of fallow:

- project health
- security candidates
- runtime coverage
- the audit verdict for changed files
- monorepo workspace scope
- license management

<Info>
Code Lens shows a reference count above each export. Click it to peek all usages. You can see at once which exports have zero references.
</Info>

## Features

- **Real-time diagnostics** for dead-code issue types. The LSP server updates them, with no separate CLI process
- **Code Lens** with reference counts above each export (click to peek references)
- **Hover information** with export usage counts, unused status, and duplicate block locations
- **Quick-fix code actions** to remove unused exports or delete unused files
- **Refactor actions** to extract duplicates into shared functions
- **Tree views** in the sidebar with an icon for each category, an issue count badge, and a welcome view
- **Status bar** with color-coded severity, a tooltip with a breakdown, and command links
- **Diagnostic documentation links**: click a diagnostic code to open its docs page
- **Related information**: circular dependencies, duplicate exports, and code duplication diagnostics link to all related files
- **Fix preview** with a searchable Quick Pick to review fixes and go to them
- **JSON schema** for `.fallowrc.json` with autocomplete and validation
- **Auto-download** of the LSP binary
- **Getting Started walkthrough** on first install

### Codebase intelligence surfaces

The extension also shows the rest of the fallow analysis. Each one is an opt-in sidebar view or status-bar item:

- **Health view** (sidebar): the project health score and grade, the top complexity findings, and hotspot and refactoring candidates. A separate run computes it when you need it. To turn it off, use `fallow.health.enabled`.
- **Security Candidates view** (sidebar): local security candidates (`client-server-leak`, the tainted-sink CWE catalogue). These are **unverified candidates to verify**, never confirmed vulnerabilities. To turn it on, use `fallow.security.enabled`.
- **Runtime Coverage view** (sidebar): hot paths and cleanup candidates (safe-to-delete or review-required) from a loaded coverage capture.
- **Audit verdict** (status bar): pass, warn, or fail for your current change set, the same as `fallow audit`.
- **License management**: activate, view the status of, refresh, and deactivate a fallow license in the editor.
- **Monorepo workspace scope** (status bar): a picker that limits sidebar analysis to one package. The limit also applies to the Health, Security, and Audit views. The extension passes the package as `--workspace`.

## Installation

<Steps>
  <Step title="Install the extension">
    Search for "fallow" in the VS Code extensions marketplace. You can also install from the command line:

    ```bash
    code --install-extension fallow-rs.fallow-vscode
    ```
  </Step>
  <Step title="Binary resolution">
    The extension finds the binary for you. It checks these places in order:

    1. the `fallow.lspPath` setting
    2. `node_modules/.bin/` for a local devDependency (`pnpm add -D fallow`)
    3. the system PATH

    If it finds no binary, it downloads one from GitHub releases.
  </Step>
  <Step title="Getting Started walkthrough">
    After the first install, a walkthrough opens with four steps: **Run Analysis**, **Explore Results**, **Fix Issues**, and **Configure Rules**. Each step links to its command. To open it again, use the Command Palette.
  </Step>
  <Step title="Start coding">
    Open a TypeScript or JavaScript project. The extension starts and runs the analysis. Diagnostics show inline, and Code Lens annotations show above exports.
  </Step>
</Steps>

## Status bar

The status bar shows the current issue count and duplication percentage. When the LSP server completes an analysis, it sends a custom `fallow/analysisComplete` notification, and the status bar updates. No separate CLI process runs.

- **Color-coded background**: red when there are unresolved imports (errors), yellow when there are other issues (warnings), and the default color when the project is clean
- **Rich tooltip**: hover to see all issues by category, such as unused files, exports, dependencies, circular dependencies, and clone groups
- **Command links in tooltip**: Run Analysis, Auto-Fix, and Show Output

You can turn each of these status-bar items on or off:

- **Health score** segment with the project grade (toggle with `fallow.health.statusBar`)
- **Audit verdict** for the current change set: pass, warn, or fail, color-coded, with a gating-candidate count (toggle with `fallow.audit.statusBar.enabled`)
- **License indicator** showing the active license state (toggle with `fallow.license.showStatusBar`)
- **Workspace scope** picker that shows the package the analysis is limited to in a monorepo (hidden in single-package projects)

## Diagnostics

Each diagnostic has a clickable **diagnostic code**, such as `unused-export` or `unresolved-import`. The code opens its documentation page at [docs.fallow.tools](https://docs.fallow.tools).

### Related information

Some diagnostics link to the other files in the issue. To go to a related location, click it in the Problems panel.

- **Circular dependencies**: each file in the cycle is a related location, so you can follow the full cycle
- **Duplicate exports**: links to the other files that export the same name
- **Code duplication**: links to all other instances of the duplicated block

### Severity levels

| Issue type | Severity | Appearance |
|:-----------|:---------|:-----------|
| Unresolved imports | Error (red) | Red underline |
| Unused files, dependencies, circular deps, duplicate exports | Warning (yellow) | Yellow underline |
| Unused exports, types, enum/class members | Hint | Faded text (unnecessary tag) |
| Code duplication | Information (blue) | Blue underline |
| Security candidates (opt-in) | Information (blue) | Blue underline |

Security candidate diagnostics are **off by default**. They are separate from the **Security Candidates** sidebar view. They show in the editor gutter only when you raise the `security-sink` or `security-client-server-leak` rule to `warn` or `error` in your fallow config. Each one is an unverified candidate to verify, shown as information and never as a red error. The hover shows the confidence signals first and points to `fallow security --file` for the full trace. A quick-fix dismisses the candidate.

## Tree views

The sidebar groups issues by type and duplicates by clone family. Each category has its own icon:

| Category | Icon |
|:---------|:-----|
| Unused files | File |
| Unused exports | Method |
| Unused types | Interface |
| Unused dependencies | Package |
| Unused enum members | Enum member |
| Unresolved imports | Error |
| Circular dependencies | Sync |
| Duplicate exports | Files |

A **badge** on the sidebar icon shows the total issue count. Before the first analysis, a **welcome view** shows a "Run Analysis" button.

Click an item in the tree to open the file at its line and column.

## Fix preview

**Fallow: Preview Fixes (Dry Run)** opens a searchable Quick Pick with each available fix, its type, and its file location. Select an item to go to it in the editor. To apply all fixes at once, choose **Apply all fixes** at the bottom.

After it applies fixes, the extension saves the changed files, restarts the LSP server, and runs the analysis again. The diagnostics then update.

## Config autocomplete

The extension gives `.fallowrc.json` files autocomplete and validation from the published [JSON schema](https://raw.githubusercontent.com/fallow-rs/fallow/main/schema.json). You do not need to set this up.

### Adopting fallow on a legacy codebase

To hide existing issues and still flag new ones, run **Fallow: Set Baseline at HEAD** from the Command Palette. The command does three things:

- It creates the local lightweight `fallow-baseline` tag at the current commit.
- It writes `fallow.changedSince` to the workspace settings.
- It runs the analysis again.

The command asks before it replaces another active baseline setting. It does not work in multi-root workspaces. It never moves an existing tag or pushes to a remote.

To share the baseline with your team, push the tag and commit the change to `.vscode/settings.json`:

```bash
git push origin refs/tags/fallow-baseline
git add .vscode/settings.json
git commit -m "chore: set fallow baseline"
```

To apply the same rule to pull requests, use the same tag in CI with `fallow dead-code --changed-since fallow-baseline`.

<Note>
  **Shallow clones hide the baseline.** `actions/checkout@v4` defaults to `fetch-depth: 1`, and GitLab CI defaults to `GIT_DEPTH: 50`. If your baseline tag is older than the fetched history, `--changed-since` and `fallow.changedSince` fall back to the full scope with no error. The LSP logs a warning to the Fallow output channel. When you use a long-lived baseline tag, set `fetch-depth: 0` on `actions/checkout` (or `GIT_DEPTH: 0` in GitLab CI).
</Note>
