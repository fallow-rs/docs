Add the fallow GitHub Action to a workflow, so that fallow checks the code that each pull request changes and posts the result on the pull request.

## Before you start

- Add fallow to the development dependencies of the project: `npm install --save-dev fallow`. The action installs the version that `package.json` names. Without it, the action installs the latest release. The `version` input overrides both.
- Read [Run fallow in CI](/integrations/ci) to know why the check uses `fallow audit`.

## Steps

1. Create the workflow file below and commit it.
2. Open a pull request that changes code.

```yaml
# .github/workflows/fallow.yml
name: Fallow

on: pull_request

permissions:
  contents: read
  pull-requests: write
  checks: write

jobs:
  fallow:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - run: npm ci
      - uses: fallow-rs/fallow@v3
        with:
          command: audit
          comment: true
```

- `fetch-depth: 0` gives the job the history of the base branch. With a shallow clone, the action fetches the commits that it needs to find the merge base.
- `npm ci` installs the dependencies, because fallow reads the packages in `node_modules`. Use the install command of your package manager.
- `command: audit` runs the [changed-code check](/concepts/changed-code) against the base commit of the pull request.
- `comment: true` posts a sticky comment and a check named **Fallow**.

`fallow-rs/fallow@v3` selects the action. The action and the fallow version that it installs are separate.

## Check the result

The job fails on the verdict `fail` (see [Exit codes and gates](/integrations/ci#gates)). The pull request shows the comment, the check, an annotation on each finding in the **Files changed** tab, and a job summary. [What fallow posts on a pull request](/integrations/ci-comments) shows each one.

## Variants

### Report only

To see the findings before the check can block a merge, add `fail-on-issues: false`. The comment and the annotations stay. Remove the line when your team is ready for the gate.

### Full analysis on the default branch

The audit compares a change with its base, so it has nothing to check on a push to `main`. To see the full state of the project, run all analyses on a schedule. An empty `command` runs all analyses:

```yaml
# .github/workflows/fallow-main.yml
name: Fallow main

on:
  schedule:
    - cron: "0 6 * * 1"

jobs:
  fallow:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - uses: fallow-rs/fallow@v3
        with:
          fail-on-issues: false
```

### Upload SARIF to code scanning {#sarif}

Add `sarif: true` to the `with` block of the fallow step, and add `security-events: write` to the `permissions` block of the workflow. The action then uploads a SARIF file to GitHub code scanning with the category `fallow`. You do not need a separate upload step.

Code scanning is free on a public repository. A private or internal repository needs GitHub Advanced Security. Without it, the action skips the upload with a warning, and the job continues.

### Review comments on lines

Set `review-comments: true` to post one review with a comment on each finding line. A comment can hold a suggestion that you apply with one click. When this input is on, the action posts no annotations. Add `review-guidance: true` to append a collapsed "What to do" block to each comment.

### Monorepo: one job for each workspace {#monorepo}

Run one job for each [workspace](/concepts/workspaces) with a matrix. Give each job its own `review-id`, so that the jobs do not resolve the review comments of each other:

```yaml
    strategy:
      matrix:
        workspace: ["@acme/web", "@acme/api"]
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - run: npm ci
      - uses: fallow-rs/fallow@v3
        with:
          command: audit
          comment: true
          review-comments: true
          workspace: ${{ matrix.workspace }}
          review-id: ${{ matrix.workspace }}
```

When `workspace` names one workspace, the action adds the workspace name to the id of the sticky comment, so each job has its own comment. [Monorepos](/guides/monorepo) shows more ways to scope a run.

### Mutation testing {#mutation-testing}

Set `mutation: true` to run [`fallow mutation`](/cli/mutation) on the lines that the pull request adds, before the analysis. The step runs your tests, so install the dependencies first. The default time budget is `10m`. The comment and the job summary then show a "Mutation testing" section, and each survived mutant on a changed line becomes a finding. The step runs only on the `pull_request`, `push`, `schedule`, `workflow_dispatch` and `merge_group` events. It refuses `pull_request_target`, because that event gives the job the secrets of the base repository.

## Permissions and tokens {#permissions}

Each surface needs a permission of the job token. A job with a `permissions` block gets only the permissions that the block lists.

| Surface | Input | Permission |
|:--|:--|:--|
| Analysis, annotations, job summary | none | `contents: read` |
| Sticky comment | `comment: true` | `pull-requests: write` |
| Fallow check | `comment: true` | `checks: write` |
| Review comments | `review-comments: true` | `pull-requests: write` |
| SARIF upload | `sarif: true` | `security-events: write` |
| Post as the Fallow app | `branded-token` (default `auto`) | `id-token: write` |

Without `id-token: write`, the comments come from `github-actions[bot]`. With it, the action gets a short-lived token of the Fallow GitHub App, and the app posts the comments. Without `checks: write`, the action posts the comment and writes the warning `Failed to post Fallow check run`.

A pull request from a fork gets a read-only token. The comment and the review then fail. The annotations and the job summary need no write token, so they still show.

## If it fails

- **Warning "found no merge base".** The clone is too shallow. Set `fetch-depth: 0` on `actions/checkout`.
- **Warning "SARIF upload skipped".** The repository is private or internal and has no GitHub Advanced Security. Remove `sarif: true`.
- **The audit warns that it compared no changed file.** The workflow ran on a push to the default branch. Run the audit on `pull_request`, or set `changed-since` to the ref to compare with.
- **No comment on the pull request.** Check the permissions in the table above. On a fork, use the annotations and the job summary.
- **Many unused dependencies.** The job did not install the dependencies before the action.

## Reference

### Inputs {#inputs}

This table lists each input with the first sentence of its description in `action.yml`. Each input is optional. Use `args` to pass a [global option](/cli/global-flags) that has no input.

| Input | Default | Description |
|:--|:--|:--|
| `command` | none | Command to run: dead-code (unused code), architecture (import cycles, boundaries and policy rules), dupes (code duplication), health (complexity), audit (changed-code check), security (security candidates), fix (auto-remove unused code). |
| `root` | `.` | Project root directory. |
| `config` | none | Path to config file (.fallowrc.json, .fallowrc.jsonc, fallow.toml, or .fallow.toml). |
| `format` | `sarif` | Output format (human, json, sarif, compact, markdown, codeclimate, pr-comment-github, pr-comment-gitlab, review-github, review-gitlab, badge). |
| `sarif` | `false` | Upload SARIF to GitHub Code Scanning. |
| `production` | `false` | Production mode: exclude test/dev files, only analyze start/build scripts. |
| `production-dead-code` | `false` | Combined mode only: run dead-code analysis in production mode. |
| `production-health` | `false` | Combined mode only: run health analysis in production mode. |
| `production-dupes` | `false` | Combined mode only: run duplication analysis in production mode. |
| `fail-on-issues` | `true` | Exit with code 1 if issues are found. |
| `changed-since` | none | Only report issues in files changed since this git ref (requires fetch-depth: 0). |
| `auto-changed-since` | `true` | Automatically scope analysis to changed files in PR context using the base SHA (requires fetch-depth: 0). |
| `baseline` | none | Path to baseline file for comparison. |
| `save-baseline` | none | Save current results as a baseline file. |
| `fail-on-stale-baseline` | `false` | Fail the job when the loaded baseline has entries that match nothing this run. |
| `version` | none | Fallow version override. |
| `args` | none | Additional arguments to pass to fallow (space-separated). |
| `artifacts-dir` | `.` | Directory for generated action artifacts such as fallow-results.json, fallow-results.sarif, fallow-stderr.log, and fallow-analysis-args.sh. |
| `comment` | `false` | Post results as a PR comment and Fallow Check Run (requires pull-requests: write for the comment and checks: write for the check). |
| `github-token` | `${{ github.token }}` | GitHub token for PR comments and SARIF upload. |
| `branded-token` | `auto` | Post PR comments and reviews as the Fallow app (branded) when the workflow grants `permissions: id-token: write`. |
| `broker-url` | `https://api.fallow.cloud` | Base URL of the Fallow token broker used to mint the branded app token. |
| `annotations` | `true` | Emit findings as inline PR annotations via workflow commands (no Advanced Security required). |

| `summary-scope` | `all` | Sticky PR summary comment scope: 'all' (default, include project-level dependency/catalog/override findings even when their anchor line is outside the diff) or 'diff' (apply the diff filter to those findings too). |
| `diff-filter` | `added` | Diff-aware finding filter: 'added' (default, only findings on PR-added lines), 'diff_context' (added lines plus surrounding context), 'file' (any file touched by the PR), 'nofilter' (every finding). |

| `workspace` | none | Scope output to one or more workspaces. |
| `changed-workspaces` | none | Git-derived monorepo scoping: scope output to workspaces containing any file changed since REF (e.g., 'origin/main'). |

| `save-snapshot` | none | Save vital signs snapshot to .fallow/snapshots/ for trend tracking. |

### Outputs {#outputs}

| Output | Description |
|:--|:--|
| `results` | Path to JSON results file. |
| `sarif` | Path to SARIF results file. |
| `issues` | Number of issues (dead-code and architecture), clone groups (dupes), security candidates (security), introduced findings counted by the audit verdict (audit), or fixes proposed/applied (fix). |
| `verdict` | Audit verdict (pass/warn/fail). |
| `gate` | Audit gate (new-only/all) or security gate (new/newly-reachable) that was applied. |
| `changed-files-unavailable` | true when the analyze step could not enumerate PR-changed files (transient GitHub API failure, expired token, missing permissions); false on the happy path. |
| `baseline-entries` | Entries in the loaded baseline. |
| `baseline-matched` | Baseline entries that matched a current finding. |
| `baseline-stale-entries` | Baseline entries that matched nothing this run. |
| `baseline-advisory` | Which staleness advisory the baseline earned: none, partial, or zero-overlap. |
| `baseline-change-scoped` | true when the run behind these numbers analyzed only part of the project, so the baseline could not be judged. |
| `baseline-scope-reasons` | Names of the channels that narrowed the run, in the order fallow publishes them, separated by a comma and a space (for example "changed-since, production"). |
| `baseline-unrecognised` | true when the loaded file carries no key the running command writes into its own baselines, so it is a baseline another command saved or an object with nothing of that command in it. |
| `baseline-saved-by` | The command that saved the loaded baseline (dead-code, dupes or health), when baseline-unrecognised is true and the file names a writer that fallow knows. |
| `baseline-gate-trips` | true when the baseline has entries that match nothing and the run could judge it, or when the loaded file is not this command's own baseline. |
| `baseline-path` | The baseline the run compared against, as the baseline input spelled it. |
| `gates-failed` | Comma-separated names of the gates whose status is fail. |
| `gates-warned` | Comma-separated names of the gates whose status is warn. |
| `gates-skipped` | Comma-separated names of the gates that stood down without judging the run. |
| `gates-passed` | Comma-separated names of the gates that ran and passed. |
| `analysis-degraded` | true when the run recorded a diagnostic meaning its findings were computed over less than the whole project. |
| `requests-unapplied` | Comma-separated names of the narrowing requests the run could not apply, each with its reason in parentheses (for example "changed-since (git-failed)"). |
| `post-skipped-reason` | Reason the Post review comments step skipped posting (pagination_failure / none). |
| `mutation-outcome` | Outcome of the mutation step: ok, skipped, gate-failed, tool-failed, refused or interrupted. |
| `mutation-completion` | Completion of the mutation run: complete or partial. |
| `mutation-score` | Mutation score in percent, for example 87.5. |
| `mutation-results` | Path to the mutation report (fallow-mutation.json). |
| `mutation-report-rendered` | true when the installed fallow can render the mutation result (`fallow report --mutation-report`), so the PR comment, the review, the annotations and the job summary show it. false for an older fallow. |
| `dedup-lookup-failed` | true when a dedup lookup failed on the Post PR comment or Post review comments step. |
