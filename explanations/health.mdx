This page lists the findings and the metrics of `fallow health`. Each section tells in a few sentences what a value means and what to do. A section for an issue type links to its rule page, with an example, the fix and the facts.

To learn how fallow measures complexity and risk, read [Health](/analysis/health).

## Complexity metrics {#complexity-metrics}

Fallow measures each function, and the template of a component, with two numbers: the [cyclomatic complexity](#cyclomatic-complexity) and the [cognitive complexity](#cognitive-complexity). A function above a limit is a finding. A function above both limits gets the [High complexity](/rules/high-complexity) issue type. Split such a function into smaller functions, and test it first.

### Cyclomatic complexity {#cyclomatic-complexity}

The cyclomatic complexity is the number of paths through a function: 1, plus 1 for each `if`, loop, `case`, `catch`, `?:`, `&&` and `||`. Each path needs its own test. Fallow reports a function above 20 by default. Split the function, or remove branches.

Full reference: [High cyclomatic complexity](/rules/high-cyclomatic-complexity)

### Cognitive complexity {#cognitive-complexity}

The cognitive complexity estimates how hard a function is to read. Nested code counts more than flat code. Fallow reports a function above 15 by default. Flatten the nesting with early returns, or move nested blocks to helper functions.

Full reference: [High cognitive complexity](/rules/high-cognitive-complexity)

### Function names {#function-names}

A finding names the function by its declaration or by its variable, for example `load` for `const load = () => {}`. A callback gets a name from the call around it when that call has a string as first argument, for example `it("renders the empty state")`. Other callbacks are `<anonymous>` or `<arrow>`: use the path and the line of the finding to find them.

### Unit size {#unit-size}

The unit size is the length of a function in lines of code. When many functions are longer than 60 lines, the report lists them under "Large functions". Split each long function. To change the limit of 60 lines, set [`health.maxUnitSize`](/reference/config-health#health-maxunitsize).

### File length {#file-length}

The file has more lines than the limit that you set in [`health.maxFileLines`](/reference/config-health#health-maxfilelines). Each line counts, also blank lines and comments. The check is off until you set a limit. Move groups of exports to their own files.

Full reference: [Long file](/rules/long-file)

## File health scores {#file-health-scores}

`fallow health --file-scores` gives each file a score and its measurements: lines, fan-in (the files that import it), fan-out (the files that it imports), the share of unused exports and the complexity density. Fallow sorts the files with the most concern first. Start with the files at the top. Fallow leaves out files without functions, such as barrel files.

### Maintainability index {#maintainability-index-mi}

The [maintainability index](/analysis/health) (MI) is a number from 0 to 100 for one file. It goes down with more complexity for each line, more unused exports and more imports. Higher is better. The health score counts a file below 70 as low. The formula is different from the index of other tools, so do not compare the numbers.

## Untested complexity risk {#untested-complexity-risk}

Complex code without tests is the most likely place for a bug. Fallow combines the complexity of each function with its test coverage. Without coverage data, fallow estimates the coverage from the imports of the test files. Give fallow real coverage data with `--coverage` for exact scores.

### CRAP score {#crap-score}

CRAP combines the cyclomatic complexity of a function with its test coverage. A complex function without tests gets a high score. Fallow reports a score of 30 or more by default. Add tests for the function first, then make it simpler.

Full reference: [High CRAP score](/rules/high-crap-score)

## Coverage gaps {#coverage-gaps}

A coverage gap is production code that no test imports, directly or through other files. `fallow health --coverage-gaps` reports a file as [Untested file](/rules/untested-file) and an export as [Untested export](/rules/untested-export). A gap is not line coverage: a test can import a file and still skip most of its code. Add a test that imports the code, or check that fallow finds your test files.

## Runtime coverage {#runtime-coverage}

[Runtime coverage](/analysis/runtime-coverage) adds data about the functions that ran in production. Each function gets a verdict, for example "safe to delete" for a function that is unused and never ran. A function that never ran can still run at another time of year, or only on an error path. Check those cases before you delete code.

Full reference: [Runtime coverage](/rules/runtime-coverage), [Safe to delete](/rules/runtime-safe-to-delete), [Review required](/rules/runtime-review-required)

### Coverage intelligence {#coverage-intelligence}

Coverage intelligence combines runtime coverage with the static analysis, the tests, the CRAP score, the owners and the changed files. It gives one recommendation for a function: [delete](/rules/coverage-intelligence-delete), [review with an owner](/rules/coverage-intelligence-review), [refactor with care](/rules/coverage-intelligence-refactor), or [add tests before a risky change](/rules/coverage-intelligence-risky-change). Follow the rule page of the recommendation.

## Hotspot metrics {#hotspot-metrics}

A hotspot is a file that is complex and changes often. `fallow health --hotspots` reads the git history to find them. Recent commits count more than old commits. The score is relative to your project: the worst file of a clean project can still have a high score. Refactor the top hotspots first, because a fix there helps most.

## Change coupling {#change-coupling}

Two files change together in most commits, and no import connects them. A person who follows the imports does not find the second file. Make the dependency visible with an import, or move the shared logic to one file. Ignore a pair when it is a coincidence of the history. This section never fails a run.

### Change dispersion {#change-dispersion}

Each hotspot shows how far a change to the file usually spreads: the median number of files, and of lines, in the commits that change the file. A high number means that a change to this file usually needs changes in many other files.

## Refactoring targets {#refactoring-targets}

`fallow health --targets` gives a list of files to refactor, with the reason, the expected effort and the confidence. The quick wins come first. Start at the top of the list, and act on the evidence of each target, for example the unused exports or the complex functions that it names.

Full reference: [Refactoring target](/rules/refactoring-target)

## Styling findings {#styling-findings}

With `--css`, `fallow health` also checks stylesheets and CSS-in-JS. [Styling](/analysis/styling) explains this analysis. These findings are warnings by default.

### Token drift {#css-token-drift}

A styling value does not use the design tokens of the project, for example a Tailwind arbitrary value or a color near a token. Use the existing token when it is correct.

Full reference: [CSS token drift](/rules/css-token-drift)

### Duplicate declaration block {#css-duplicate-block}

The same block of declarations is in two or more rules. Merge the copies into one rule.

Full reference: [CSS duplicate block](/rules/css-duplicate-block)

### Selector complexity {#css-selector-complexity}

A rule uses an id selector, deep nesting, `!important`, or a complex selector. Make the selector simpler when you can.

Full reference: [CSS selector complexity](/rules/css-selector-complexity)

### Dead surface {#css-dead-surface}

A class, a token, a `@keyframes` rule or other styling has no use in the project. Make sure that no dynamic class name uses it, then remove it.

Full reference: [CSS dead surface](/rules/css-dead-surface)

### Broken reference {#css-broken-reference}

Code uses a class or an animation that no stylesheet of the project defines. Correct the name, unless an external stylesheet defines it.

Full reference: [CSS broken reference](/rules/css-broken-reference)

## Health score {#health-score}

The [health score](/analysis/health) is one number from 0 to 100 for the whole project. Higher is better. Fallow subtracts points for unused files and exports, complex functions, hotspots, cycles, duplication and other problems. The grade is A at 85 or more, B at 70, C at 55, D at 40 and F below 40. The JSON output lists each penalty, so you can see which problem costs the most points.
