The output of `fallow health` has a number next to each function and each file, and a link below each section. You probably followed one of these links, and you want to know what the number means and what to do now. Each section on this page answers that for one metric or one finding. A section for an issue type links to its rule page, with an example, the fix and the facts.

To learn how fallow measures complexity and risk, read [Health](/analysis/health).

## Complexity metrics {#complexity-metrics}

In the demo project, `fallow health` reports one function:

```text
● High complexity functions (1)
  src/services/customers.ts
    :9 classifyCustomer CRITICAL
          23 ! cyclomatic   32 ! cognitive   39 lines
         552.0 ! CRAP
```

Fallow measures each function, and the template of a component, with two numbers: the [cyclomatic complexity](#cyclomatic-complexity) and the [cognitive complexity](#cognitive-complexity). A function above a limit is a finding, and `!` marks each limit that it passes. A function above both limits, such as `classifyCustomer`, gets the [High complexity](/rules/high-complexity) issue type. Test such a function first, then split it into smaller functions.

### Cyclomatic complexity {#cyclomatic-complexity}

The cyclomatic complexity is the number of paths through a function: 1, plus 1 for each `if`, loop, `case`, `catch`, `?:`, `&&`, `||`, `??` and `?.`. Each path needs its own test, so `classifyCustomer` has 23 paths to test. Fallow reports a function above 20 by default. Split the function, or remove branches.

Full reference: [High cyclomatic complexity](/rules/high-cyclomatic-complexity)

### Cognitive complexity {#cognitive-complexity}

The cognitive complexity estimates how hard a function is to read. Nested code counts more than flat code. `classifyCustomer` has `if` blocks inside a loop inside an `if`, so it gets 32, more than its 23 paths. Fallow reports a function above 15 by default. Flatten the nesting with early returns, or move nested blocks to helper functions.

Full reference: [High cognitive complexity](/rules/high-cognitive-complexity)

### Function names {#function-names}

A finding names the function by its declaration or by its variable, for example `load` for `const load = () => {}`. An anonymous `export default` is `default`. A callback gets a name from the call around it when that call has a string as first argument:

| Code | Finding `name` |
|:--|:--|
| `Effect.fn("Users.create")(function* () {...})` | `Users.create` |
| `Command.make("setup", {...}, (args) => ...)` | `Command.make("setup")` |
| `api.group().handle("github", (req) => ...)` | `handle("github")` |
| `it("renders the empty state", () => ...)` | `it("renders the empty state")` |
| `const load = (id) => Effect.gen(function* () {...})` | `load`, for the arrow and for the generator |

Fallow keeps the first 40 characters of a long string. A generator takes the name of the function that returns it, also through `.pipe(...)`. Other callbacks are `<anonymous>` or `<arrow>`: use the path and the line of the finding to find them. The name does not change the score or the coverage match.

In [Effect](https://effect.website) code, the combinators are calls, so they add nothing: `pipe(...)`, `Effect.catchTag(...)`, `Effect.if(...)`, `Match.when(...)`, and `yield*` in `Effect.gen`. Each callback is its own unit, and its nesting starts at zero.

### Templates and components {#templates-and-components}

A component template is a unit of its own, with the name `<template>`. For an Angular component, fallow reads an external `templateUrl` file and an inline `@Component({ template })` literal. When a class method of the component has a finding, fallow also adds a `<component>` finding. Its values are the values of the worst class method plus the values of the template. The ranking and `--targets` use these totals, and `component_rollup` has the class part and the template part.

- Fix a `<template>` finding with child components, or move derived data to the class as computed signals.
- Fix the larger part of a `<component>` finding first.
- A template file gets its CRAP estimate from its component class: `coverage_source` is `estimated_component_inherited`, and `inherited_from` names the class file. Add tests to the class.
- To hide an inline template and the `<component>` finding, put `// fallow-ignore-next-line complexity` above the decorator or above the worst class method. To hide an external template, put `<!-- fallow-ignore-file complexity -->` at the top of the template.

Full reference: [High complexity](/rules/high-complexity)

### Unit size {#unit-size}

The unit size is the length of a function in lines of code. When many functions are longer than 60 lines, the report lists them under "Large functions". Split each long function. To change the limit of 60 lines, set [`health.maxUnitSize`](/reference/config-health#health-maxunitsize).

### File length {#file-length}

The file has more lines than the limit that you set in [`health.maxFileLines`](/reference/config-health#health-maxfilelines). Each line counts, also blank lines and comments. The check is off until you set a limit. Move groups of exports to their own files.

Full reference: [Long file](/rules/long-file)

## File health scores {#file-health-scores}

The complexity metrics rate one function. A file can be hard to change for other reasons too, for example many imports or many unused exports. `fallow health --file-scores` gives each file a score and its measurements. The measurements are the lines, the fan-in (the files that import it), fan-out (the files that it imports), the share of unused exports and the complexity density. Fallow sorts the files with the most concern first, so start with the files at the top. Fallow leaves out files without functions, such as barrel files.

### Maintainability index {#maintainability-index-mi}

The [maintainability index](/analysis/health) (MI) is a number from 0 to 100 for one file. It goes down with more complexity for each line, more unused exports and more imports. Higher is better. In the demo project, `src/utils/legacy-currency.ts` has the MI 78.8, lower than most files, because each of its exports is unused. The health score counts a file below 70 as low. The formula is different from the index of other tools, so do not compare the numbers. [The MI formula](/cli/health#maintainability-index-formula) gives each coefficient.

## Untested complexity risk {#untested-complexity-risk}

Complexity tells you how hard a function is. It does not tell you if tests protect the function, and complex code without tests is the most likely place for a bug. So fallow combines the complexity of each function with its test coverage. Without coverage data, fallow estimates the coverage from the imports of the test files, and the report says so in a hint line:

```text
  No coverage file found, so CRAP scores are a static estimate. Pass `--coverage <coverage-final.json>` for measured scores, or raise `health.maxCrap`.
```

This line is not an error. Give fallow real coverage data with `--coverage` for exact scores.

### CRAP score {#crap-score}

CRAP combines the cyclomatic complexity of a function with its test coverage. A complex function without tests gets a high score: `classifyCustomer` has 23 paths and no test, so its estimate is 552.0. Fallow reports a score of 30 or more by default. Add tests for the function first, then make it simpler. [CRAP](/cli/health#crap-formula) gives the formula and the action of each case, and [Severity bands](/cli/health#severity-bands) gives the bands.

Full reference: [High CRAP score](/rules/high-crap-score)

## Coverage gaps {#coverage-gaps}

A coverage gap asks a simpler question than CRAP: does any test import the code at all? A coverage gap is production code that no test imports, directly or through other files. `fallow health --coverage-gaps` reports a file as [Untested file](/rules/untested-file) and an export as [Untested export](/rules/untested-export). A gap is not line coverage: a test can import a file and still skip most of its code. Add a test that imports the code, or check that fallow finds your test files.

## Runtime coverage {#runtime-coverage}

Test coverage shows the code that your tests run. [Runtime coverage](/analysis/runtime-coverage) adds data about the functions that ran in production. Each function gets a verdict, for example "safe to delete" for a function that is unused and never ran. A function that never ran can still run at another time of year, or only on an error path. Check those cases before you delete code.

Full reference: [Runtime coverage](/rules/runtime-coverage), [Safe to delete](/rules/runtime-safe-to-delete), [Review required](/rules/runtime-review-required), [Low traffic](/rules/runtime-low-traffic), [Coverage unavailable](/rules/runtime-coverage-unavailable)

### Evidence fields {#coverage-evidence}

Each entry of `runtime_coverage.findings` has an `evidence` object with the facts behind its verdict:

| Field | Values |
|:--|:--|
| `static_status` | `used`: the module graph reaches the function. `unused`: static analysis finds it unused. |
| `test_coverage` | `covered`: the local tests run the function. Else `not_covered`. |
| `v8_tracking` | `tracked`: V8 saw the function in the capture window. Else `untracked`. |
| `test_only_reference` | `true`: the production graph does not reach the function, but a test, spec, story, fixture or benchmark file uses it. The verdict is then never `safe_to_delete`. `false`: fallow compared both graphs and found no such use. Absent when the run had no production filter. |

### Coverage intelligence {#coverage-intelligence}

Coverage intelligence combines runtime coverage with the static analysis, the tests, the CRAP score, the owners and the changed files. It gives one recommendation for a function: [delete](/rules/coverage-intelligence-delete), [review with an owner](/rules/coverage-intelligence-review), [refactor with care](/rules/coverage-intelligence-refactor), or [add tests before a risky change](/rules/coverage-intelligence-risky-change). Follow the rule page of the recommendation.

## Hotspot metrics {#hotspot-metrics}

A complex file costs you time only when you change it, so the metrics above need the change history too. A hotspot is a file that is complex and changes often. `fallow health --hotspots` reads the git history to find them. Recent commits count more than old commits. The score is relative to your project: the worst file of a clean project can still have a high score. Refactor the top hotspots first, because a fix there helps most. [Hotspots](/cli/health#hotspots) gives the formula, the trend rules and the fields.

### Ownership markers {#ownership-markers}

With `--ownership`, the human output adds a summary line above the hotspots, for example `9/10 hotspots depend on a single recent contributor · top authors: alice (6), bob (4)`. Each hotspot row has a `bus=` marker:

- Red and bold, when the top contributor has 90 percent or more of the weighted commits, or when the bus factor is 1 and the trend is `Accelerating`. The marker then says `(sole author)` for a share of 100 percent, else `(at risk)`.
- Yellow, for a bus factor of 1 in other cases.
- Dimmed, for a bus factor of 2 or more.

### Test paths {#test-paths}

Hotspots keep test files in the ranking, because the work on tests is real work. The human output tags them `[test]`, and the JSON output has `is_test_path: true`. A path is a test path when one of these is true:

- A directory of the path is `test`, `tests`, `__tests__`, `__test__`, `e2e`, `test-d`, `__mocks__`, `__fixtures__`, `fixtures` or `__snapshots__`.
- A directory is `spec` or `specs` at a test root: the project root, a package root, or a directory next to a `src` or `lib` directory.
- The file name has `.test.`, `.test-d.`, `.spec.`, `.e2e.`, `.e2e-spec.` or `.fixture.`.
- The file name has `.cy.`, and the file is a script below a `cypress` directory, or below a directory that holds a Cypress config or a `cypress` directory.

The match ignores ASCII case. `fallow audit` and `fallow similar-code inspect` use the same definition.

## Change coupling {#change-coupling}

Two files often change in the same commits, and no import connects them. Fallow reports a pair when the two files share at least 5 commits, and the shared commits are at least 30 percent of the mean commit count of the two files. A person who follows the imports does not find the second file. Make the dependency visible with an import, or move the shared logic to one file. Ignore a pair when it is a coincidence of the history. This section never fails a run. [Change coupling](/cli/health#change-coupling) gives the window and the fields.

### Change dispersion {#change-dispersion}

Each hotspot shows how far a change to the file usually spreads: the median number of files, and of lines, in the commits that change the file. A high number means that a change to this file usually needs changes in many other files.

## Shallow directories {#shallow-directories}

A directory is a module: files outside it use its interface items, and it keeps the rest inside. A deep directory hides much code behind a small interface. A shallow directory shows almost all that it has, so each caller must learn many names and gets little in return. `fallow health --shallow-directories` reports a directory when files outside it use at least as many of its interface items as it keeps inside, and it shows at least `health.shallowDirectories.minInterface` items (default 8).

An interface item is a module-scope function or an exported class with a method. Types, constants, enums and UI components are no items, because a wide set of them is usually on purpose. An export that a package entry re-exports is public API, so it is no item either. Only runtime imports from files that are not tests or stories count as use. A barrel `index` file is the face of its directory: a caller that imports through it counts for the file that declares the item.

Some directories pass the counts but do not act as one module. Fallow does not report them, and their parent directory counts their items:

- a catalog, where the shown items come about one per file (one hook, model or task per file), or all from one file;
- a family, where at least 30 percent of the shown functions have one parameter list, for example a set of editor commands;
- low reuse, where the shown items have fewer than 2 outside users on average.

A reported directory claims its items, so one wide child does not make each of its parents shallow too.

The signal finds junk-drawer `utils`, `lib` and `shared` directories best. A cohesive set of same-role functions with different parameter lists, such as an i18n helper set, can still report: in a check on public projects, about half of the findings were real. Move the logic behind fewer items, split the directory by the concern of its callers, or merge a helper into its only caller. To keep the interface narrow after the fix, see [Keep a module deep](/guides/keep-a-module-deep). When the width is on purpose, add the directory to `health.shallowDirectories.ignore`. [Fields](#shallow-directory-fields) lists the JSON fields.

### Fields {#shallow-directory-fields}

| Field | Description |
|:--|:--|
| `min_interface` | The `health.shallowDirectories.minInterface` value of the run. |
| `total` | The shallow directories before `--top`. |
| `directories[].path` | The directory, relative to the project root. |
| `directories[].anchor_file` | The `index` file of the directory, else its first source file. SARIF and CodeClimate report the finding on this file. |
| `directories[].shown_count`, `shown_files` | The interface items that files outside the directory use, and the files of the directory that declare them. |
| `directories[].hidden_count` | The functions and classes that no outside file uses. |
| `directories[].items` | At most 7 shown items, the most used first: `name`, `path`, `line`, `kind` (`function` or `class`), `outside_files`, and `members` for a class. `is_default` marks a default export. |
| `directories[].more_items` | The shown items that `items` leaves out. |
| `directories[].actions` | `narrow-interface`, and `ignore-directory`. Add its `value`, an escaped glob of the directory, to its `config_key` list (`health.shallowDirectories.ignore`) to hide the directory. |

SARIF has the rule `fallow/shallow-directory` at level `note`. CodeClimate has the check `fallow/shallow-directory` at severity `info`. Both fingerprints read the directory, so a new anchor file keeps them. The markdown format adds a `Shallow Directories` table, and the compact format has one line for each directory:

```text
shallow-directory:src/utils/index.ts:dir=src/utils,shown=8,hidden=2,files=2
```

Full reference: [Shallow directory](/rules/shallow-directory)

## Refactoring targets {#refactoring-targets}

`fallow health --targets` gives a list of files to refactor, with the reason, the expected effort and the confidence. The quick wins come first. Start at the top of the list, and act on the evidence of each target, for example the unused exports or the complex functions that it names. [Refactoring targets](/cli/health#refactoring-targets) gives the priority formula and the rule of each category.

Full reference: [Refactoring target](/rules/refactoring-target)

## Styling findings {#styling-findings}

With `--css`, `fallow health` also checks stylesheets and CSS-in-JS. [Styling](/analysis/styling) explains this analysis. These findings are warnings by default.

### Token drift {#css-token-drift}

A styling value does not use the design tokens of the project, for example a Tailwind arbitrary value or a color near a token. Use the existing token when it is correct.

Full reference: [CSS token drift](/rules/css-token-drift)

### Duplicate declaration block {#css-duplicate-block}

The same block of declarations is in two or more rules. Merge the copies into one rule.

Full reference: [CSS duplicate block](/rules/css-duplicate-block)

### Selector complexity {#css-selector-complexity}

A rule uses an id selector, deep nesting, `!important`, or a complex selector. Make the selector simpler when you can.

Full reference: [CSS selector complexity](/rules/css-selector-complexity)

### Dead surface {#css-dead-surface}

A class, a token, a `@keyframes` rule or other styling has no use in the project. Make sure that no dynamic class name uses it, then remove it.

Full reference: [CSS dead surface](/rules/css-dead-surface)

### Broken reference {#css-broken-reference}

Code uses a class or an animation that no stylesheet of the project defines. Correct the name, unless an external stylesheet defines it.

Full reference: [CSS broken reference](/rules/css-broken-reference)

### CSS analytics {#css-analytics}

With `--css`, the JSON output of `fallow health` has `css_analytics`, `styling_findings` and `styling_health`.

Each cleanup candidate in `css_analytics` is a list. A list is absent when it is empty.

| Field | Content |
|:--|:--|
| `unreferenced_css_classes` | A class of a plain stylesheet that no `class` or `className` of the project markup uses. |
| `unresolved_class_references` | A class in markup that is one edit away from a defined class, probably a typo. |
| `undefined_keyframes` | An animation that names a `@keyframes` block that no file defines. |
| `unused_font_faces` | A `@font-face` family that no rule uses. |
| `unused_theme_tokens` | A Tailwind v4 `@theme` token whose utility no file uses. |
| `token_consumers` | The users of each design token. See [Token consumers](#token-consumers). |
| `font_size_unit_mix` | `font-size` values in more than one unit, for example `px` and `rem`. |

A `@theme` token counts as used through its utility (`bg-brand` for `--color-brand`), a `var(--token)` read, an `@apply` body, an arbitrary value such as `rounded-[--radius-card]`, or a reference from another `@theme` token. The token check runs only for a Tailwind v4 project: a `tailwindcss` dependency and a `@theme` block. It reports nothing when Tailwind plugins or published CSS can use the tokens.

A Sass or Less animation value can hold a variable, for example `animation: #{$name} 1s`. Such a value can name each `@keyframes` block of a Sass or Less source, so fallow does not report these blocks as unused. `css_analytics.summary.keyframes_unchecked` counts them, and the human output shows them as `not checked`. A `@keyframes` block in plain CSS is always checked.

A class prefix before a `{{` expression, as in `grid--{{ columns }}`, uses each class that starts with `grid--`. Fallow reads server templates as class references. [`markupExtensions`](/reference/config-files#markupextensions) lists the template extensions.

### Token consumers {#token-consumers}

`token_consumers` is a reverse index of the design tokens. Each entry has these fields:

| Field | Content |
|:--|:--|
| `token` | A Tailwind token with its `--` prefix (`--color-brand`), or the path of a CSS-in-JS token (`vars.color.primary`). |
| `namespace` | The Tailwind namespace (`color`), or the export binding of a CSS-in-JS token set (`vars`). |
| `definition_path`, `definition_line` | The place of the definition. |
| `consumer_count` | The number of uses. |
| `consumers` | A sample of up to 20 uses, each with `path`, `line` and `kind`. |

| `kind` | Use |
|:--|:--|
| `utility` | A class that ends in `-<name>`, such as `bg-brand`. |
| `apply` | A class in an `@apply` body. |
| `css-var` | A `var(--token)` read outside `@theme`. |
| `theme-var` | A `var(--token)` read in another `@theme` token. |
| `js-member` | A member access on a StyleX or vanilla-extract token binding, also through an import. |
| `js-call` | A PandaCSS `token(...)` call, or a StyleX `createTheme` call. |

CSS-in-JS entries cover StyleX `defineVars`, vanilla-extract `createTheme`, `createThemeContract` and `createGlobalTheme`, PandaCSS `defineTokens`, styled-components and Emotion. Fallow resolves each import to the file of the definition, so a `vars` binding of another module does not count.

`consumer_count` is a lower bound. Fallow cannot see a computed class name such as `bg-${color}`, an import that it cannot resolve, or computed token access. A count of `0` is a reason to investigate, not proof that you can delete the token. A run on a part of the project has no `token_consumers`.

### Styling score {#styling-score}

`styling_health` has `score` (0 to 100), `grade`, `formula_version`, `penalties`, `confidence` and `confidence_reason`. The score starts at 100, and fallow subtracts five penalties:

| Penalty | Measures | Maximum |
|:--|:--|:--|
| `duplication` | The removable declarations in copied declaration blocks. | 20 |
| `dead_surface` | The unused `@theme` tokens as a share of all tokens, plus the unused classes, `@property` and `@layer` rules and `@font-face` families as a share of all declarations. | 20 |
| `broken_references` | The unresolved class references and the undefined `@keyframes`. | 15 |
| `token_erosion` | Mixed `font-size` units, Tailwind arbitrary values, and the hardcoded `box-shadow`, `border-radius` and `line-height` values above a small set for each property. A `var(--*)` value does not count. | 10 |
| `structural` | `!important` above a small share, and deep nesting. | 10 |

`confidence` is `low` when the score comes from few declarations, or from mostly compile-time CSS-in-JS. `confidence_reason` then says why, and the human output puts `~` before the score. Confidence does not change the score. The styling score never changes an exit code, a badge or the health score.

`formula_version` (`3`) is separate from the formula version of the health score. When you compare styling scores over time, compare only scores with the same `formula_version`.

## Health score {#health-score}

The sections above rate functions and files. The [health score](/analysis/health) is one number from 0 to 100 for the whole project. Higher is better. Fallow subtracts points for unused files and exports, complex functions, hotspots, cycles, duplication and other problems. The grade is A at 85 or more, B at 70, C at 55, D at 40 and F below 40.

The demo project gets a low score, and the first lines of the report show why:

```text
● Health score: 61 C
  Deductions: unused deps -25.0 · duplication -10.0 · dead exports -2.9 · dead files -1.3
```

Fallow counts the unused dependencies for each 1,000 files, so in a small project one package can cost the maximum of 25 points. The demo project has 16 files and one unused dependency, `left-pad`. The JSON output lists each penalty, so you can see which problem costs the most points.
