You run a linter already, and you want to know what fallow adds. A linter reads one file and checks it against rules. Fallow reads the whole project: it starts at the [entry points](/concepts/entry-points) and follows each import. Some problems exist only between files, so a check of one file at a time cannot find them. That is why you use a linter and fallow together.

## The problem

In the demo project, `src/services/orders.ts` exports `cancelOrder`, and no file imports it. The export looks correct in its own file, so a linter that reads only that file sees nothing wrong. To know that nothing imports `cancelOrder`, a tool must read each file that could import it. The same is true for `src/utils/legacy-currency.ts`, which no code reaches, and for `left-pad`, a package in `package.json` that no file imports.

## Which tool finds which problem

The "Needs" column gives the reason for each row. A tool that reads one file at a time finds only the problems that need one file.

| Problem | Needs | Tool |
|:--|:--|:--|
| A variable that the file never uses | One file | Linter |
| A missing dependency of a React hook | One file | Linter |
| `==` where `===` is meant | One file | Linter |
| Inconsistent code style | One file | Formatter |
| An export that no file imports | The whole project | Fallow |
| A file that no entry point reaches | The whole project | Fallow |
| A package in `package.json` that no file imports | The whole project | Fallow |
| An import of a package that `package.json` does not declare | The whole project | Fallow, or a linter with a plugin |
| A circular import chain through many files | The whole project | Fallow, or a linter with a plugin |
| An import across an architecture boundary | The whole project | Fallow, or a linter with a plugin |
| A block of code that is copied in several files | The whole project | Fallow |
| A complex function | One function | Fallow, or a linter |
| A complex file that changes often | The project and its git history | Fallow |
| New unused code in a pull request | The project and the change | Fallow, with a [changed-code check](/concepts/changed-code) |

Some linter plugins also build the import graph, for example to find cycles. Fallow builds the graph once for each run and uses it for all of its checks.

## How fallow checks the project

Each row with "The whole project" needs one view of all files and their imports. Fallow parses each file once and builds a graph of the imports of the project. It follows re-export chains through [barrel files](/concepts/entry-points), and it resolves the path aliases of `tsconfig.json`. Its [plugins](/concepts/plugins) find the entry points of frameworks, such as the pages of Next.js. Then it reads the graph:

- An export that no reachable file imports is an [unused export](/rules/unused-export), such as `cancelOrder`.
- A file that no entry point reaches is an [unused file](/rules/unused-file), such as `src/utils/legacy-currency.ts`.
- A loop in the graph is a [circular dependency](/rules/circular-dependency). Fallow finds loops of each length, through `import` and `require()`.
- An import between two zones of your [boundaries](/configuration/boundaries) config, that the rules do not allow, is a [boundary violation](/rules/boundary-violation). For an import through a barrel file, fallow checks the zone of the file that declares the name.

## What fallow cannot do

The graph shows how the files use each other. It does not show what happens inside one file, and it does not know the code outside the project:

- Fallow does not check style, scope or the logic inside one file. Keep your linter for that.
- An export that code outside the project imports, such as the public API of a library, looks unused. Mark it with `/** @public */`, or make its file an entry point.
- Some cycles are intentional, for example in a framework with dependency injection. Fallow cannot tell an intentional cycle from a mistake. Accept a known cycle in [`circularDependencies.allow`](/reference/config-architecture#circulardependencies-allow).

## Run both in CI

Each tool finds problems that the other does not, so CI needs both. Run the formatter, the linter and fallow as separate jobs. They do not depend on each other, so they can run in parallel. [Run fallow in CI](/integrations/ci) shows how to add fallow to a pipeline. To start on a project with many findings, save a [baseline](/guides/baselines), so that CI fails only on new findings.
