Linters check files. TypeScript checks types. Fallow checks the codebase, so it finds project-level issues that a linter misses. Use this page to see which tool finds which issue, and how to run them together in CI.

Each tool answers a different question:

- **Formatter**: "Does this file look consistent?"
- **Linter**: "Does this file follow the rules?"
- **Fallow**: "Is this codebase structurally sound?"

Fallow analyzes the module graph of the whole project. The analysis is static by default. Teams that want production evidence for dead code decisions can add the optional runtime intelligence layer (see [static vs runtime](/explanations/static-vs-runtime)).

## Three pillars of code quality

<CardGroup cols={3}>
  <Card title="Formatter" icon="paintbrush">
    Prettier, Biome, dprint. Makes formatting consistent in all files, for example indentation, quotes, and trailing commas. Works on one file at a time and does not know about imports or project structure.
  </Card>
  <Card title="Linter" icon="list-check">
    ESLint, Biome, oxlint. Enforces coding rules and finds local code smells, for example undefined variables, missing dependencies in `useEffect`, and suspicious patterns. Works on one file at a time, with optional type context from `tsc`.
  </Card>
  <Card title="Codebase intelligence" icon="diagram-project">
    Fallow. Finds issues that exist only at the project level, for example unused files, orphaned exports, circular dependencies, and dependency graph violations. To find them, fallow builds and walks the full module graph.
  </Card>
</CardGroup>

**Linters read files.** Fallow **builds the import graph** of the whole project and checks the relationships between modules.

## What each tool finds

| Issue | ESLint | Biome | oxlint | Fallow |
|:------|:------:|:-----:|:------:|:------:|
| Unused variable within a file | Yes | Yes | Yes | No |
| Missing `useEffect` dependency | Yes | Yes | Yes | No |
| Suspicious `==` vs `===` | Yes | Yes | Yes | No |
| Code style violations | Yes | Yes | Yes | No |
| Exported symbol never imported | Slow \[1\] | No | No | Yes |
| File not reachable from entry point | No | No | No | Yes |
| Circular import chain across N files | Slow \[2\] | Yes \[2\] | Yes \[2\] | Yes |
| Package in deps but never imported | No \[3\] | No \[3\] | No | Yes |
| Import of package not in package.json | Yes | Yes | No | Yes |
| Architecture boundary enforcement | Yes \[4\] | Limited \[4\] | No | Yes |
| Duplicated logic blocks across modules | No | No | No | Yes |
| Per-function cyclomatic complexity | Yes | No | Yes | Yes |
| Per-function cognitive complexity | No | Yes | No | Yes |
| Complexity + git churn hotspot correlation | No | No | No | Yes |

**\[1\] Unused exports.** `eslint-plugin-import/no-unused-modules` rebuilds the full import graph on every lint run. On projects with 20-30K LOC, this adds ~320 seconds to total lint time ([#1487](https://github.com/import-js/eslint-plugin-import/issues/1487)). The rule gives incorrect results with `import { name as alias }` ([#1339](https://github.com/import-js/eslint-plugin-import/issues/1339)), and it does not follow barrel file re-export chains. Biome and oxlint have no equivalent rule.

**\[2\] Circular imports.**

- ESLint: `eslint-plugin-import/no-cycle` takes 45-305 seconds on large projects and has known OOM failures ([#2348](https://github.com/import-js/eslint-plugin-import/issues/2348), [#2076](https://github.com/import-js/eslint-plugin-import/issues/2076)). Teams often set `maxDepth: 1` to keep it fast, and then miss longer cycles. The rule covers only ES `import`, not `require()`.
- Biome v2: `noImportCycles` is written in Rust and is graph-aware, but Biome documents it as computationally expensive.
- oxlint: `no-cycle` is written in Rust and is faster than the JS version.
- Fallow: builds and caches the graph once, has no depth cap, and covers both `import` and `require()`.

**\[3\] Unused vs unlisted deps.** `no-extraneous-dependencies` (ESLint) and `noUndeclaredDependencies` (Biome) find imports of packages that are missing from `package.json`. That is the opposite problem. No linter finds packages that `package.json` lists but no file imports. Fallow finds both.

**\[4\] Boundaries.**

- ESLint: `eslint-plugin-boundaries` enforces import rules between element types with capture groups and templates. `no-restricted-paths` enforces directory-level restrictions, but you must list every forbidden pair. Neither rule follows re-export chains, so an import through a barrel file can bypass a boundary.
- Biome: `noRestrictedImports` accepts plain string paths only. It has no globs or patterns.
- oxlint: has no boundary rules.
- Fallow: has [zone presets](/configuration/boundaries) (`bulletproof`, `layered`, `hexagonal`, `feature-sliced`) and follows re-export chains.

## Detailed comparison

### Unused exports

Fallow builds a persistent module graph, resolves re-export chains iteratively, and resolves TypeScript path aliases.

<Info>
In a library, external code imports your public API exports on purpose. To stop fallow from flagging them, mark them with the `/** @public */` JSDoc tag (or `@internal`, `@beta`, `@alpha`), or configure your [entry points](/configuration/overview#entry).
</Info>

```bash
fallow dead-code --unused-exports
```

```text
● Unused exports (3)
  src/components/Card/index.ts
    :1  CardFooter
  src/utils/format.ts
    :14 formatCurrency
    :28 formatDate
```

### Unused files

`no-unused-modules` finds exports with no importers. It does not find files that no file imports. A file with no exports and no importers does not trigger any ESLint rule. Examples are an orphaned utility, or the leftover test file of a deleted component.

To find unreachable files, a tool must start from the entry points and walk the full import graph. ESLint has no concept of entry points. It lints files, and it does not walk a graph from its roots. Fallow reads entry points from `package.json` fields and framework conventions (Next.js pages, Vite entry, etc.). Then it marks every file that those roots do not reach.

### Circular dependencies

```text
src/auth.ts → src/user.ts → src/permissions.ts → src/auth.ts
```

Some cycles are not bugs. Dependency injection frameworks (NestJS, InversifyJS) create intentional cycles. To suppress one, use `// fallow-ignore-next-line circular-dependency`, the same way you use an ESLint disable comment. No tool automatically tells an intentional cycle from an accidental one.

### Architecture boundary violations

Fallow follows re-export chains when it checks boundaries. If `shared/index.ts` re-exports a symbol from `core/`, fallow treats an import of that symbol as an import from `core/`, not `shared/`. [Zone presets](/configuration/boundaries) (`bulletproof`, `layered`, `hexagonal`, `feature-sliced`) cover common architecture patterns. Zones use glob patterns. You write rules as allowlists ("this zone can only import from these zones"), so you do not have to list every forbidden path.

```jsonc
{
  "boundaries": {
    "zones": [
      { "name": "ui", "include": ["src/components/**"] },
      { "name": "api", "include": ["src/api/**"] }
    ],
    "rules": [
      { "from": "ui", "disallow": ["api"] }
    ]
  }
}
```

## Recommended CI pipeline

Run the formatter, the linter, and fallow in parallel. Some linter plugins (`no-cycle`, `no-unused-modules`) find a subset of the issues that fallow finds. If you already use those plugins, fallow finds the same issues faster. It also finds the issues that linters cannot find: unused files, unused deps, duplication, and churn hotspots. If you do not use those plugins, fallow covers all of these in one pass:

```yaml
jobs:
  format:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx prettier --check .          # or: npx biome check --only=format

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx eslint .                    # or: npx biome lint / npx oxlint

  analyze:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: fallow-rs/fallow@v3
```

<Info>
The fallow GitHub Action automatically uploads SARIF results to GitHub Code Scanning, so you get inline annotations on PR diffs. Linter results usually show up as separate status checks or linter-review actions. For GitLab CI and other runners, see [CI integration](/integrations/ci).
</Info>

## What to use when

| Situation | Tool |
|:----------|:-----|
| Variable used in wrong scope | Linter |
| Missing React hook dependency | Linter |
| Inconsistent code style | Formatter |
| Exported function nobody imports | Fallow |
| File that was left behind after a refactor | Fallow |
| `lodash` in `package.json` but never imported | Fallow |
| 8-file circular dependency chain | Fallow |
| Feature module importing directly from core internals | Fallow |
| Growing codebase, want to prevent new dead code in PRs | Fallow (`--changed-since`) |
| Library export consumed by external consumers | Fallow (configure [entry points](/configuration/overview#entry) or `/** @public */` / `@internal` / `@beta` / `@alpha`) |

<Tip>
If your codebase already has unused exports and files, use `--save-baseline` to save the current issues. Then run CI with `--baseline` so that it fails only on new issues. For incremental adoption, see the [CI integration guide](/integrations/ci).
</Tip>
