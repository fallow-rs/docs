## What it reports

Class member is never referenced.

[Dead code](/analysis/dead-code) explains how fallow finds it.

## Why it matters

No code calls the member, but it stays in the public shape of the class. People keep it in step during refactors, and readers assume that some caller depends on it.

## Example

class Parser has a public parseLegacy method that is never called in the project.

```ts title="src/index.ts"
import { Parser } from "./parser";

const parser = new Parser();
console.log(parser.parse("ORDER-42"));
```

```ts title="src/parser.ts"
export class Parser {
  parse(input: string): number {
    return Number(input.replace("ORDER-", ""));
  }

  parseLegacy(input: string): number {
    return Number(input.slice(3));
  }
}
```

## Fix

Remove or privatize the member. For reflection/framework lifecycle hooks, configure or suppress the intentional entry point.

## When to keep the code

- A framework calls the member at run time. Add its name to [`usedClassMembers`](/reference/config-dead-code#usedclassmembers).
- A scoped `usedClassMembers` rule with `"extends": "Base"` applies to the subclasses of `Base`, not to `Base` itself. No config key selects one class by its name. To keep all members of one class, put `// fallow-ignore-file unused-class-member` in the file of that class, or [suppress](/guides/suppress) each member.

## Notes

- The rule checks public members. A `private` member is not checked, and [Unused protected class members](/rules/unused-protected-class-member) checks `protected` members.
- A use through `this` inside the class counts as a use.
- A class that implements an interface keeps each required member of the interface. This includes the required members that the interface gets from each interface that it extends, also from another module. TypeScript rejects the class without them.
- A key of the annotation object in `makeObservable(this, {...})` or `makeAutoObservable(this, {...})` from `mobx` counts as a use of the member with that name, because MobX reads the member when the constructor runs. A key with the value `false` does not count, because it excludes the member from MobX.
- Fallow does not report a member with a decorator, because a framework uses it at run time. A Lit `@state()` property is checked. To check members with some decorators, list those decorators in [`ignoreDecorators`](/reference/config-dead-code#ignoredecorators).
- Fallow does not report the lifecycle methods of React, Angular and custom elements. A [plugin](/concepts/plugins) can declare the lifecycle methods that its framework calls, and fallow counts them as used while the plugin is on. For example, the Ionic plugin (`@ionic/angular`) counts `ionViewWillEnter`, `ionViewDidEnter`, `ionViewWillLeave` and `ionViewDidLeave` as used. The [plugin source](https://github.com/fallow-rs/fallow/tree/main/crates/core/src/plugins) lists the names that each plugin knows.
- When the class extends another class, a call of the member in the parent class counts as a use of the override.
- When code gives an instance in a variable to `Object.keys`, `Object.values`, a rest pattern or `for...in`, fallow counts each member as used.
- A Playwright test that `test.extend<T>()` or `mergeTests(...).extend<T>()` makes from `@playwright/test` uses the members of each fixture class that the test reads.
- A destructured property of a factory result uses the members of the class that the property holds, for example `const { ctx } = newService()` followed by `ctx.seed()`. A local wrapper such as `const setup = () => newService(db)` counts as the factory. The name can have a binding in each test of a file, when each binding destructures the same property of the same call. A parameter or another declaration with the same name in the file stops the credit.

## Known limits

Fallow reads the source text and does not infer types. Without [type-aware analysis](/analysis/type-aware), it reports a member that code calls only through one of these receivers:

- A test double whose type comes from the class, for example `Mocked<StorageRepository>` or a mock that copies the members of the class. A call on the mock does not count as a use of the class member.
- A fixture that a test framework gives to a test without a typed `extend<T>()` call.
- An instance that a library receives and calls through an interface of the library, for example a PDF signer, a mail transport, or a ProseMirror node view.
- A receiver that a helper builds again from a factory result, for example `return { ctx }` after `const { ctx } = newService()`.

With `--type-aware`, the TypeScript checker resolves each call to the class member, so a call through a typed mock, a wrapper or a fixture counts as a use. A class that `implements` a library interface keeps each required member of the interface and each optional member that the library declares, because the library can call it. Some members stay reported in type-aware mode too:

- The TypeScript project of the file has errors that block the analysis.
- The member or its class has a decorator.
- The library receives the class without an `implements` or `extends` clause.

For these members, add the name to [`usedClassMembers`](/reference/config-dead-code#usedclassmembers), or [suppress](/guides/suppress) the finding.
