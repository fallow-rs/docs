## What it reports

Client-bound code reaches a non-public env read.

[Security](/analysis/security) explains how fallow finds it.

## Why it matters

`client-server-leak` reports a candidate when a `use client` module can transitively reach a static non-public `process.env` or `import.meta.env` read. Public-by-convention env prefixes are treated as public. The finding is advisory and still needs bundle, framework, and runtime verification before treating it as a real exposure.

## Example

A module marked `use client` imports code that reads a non-public `process.env` or `import.meta.env` value through a static path.

```tsx title="src/CheckoutButton.tsx"
"use client";

import { createPayment } from "./payments";

export const CheckoutButton = () => (
  <button onClick={() => createPayment(4200)}>Pay now</button>
);
```

```ts title="src/payments.ts"
export const createPayment = (amount: number) =>
  fetch("https://payments.internal/charge", {
    method: "POST",
    headers: { authorization: `Bearer ${process.env.PAYMENT_API_KEY}` },
    body: JSON.stringify({ amount }),
  });
```

## Fix

Keep non-public env reads on the server side, move the value behind an API boundary, or rename only intentionally public values to the framework's public prefix. For a `server-only-import` candidate, the fix depends on the sink.

For a React Router `.server` module, move the call into `loader`, `action`, `middleware` or `headers`, or move the code that the client needs out of the `.server` module.

For other server-only code in Next.js, keep the import out of the `use client` cone; a module that only `next/dynamic(..., { ssr: false })` loads is a false positive.
