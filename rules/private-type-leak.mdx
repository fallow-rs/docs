## What it reports

Exported signature references a private type.

[Dead code](/analysis/dead-code) explains how fallow finds it.

## Why it matters

Exported values or types whose public TypeScript signature references a same-file type declaration that is not exported. Consumers cannot name that private type directly, so the backing type should be exported or removed from the public signature.

## Example

`export function makeUser(): InternalUser` exposes InternalUser even though InternalUser is not exported.

```json title=".fallowrc.json"
{
  "rules": {
    "private-type-leaks": "warn"
  }
}
```

```ts title="src/index.ts"
import { makeUser } from "./user";

console.log(makeUser("Ada").name);
```

```ts title="src/user.ts"
interface InternalUser {
  id: number;
  name: string;
}

export function makeUser(name: string): InternalUser {
  return { id: Date.now(), name };
}
```

## Fix

Export the referenced type, change the public signature to an exported type, or keep the helper private.

## When to keep the code

- In an application, a private `Props`, `Options` or `State` type of an exported function is often intentional. Do not export such a type only to satisfy this rule. Turn the rule on for packages that publish TypeScript declarations.
- While this rule is on for a file, [`unused-type`](/analysis/dead-code#types-in-the-signature-of-an-export) does not report a type that the signature of an export in that file uses, so the two rules do not ask for opposite fixes.

## Notes

- A private member (`#field` or `private`) is not part of the public signature, so its type does not leak.
- Fallow skips Storybook story files, and route files where the framework requires several exports in one file, for example the `page` and `layout` files of the Next.js App Router.
